Exercise 1. fork() copies the address space, not the variable

  • May 12, 2026
  • Kellen Kanarios

Write a program that calls fork(). Before forking, set a variable — say x — to 100. What is its value in the child? What happens when parent and child both change it?

Solution

The child gets a copy of the parent's address space, \(x\) included. Each subsequent write lands in that process's own copy, so neither sees the other's change.

Exercise 2. A file descriptor survives the fork

  • May 12, 2026
  • Kellen Kanarios

Open a file with open() and then fork(). Can both child and parent use the returned descriptor? What happens when they write to the file concurrently?

Solution

Both have access to the same descriptor. Concurrent writes can in principle interleave, but in my runs whichever process was scheduled first always finished writing before the other started — plausibly a scheduling artifact rather than a guarantee.

Exercise 3. Ordering child before parent without wait()

  • May 12, 2026
  • Kellen Kanarios

Write a program where the child prints "hello" and the parent prints "goodbye", with the child always printing first. Can you do it without calling wait() in the parent?

Solution

Reusing the shared file from the previous exercise: have the child write a value, and have the parent spin in a while loop until it reads that value back. It works, and it is miserable — which is presumably why wait() exists.

Exercise 4. What wait() returns, and what it does in the child

  • May 12, 2026
  • Kellen Kanarios

Now use wait() in the parent to wait for the child. What does it return? What happens if you call wait() in the child?

Solution

It returns the pid of the child that died. Called in the child — which has no children of its own — it returns \(-1\) immediately.

Exercise 5. Why exec() has so many variants

  • May 12, 2026
  • Kellen Kanarios

Write a program that calls fork() and then some form of exec() to run /bin/ls. Try the variants — execl(), execle(), execlp(), execv(), execvp(), execvP(). Why are there so many spellings of one call?

Solution

The suffixes are a small matrix of three independent choices. The v family takes a variable-size argument vector where the l family takes a fixed argument list. The e family takes an explicit environment — the list of environment variables the new program will see — instead of inheriting the caller's. The p family resolves the program name against PATH, the way a shell does, instead of requiring a path.

Exercise 6. When waitpid() beats wait()

  • May 12, 2026
  • Kellen Kanarios

Rewrite the previous program using waitpid() instead of wait(). When is waitpid() the one you want?

Solution

When a parent has several children. wait() returns on whichever dies first; waitpid() lets you name the child you care about.

Exercise 7. printf() after closing STDOUT in the child

  • May 12, 2026
  • Kellen Kanarios

Create a child process that closes standard output (STDOUT_FILENO). What happens if the child then calls printf()?

Solution

Nothing prints from the child. The parent's stdout is a separate descriptor and is untouched, so it still prints.

Exercise 8. Connecting two children with pipe()

  • May 12, 2026
  • Kellen Kanarios

Create two children and connect the standard output of one to the standard input of the other using pipe().

Solution

It worked only once I added fflush() — the writer's output was sitting in stdio's buffer rather than in the pipe. Whether that is required in general or an artifact of how I structured the writer, I am not sure.

    Exercise 1. CPU utilization of two compute-bound processes

    • May 12, 2026
    • Kellen Kanarios

    Run process-run.py with the flags -l 5:100,5:100. What should the CPU utilization be?

    Solution
    Prediction. Two processes of \(5\) instructions each, every instruction using the CPU with probability one, so nothing ever blocks: 
    Process 0
  cpu
  cpu
  cpu
  cpu
  cpu

Process 1
  cpu
  cpu
  cpu
  cpu
  cpu
    Utilization should be 100%. The first process runs to completion, then the second. Were both waiting on I/O this would not hold.

    Confirmed with -c -p: 100% utilization.

    Exercise 2. Completion time when one process blocks on I/O

    • May 12, 2026
    • Kellen Kanarios

    Run process-run.py with the flags -l 4:100,1:0. How long does it take to complete both processes?

    Solution
    Prediction. One process of \(4\) CPU instructions and one of a single I/O instruction: 
    Process 0
  cpu
  cpu
  cpu
  cpu

Process 1
  io
  io_done
    It should take \(4 + \text {time of IO}\): the compute-bound process runs its four instructions first, and only then does the second process start and sit out the whole I/O.

    With -c -p it takes \(11\) timesteps, which is indeed \(\approx 4 + \text {time of IO}\).

    Exercise 3. Why the order of the processes matters

    • May 12, 2026
    • Kellen Kanarios

    Switch the order: ./process-run.py -l 1:0,4:100. What happens now? Does switching the order matter, and why?

    Solution
    Prediction. Now the trace is 
    Process 0
  io
  io_done

Process 1
  cpu
  cpu
  cpu
  cpu
    which should take \(\max (5, 1 + \text {time IO})\) depending on the -L flag. Order matters, because the CPU instructions can run while the non-blocking I/O is outstanding — which is the argument for scheduling at all.

    It takes \(7\) timesteps: the I/O overlaps with the compute as expected.

    Exercise 4. SWITCH_ON_END serializes an I/O-bound process against a CPU-bound one

    • May 12, 2026
    • Kellen Kanarios

    The -S flag decides how the system reacts when a process issues I/O. Under SWITCH_ON_END the system does not switch away while a process is doing I/O; it waits until that process finishes entirely. What happens with one I/O-bound and one CPU-bound process — -l 1:0,4:100 -c -S SWITCH_ON_END?

    Solution

    The whole CPU-bound process is held hostage by the I/O:

    Time        PID: 0        PID: 1           CPU           IOs
  1         RUN:io         READY             1
  2        BLOCKED         READY                           1
  3        BLOCKED         READY                           1
  4        BLOCKED         READY                           1
  5        BLOCKED         READY                           1
  6        BLOCKED         READY                           1
  7*   RUN:io_done         READY             1
  8           DONE       RUN:cpu             1
  9           DONE       RUN:cpu             1
 10           DONE       RUN:cpu             1
 11           DONE       RUN:cpu             1

    Exercise 5. SWITCH_ON_IO overlaps the two

    • May 12, 2026
    • Kellen Kanarios

    Run the same processes with switching set to happen whenever one is WAITING for I/O — -l 1:0,4:100 -c -S SWITCH_ON_IO. What happens now? Use -c and -p to confirm.

    Solution
    Prediction. Timestep \(1\) still runs RUN:io, but then PID: 1 should occupy the next \(4\) timesteps until it completes. After one more BLOCKED step we run RUN:io_done and both finish.

    Exactly that:

    Time        PID: 0        PID: 1           CPU           IOs
  1         RUN:io         READY             1
  2        BLOCKED       RUN:cpu             1             1
  3        BLOCKED       RUN:cpu             1             1
  4        BLOCKED       RUN:cpu             1             1
  5        BLOCKED       RUN:cpu             1             1
  6        BLOCKED          DONE                           1
  7*   RUN:io_done          DONE             1

    Exercise 6. IO_RUN_LATER wastes the overlap it just bought

    • May 12, 2026
    • Kellen Kanarios

    With -I IO_RUN_LATER, a completed I/O does not immediately return the issuing process to the CPU; whatever was running keeps running. What happens with ./process-run.py -l 3:0,5:100,5:100,5:100 -S SWITCH_ON_IO -I IO_RUN_LATER -c -p? Are system resources being used effectively?

    Solution
    Prediction. They are not. All three CPU-bound processes finish before we return to the I/O-bound one, which then issues its next io with nothing left to overlap it against — the concurrency benefit evaporates.

    The trace is long, but the totals say it:

    Stats: Total Time 31
Stats: CPU Busy 21 (67.74%)
Stats: IO Busy  15 (48.39%)

    Exercise 7. IO_RUN_IMMEDIATE and why recent I/O predicts more I/O

    • May 12, 2026
    • Kellen Kanarios

    Run the same processes with -I IO_RUN_IMMEDIATE, which runs the issuing process as soon as its I/O completes. How does the behavior differ, and why might rerunning a process that just finished I/O be a good idea?

    Solution
    Prediction. Returning to the I/O-bound process lets it issue its next io before handing the CPU back, so the requests stay in flight alongside the compute. As a heuristic it is a bet that a process which just did I/O will do more of it.

    The bet pays:

    Stats: Total Time 21
Stats: CPU Busy 21 (100.00%)
Stats: IO Busy  15 (71.43%)

    Exercise 8. Which flag matters under randomly generated workloads

    • May 12, 2026
    • Kellen Kanarios

    Run some randomly generated processes — -s 1 -l 3:50,3:50, -s 2 -l 3:50,3:50, -s 3 -l 3:50,3:50. Predict how the trace turns out. What changes between -I IO_RUN_IMMEDIATE and -I IO_RUN_LATER, and between -S SWITCH_ON_IO and -S SWITCH_ON_END?

    Solution
    Prediction. With each instruction a coin flip between CPU and I/O, IO_RUN_LATER and IO_RUN_IMMEDIATE should be close to indistinguishable. SWITCH_ON_IO over SWITCH_ON_END should matter more and more as processes are added, since there is almost always CPU work waiting — though with only two processes the gain may be small, as both are likely to be blocked at some point.

    For seed -s 1 the two -I policies perform identically, and enabling SWITCH_ON_IO improves both CPU and I/O utilization.

    7. Scheduling: Introduction [ostep-ch7]

    • May 12, 2026
    • Kellen Kanarios

    Exercise 1. When SJF matches FIFO

    • May 12, 2026
    • Kellen Kanarios

    For what types of workloads does SJF scheduling deliver the same turnaround times as FIFO scheduling?

    Solution

    Workloads that arrive in increasing order of total job time — FIFO is then already running them shortest-first.

    Exercise 2. When SJF matches round robin

    • May 12, 2026
    • Kellen Kanarios

    For what workloads and quantum lengths does SJF deliver the same response times as Round-robin scheduling?

    Solution

    Short jobs and long quanta. A quantum long enough to hold a whole job turns round robin into run-to-completion, and short jobs make the ordering hardly matter.

    Exercise 3. Response time under SJF as jobs grow

    • May 12, 2026
    • Kellen Kanarios

    What happens to response time under SJF as job lengths increase?

    Solution

    It degrades: the longest job waits out every shorter one ahead of it, so as those grow the response time grows with them.

    Exercise 4. Worst-case response time under round robin

    • May 12, 2026
    • Kellen Kanarios

    What happens to response time under round robin as the quantum grows? Can you write the worst-case response time for \(N\) jobs?

    Solution

    Job \(i\) waits out the \(i - 1\) slices ahead of it, so with quantum \(S\) the worst case is the last job's:

    \[\mathrm {RT}_{\max } = S(N - 1)\]

    and averaging over the \(N\) jobs halves it,

    \[\overline {\mathrm {RT}} = \frac {1}{N} \sum _{i = 1}^{N} (i - 1)S = \frac {S}{N} \cdot \frac {N(N-1)}{2} = \frac {S(N - 1)}{2}\]

    Both grow linearly in the quantum: round robin's responsiveness is precisely what a long quantum spends.
