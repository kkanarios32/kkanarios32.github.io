XLA Compilation [M74N]

  • May 22, 2026
  • Kellen Kanarios

Overview.

  • Dispatch / Cache: caches compilation based on input argument signatures i.e. shapes, dtypes, sharding. If shapes change will need to recompile.
  • Lowering: Python -> jaxpr -> StableHLO. This stage is a translation, not an optimization — no Operator fusion happens here. See chlo desugars, stablehlo is stable, mhlo is internal for the dialects involved and Three calls, three IR levels for how to print each level.
  • XLA: StableHLO is converted to HLO, and the optimizing passes — simplification, layout assignment, fusion, collective scheduling, memory assignment — run there. Read after_optimizations, not before_optimizations, for anything performance-related (Only after_optimizations matches the profile).
  • TPU specific: Further reduced to LLO IR, then very large instruction word (VLIW) scheduling to map dot products to Matrix Multiply Unit (MXU).
Remark. The Python source is thrown away as soon as it is traced into a jaxpr, and the jaxpr in turn is thrown away once it is lowered. What XLA ingests is StableHLO, which it converts to HLO before optimizing; HLO is XLA's internal representation, not its input format. The only thread back to the Python you wrote is the metadata carried on each instruction (op_name is the trace path back to Python).

Lifecycle of a JAX program [NR79]

  • August 7, 2026
  • Kellen Kanarios

We have the following compilation pipeline

  1. Tracing: Python / JAX -> jaxpr
    • jax.make_jaxpr(fun)(*args)
    • Abstract execution. JAX executes python code using abstract tracer objects instead of real arrays.
    • Every operation and its intermediate result is recorded into jaxpr.
    • Sequence used to construct a grap, which the XLA compiler will later optimize.
    • Python code is executed once during tracing but excluded from final graph.
    • Each JAX primitive registers functions for
      • Lowering to StableHLO
      • How it is transformed under grad and vmap.
  2. Lowering: Jaxpr -> StableHLO
    • fn_lowered = jax.jit(fun).lower(*args)
    • stable_hlo = fn_lowered.as_text()
    • fn_lowered.compiler_ir(dialect='stablehlo') for the MLIR module rather than its text. There is no 'hlo' dialect to ask for here — HLO is produced inside XLA, one step later (chlo desugars, stablehlo is stable, mhlo is internal), and you reach it through .compile().as_text() (Three calls, three IR levels).
    • Multiple ML frameworks lower to StableHLO.
      • Hardware agnostic.
      • Backwards compatible.
  3. Compile: HLO -> Optimized HLO -> LLO IR -> VLIW -> Executables
    • compiled = fn_lowered.compile()
    • compiled.runtime_executable() returns a LoadedExecutable.
    • Useful(?) compiled.cost_analysis().
    • HLO:
      • Input for XLA compiler.
      • Directed acyclic graph of copmutational operations.
      • All array dimensions are known at compile time.
      • Limited opcodes i.e. Add, Multiply, Transpose, Dot, etc.

XLA Shapes and Memory Layout.

  • Every data type defined by data type and fixed dimensions, determined at compile time.
  • Minor-to-major order i.e. fastest changing to slowesting changin.
  • Tiling: arrays are split into smaller blocks to fit into VREG. Want to arrange data to efficiently fit VREG.

Execution.

  • Move tensors from CPU to HBM. Sharding is taken care of by PJIT if on TPU pod.
  • Async: Immediately returns a Future JAX array while the hardware executes VLIW microcode asynchronously.
  • Buffer management: Returns pointer to TPU memory. All handled lazily. Not copied back to CPU until jax.block_until_ready().

Getting the dumps

  • Kellen Kanarios

Half of reading compiler output is arranging to read the right compiler output. The recurring mistake is answering a performance question from before_optimizations, which describes a program that never ran.

Card. Three calls, three IR levels [AGEG]

  • August 22, 2026
  • Kellen Kanarios

How do you print each IR level for a JAX function f?

Answer
  1. jaxpr — jax.make_jaxpr(f)(x).
  2. StableHLO, pre-XLA — jax.jit(f).lower(x).as_text(), or .compiler_ir(dialect='stablehlo').
  3. Optimized HLO, post-XLA passes and matching the profile — jax.jit(f).lower(x).compile().as_text().
The three answer genuinely different questions, and reaching for the wrong one wastes an afternoon (Lifecycle of a JAX program):
  • The jaxpr says what tracing captured — so it answers "why is this constant baked in", "why is there a convert_element_type here" (A weak type adopts the other operand's dtype), "did my Python branch get traced at all".
  • The StableHLO says what JAX handed to XLA — the boundary where a JAX bug becomes an XLA bug.
  • The optimized HLO says what XLA built — fusions, layouts, collectives (Only after_optimizations matches the profile).

Card. Only after_optimizations matches the profile [BQUG]

  • August 22, 2026
  • Kellen Kanarios

What is the difference between the before_optimizations and after_optimizations HLO files in an XLA dump?

Answer before_optimizations — the HLO as imported from StableHLO. Shapes carry no meaningful layouts yet (The layout is minor-to-major), nothing is fused, and there is roughly one instruction per source operation. Read it when you want to know what JAX asked for. after_optimizations — past simplification, layout assignment, Operator fusion, collective scheduling, and memory assignment. Read it when you want to know what runs. Only the second one corresponds to the kernels in a profile, because the fusion names in the profile are the fusion instruction names here (A fusion op is a kernel launch boundary). A performance question answered from before_optimizations is answered about a program that never executed — the op you are worried about may have been fused away, folded, or duplicated (The dump filename encodes the stage).

Card. Per-pass dumps find the pass that broke it [8U47]

  • August 22, 2026
  • Kellen Kanarios

What does XLA_FLAGS=--xla_dump_to=/tmp/dump give you, and how do you get per-pass IR?

Answer A directory of per-module files: pre- and post-optimization HLO text (Only after_optimizations matches the profile), the buffer assignment, and on GPU the generated PTX and LLVM IR (The dump filename encodes the stage). Add --xla_dump_hlo_pass_re=.* to dump the HLO before and after every pass matching the regex. That is how you find which pass introduced a copy or broke a fusion — bisect the pass list rather than staring at the endpoints. Narrow the regex once you have a suspect, since .* on a real model produces a great many files. --xla_dump_hlo_as_html and --xla_dump_hlo_as_dot give graph views, which are far easier than text for fusion structure (A fusion op is a kernel launch boundary) — a flat instruction list hides exactly the thing you are looking at. The MLIR side has the same facility in --mlir-print-ir-after-all (Print generic, print locations, disable threading).

Card. The dump filename encodes the stage [JFMQ]

  • August 22, 2026
  • Kellen Kanarios

Reading an XLA dump directory: what is in module_0001.jit_f.before_optimizations.txt versus the after_optimizations and sm_XX files?

Answer The filename encodes module index, entry name, and pipeline stage. Read them in this order:
  1. before_optimizations — one-to-one with your StableHLO. Use it to confirm JAX emitted what you meant.
  2. after_optimizations — fused, laid out, scheduled. Map profile kernels to the fusion names here (Only after_optimizations matches the profile).
  3. Backend artifacts — PTX and LLVM IR on GPU, Mosaic or LLO on TPU. What actually ran.
Each module index is a separate compilation, so a program with several jit boundaries, or one that retraced on a new input shape, produces several sets. When a dump directory has more modules than you expected, that count is the finding — it means recompilation you did not intend (XLA Compilation).
