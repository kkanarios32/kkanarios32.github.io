Card. Commit is a state transition, not an allocation [W5Z4]

  • August 9, 2026
  • Kellen Kanarios

A store's lifetime: when is its Store buffer slot allocated, and what changes at Reorder buffer commit?

Answer The slot is allocated at dispatch/rename, not at commit. It has to exist before the store executes: that is where the address and data get written in, and where younger loads find the value to Store-to-load forwarding. Commit is only a state transition. The entry stops being speculative — it becomes a senior store, and is now eligible to drain. Nothing reaches the cache at that instant.

Context

    Definition. Store buffer [UNB6]

    • May 13, 2026
    • Kellen Kanarios

    A FIFO of stores that have left the pipeline but are not yet globally visible, decoupling instruction commit from cache write. A store's slot is allocated early — at dispatch/rename, since it must exist before execute for the address and data to be written into — so commit is not a handoff into the buffer but a state transition within it: when the store reaches the head of the Reorder buffer, its entry stops being speculative and becomes a senior store, eligible to drain. Nothing reaches L1 at that instant. The actual cache write, called drain, happens asynchronously and may be delayed by cache misses, coherence traffic, or memory-ordering rules.

    Without this split, the ROB would have to stall on a cache miss for every store. With it, once a store is known to be non-speculative, the front-end moves on while the store buffer absorbs whatever latency the memory hierarchy imposes. Commit and drain are therefore two distinct moments in the lifetime of a store:

    • Commit — the store is architecturally real. Younger speculation cannot squash it, but other cores do not see it yet.
    • Drain — the value is written to L1 and becomes visible to the coherence protocol, and therefore to other cores.

    Between these two moments the value lives only in the store buffer. Younger same-core loads can still observe it through Store-to-load forwarding, but other cores cannot — which is the structural reason Total store order permits store-load reordering across cores. A Memory fence like mfence forces the buffer to drain so that subsequent operations see a consistent global view.

    Drain is not a single event either, and the two halves are easy to conflate. Acquiring permission — an Upgrade if the line is already in S, a GetM if it is not — is distinct from performing the write, merging the data into the line while holding M. Only the second is architecturally required to be post-commit. Ownership is invisible to software, so a core issues the Cache coherence request speculatively at AGU execute time, as soon as the physical address is known and often tens of cycles before retirement; if the store is squashed or the line is snooped away before the merge, nothing is lost but fabric traffic. This is why store misses so often look free in a trace — the latency was paid during Speculative execution, not at the head of the buffer. The merge under M is the store's global visibility point.

    Remark. Retirement bandwidth (ROB commits per cycle) and store bandwidth (drain rate to L1) are separate throughput limits. A workload that retires stores faster than the cache can absorb them eventually backs up the ROB anyway, but the store buffer absorbs short bursts at no cost.

    Related

      Reorder buffer [BI4H]

      • May 13, 2026
      • Kellen Kanarios

      The structure that lets an out-of-order execution CPU look in-order to the programmer. The ROB holds every in-flight instruction in original program order, regardless of the order they actually executed. When the oldest entry has its result ready and all earlier entries have already committed, the ROB commits it — writing its result to architectural state and freeing the slot.

      For stores, commit is only half the story. The ROB entry is freed and the instruction is architecturally real, but the value has not yet reached the cache — it is handed off to the Store buffer for asynchronous drain. This is what keeps the ROB from stalling behind every cache miss: once a store is known to be non-speculative, the front-end can move on.

      Each ROB entry typically tracks:

      • Instruction identity and program order position.
      • Operand register names (and renamed sources).
      • Status — pending, executing, complete, speculated.
      • The instruction's result, held in a data field that doubles as a register renaming register.

      Speculatively-issued instructions also enter the ROB but are tagged. On a branch misprediction, all speculative entries past the mispredicted branch are squashed.

      The Pentium Pro introduced this design with a 40-entry ROB. The ROB sits at both ends of the pipeline — dispatch enters it, retirement leaves it — which is what makes the rest of the back-end free to issue and execute out of order.

      Remark. ROB size, Reservation station count, and pipeline depth set each other's bounds. A shallow pipeline can afford a small ROB; a deep one (Pentium 4 had 126) needs a large one to keep the back-end fed.

      Definition. Store-to-load forwarding [GXCN]

      • May 13, 2026
      • Kellen Kanarios

      The mechanism by which a younger load on the same core observes the value of an older store that is still sitting in the Store buffer and has not yet drained to L1. The load-store unit checks the store buffer for any in-flight store to the same address; if one exists, the load's data comes directly from the buffer entry rather than from the cache, satisfying the same-core sequential semantics that the program expects.

      Forwarding is the reason the commit/drain split does not break the single-core illusion. Within one thread, a store followed by a load to the same address must read the just-stored value — and would, on a machine without a store buffer, because the cache is the single source of truth. With a store buffer, the cache is briefly stale relative to architectural state; forwarding patches that hole.

      The structural consequence shows up in Total store order: store-load reordering across cores is permitted precisely because forwarding makes same-core reads see the new value, while cross-core reads continue to see the old one until drain. This asymmetry is the entire point of TSO's relaxation — the store buffer can hide latency from the issuing thread without forcing other threads to wait.

      Remark. Address matching in the store buffer is partial: most implementations check enough low-order bits to detect a hit but fall back to a stall (or a re-execution) on aliasing or partial-overlap cases. Reliable wide-then-narrow forwarding is one of the harder corners of memory disambiguation.
