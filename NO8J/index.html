HLO [NO8J]

  • August 7, 2026
  • Kellen Kanarios

XLA's internal representation: a directed acyclic graph of tensor operations, with every array dimension known at compile time. It is what StableHLO is converted into on the way into the compiler (chlo desugars, stablehlo is stable, mhlo is internal), and it is not an MLIR dialect — a backend consuming XLA has to translate from HLO on its own (XLA Compilation).

Two design choices shape how an HLO dump reads, and both trade verbosity for locality. Every instruction prints its result shape before the opcode and every operand with its full shape and layout, so a line is self-contained (An HLO line is self-contained); and the module is a flat list of computations rather than a nesting, with ENTRY and ROOT the only structural landmarks (ENTRY names the computation, ROOT names the output). Static shapes are what make the first affordable.

The distinction that matters most in practice is which HLO you are reading. before_optimizations is a transliteration of what JAX emitted; after_optimizations is fused, laid out, and scheduled, and is the only one whose instruction names appear in a profile (Only after_optimizations matches the profile). A performance question answered from the wrong file is answered about a program that never ran.

Example.

The same function after XLA. jax.jit(f).lower(x, w, b).compile().as_text() for tanh(x @ w + b), on CPU. The two fusion bodies are printed first, then the entry computation:

HloModule jit_f, is_scheduled=true,
  entry_computation_layout={(f32[8,16]{1,0}, f32[16,4]{1,0}, f32[4]{0})->f32[8,4]{1,0}}

%fused_computation (param_0: f32[8,16], param_1: f32[16,4]) -> f32[8,4] {
  %param_0 = f32[8,16]{1,0} parameter(0)
  %param_1 = f32[16,4]{1,0} parameter(1)
  ROOT %dot_general.0 = f32[8,4]{1,0} dot(%param_0, %param_1),
      lhs_contracting_dims={1}, rhs_contracting_dims={0},
      metadata={op_name="jit(f)/dot_general" stack_frame_id=2}
}

%fused_computation.1 (param_0.2: f32[8,4], param_1.2: f32[4]) -> f32[8,4] {
  %param_0.2 = f32[8,4]{1,0} parameter(0)
  %param_1.2 = f32[4]{0} parameter(1)
  %add.1 = f32[8,4]{1,0} broadcast(%param_1.2), dimensions={1}
  %add.0 = f32[8,4]{1,0} add(%param_0.2, %add.1)
  ROOT %tanh.0 = f32[8,4]{1,0} tanh(%add.0)
}

ENTRY %main.1 (x.1: f32[8,16], w.1: f32[16,4], b.1: f32[4]) -> f32[8,4] {
  %x.1 = f32[8,16]{1,0} parameter(0), metadata={op_name="x"}
  %w.1 = f32[16,4]{1,0} parameter(1), metadata={op_name="w"}
  %b.1 = f32[4]{0} parameter(2), metadata={op_name="b"}
  %ynn_fusion = f32[8,4]{1,0} fusion(%x.1, %w.1), kind=kCustom, calls=%fused_computation
  ROOT %add_tanh_fusion = f32[8,4]{1,0} fusion(%ynn_fusion, %b.1), kind=kLoop,
      calls=%fused_computation.1
}

Read ENTRY first, then follow calls= (ENTRY names the computation, ROOT names the output). The whole program is two kernels. Everything else in the file is their bodies.

  • Every shape now carries a layout (The layout is minor-to-major), and entry_computation_layout states the ABI the caller must satisfy (The entry layout is the ABI). is_scheduled=true means the order shown is execution order (The gap between start and done is the overlap).
  • The four jaxpr equations became two kernels, split where the hardware splits. The matmul is kind=kCustom — a library-backed emitter, not generated code — and the bias add and tanh are kind=kLoop, one elementwise pass (The fusion kind names the emitter). The broadcast is inside that loop, so the bias is never materialised to 8x4 in memory (A fusion op is a kernel launch boundary).
  • A fusion body's parameter(i) lines up with the fusion op's operands (parameter(i) is positional) — that positional match is the only link between body and call site.
  • The names %add.0 and %add.1 are uniquified junk (The numeric suffix means nothing): %add.1 is a broadcast. Key on metadata instead (op_name is the trace path back to Python).

Card. An HLO line is self-contained [5QXE]

  • August 22, 2026
  • Kellen Kanarios

Name every part of %add.7 = f32[8,128]{1,0} add(f32[8,128]{1,0} %p0, f32[8,128]{1,0} %bcast.3), metadata={op_name="jit(f)/add"}

Answer 
%name = <shape> <opcode>(<typed operands>), <attributes>, metadata={...}
Two things differ from MLIR and both are deliberate. The result shape comes before the opcode, and every operand is printed with its full shape and layout (The layout is minor-to-major). So an HLO line is self-contained. You never scroll up to learn a type — which matters, because an optimized HLO module is one enormous flat list of instructions with no nesting to orient you. The cost is verbosity, and the reason it is affordable is that HLO has no dynamic shapes: every dimension is known at compile time, so every shape can be printed (Question mark is a dynamic dimension, star is unknown rank). The name is meaningless (The numeric suffix means nothing); metadata is what maps the line back to Python (op_name is the trace path back to Python).

Card. The layout is minor-to-major [RR6G]

  • August 22, 2026
  • Kellen Kanarios

What does the {1,0} in f32[8,128]{1,0} mean?

Answer The layout: dimension numbers listed minor-to-major. {1,0} says dimension 1 (size 128) is minor-most — the contiguous one — so this is standard row-major. {0,1} on the same shape would be column-major (XLA Compilation). Layouts appear after XLA's layout assignment pass, so a before_optimizations dump has them but they are not yet meaningful (Only after_optimizations matches the profile). Layouts are the reason for ops that do nothing mathematically. A copy, bitcast, or transpose that leaves the values unchanged is there to satisfy a layout requirement (bitcast is free, copy is not), typically because a dot wants its contracting dimension minor-most (A dot's output order is batch, lhs free, rhs free) or a custom call pinned one (A custom call is a black box XLA cannot fuse across). Chasing copies in optimized HLO is chasing layout.

Card. Tuples are first-class in HLO [31V3]

  • August 22, 2026
  • Kellen Kanarios

What are the HLO shapes s32[], pred[8], (f32[8]{0}, s32[]), and token[]?

Answer
  • s32[] — a rank-0 signed 32-bit scalar. The letter is the class: s signed, u unsigned, f float, plus bf16, f8e4m3 and friends for narrow types. Unlike MLIR, HLO integers are signed or unsigned in the type (Signedness lives in the op, not the type).
  • pred[8] — a boolean array; pred is XLA's bool.
  • Parens are a tuple shape. Tuples are first-class in HLO, and are how every multi-output op and all while state is expressed (A while loop's whole state is one tuple) — which is why get-tuple-element is everywhere (get-tuple-element is free aliasing).
  • token[] — an ordering token, carrying no data. Side-effecting ops (infeed, collectives, after-all) thread a token to express an ordering the dataflow graph otherwise could not.

Card. ENTRY names the computation, ROOT names the output [TN01]

  • August 22, 2026
  • Kellen Kanarios

What do ENTRY and ROOT mark in an HLO module?

Answer ENTRY flags the module's entry computation — the one actually invoked. Every other computation in the file is called by name: fusion bodies (A fusion op is a kernel launch boundary), reducers (reduce removes the dims it lists), while conditions and bodies (A while loop's whole state is one tuple), branch computations. ROOT flags the single instruction whose value is that computation's output. Every computation has exactly one, and in older dumps it is not necessarily the last line textually. Why this is the first thing to find. An optimized HLO file is a flat pile of computations in no useful order. ENTRY tells you where the program starts, ROOT tells you where it ends, and following calls= and to_apply= from there is how you read the rest. Its parameter and result shapes must match entry_computation_layout (The entry layout is the ABI).

Card. The entry layout is the ABI [UON0]

  • August 22, 2026
  • Kellen Kanarios

Read the module header HloModule jit_f, entry_computation_layout={(f32[8,128]{1,0}, f32[128]{0})->f32[8,128]{1,0}}, is_scheduled=true

Answer
  • The module name comes from the jitted function, which is how you tell several compilations apart in a dump directory (The dump filename encodes the stage).
  • entry_computation_layout is the ABI: the parameter shapes and layouts (The layout is minor-to-major) and the result shape the caller must supply and expect. A buffer whose layout disagrees with this is the mismatch, and it is checked here rather than anywhere friendlier.
  • is_scheduled=true means this is a post-scheduling dump, so instruction order is actual execution order and not merely a topological sort of the dataflow.
That last flag changes how you read everything below it. Only in a scheduled dump does the distance between an all-reduce-start and its all-reduce-done mean anything (The gap between start and done is the overlap).

Card. parameter(i) is positional [W9HX]

  • August 22, 2026
  • Kellen Kanarios

What is %p0 = f32[8,128]{1,0} parameter(0), and what does the number mean?

Answer A formal parameter of the enclosing computation. The integer is its position in the parameter list — an index, not a renameable identifier. Where it points depends on the computation:
  • In the ENTRY computation (ENTRY names the computation, ROOT names the output), parameter(i) is the i-th argument in entry_computation_layout (The entry layout is the ABI), and so the i-th argument you passed to the jitted function.
  • In a fusion computation, the parameters correspond positionally to the fusion op's operands (A fusion op is a kernel launch boundary).
That positional correspondence is the thread you pull to read a fusion body. The body names nothing that ties it to the caller — you match parameter(0) to the first operand of the fusion instruction and work inward from there.

Card. The numeric suffix means nothing [06HG]

  • August 22, 2026
  • Kellen Kanarios

What does the trailing .7 in %add.7 tell you?

Answer Nothing semantic. It is uniquification of a name that is otherwise derived from the opcode or the metadata — the compiler needed the names distinct and appended a counter. The numbers change between dumps and between passes, so never key notes, scripts, or diffs on them. Two dumps of the same program with one extra pass in between will renumber wholesale, and a diff on names shows an enormous change where nothing happened. Key on metadata op_name instead (op_name is the trace path back to Python), which is derived from the JAX trace path and is stable, or on the structure of the graph. The same instability holds for MLIR value names (SSA names are printing hints).

Card. op_name is the trace path back to Python [FG58]

  • August 22, 2026
  • Kellen Kanarios

How do you map an HLO instruction back to Python?

Answer The metadata field: 
%dot_general.0 = f32[8,4]{1,0} dot(%param_0, %param_1), lhs_contracting_dims={1},
    rhs_contracting_dims={0}, metadata={op_name="jit(f)/dot_general" stack_frame_id=2}
op_name is the JAX trace path, not just a label: nested transformation scopes — jit, jvp, transpose, vmap, remat — separated by slashes, ending in the jaxpr primitive that emitted the op. So it says more than a source line. It says which transformation produced this instruction: an op under jvp(...) is forward-mode work, one under transpose(...) is the backward pass (A grad jaxpr is the forward program plus its transpose). The source location is indirect. Current XLA interns it: stack_frame_id indexes a StackFrames table printed at the top of the module, which chains through FileLocations to FileNames and FunctionNames. You resolve the id there rather than reading a filename off the instruction, and the chain gives you the whole call stack, not one frame. This is the path that survives the passes that scramble names (The numeric suffix means nothing). The MLIR equivalent is the location (Locations are the provenance of an op).

2. Fusion

  • August 7, 2026
  • Kellen Kanarios

Operator fusion is where XLA earns its keep, and the fusion instruction is the kernel launch boundary — the unit that shows up in a profile and the unit a performance question is usually about.

Card. A fusion op is a kernel launch boundary [ZUYH]

  • August 22, 2026
  • Kellen Kanarios

What is a fusion instruction in HLO and where is its body?

Answer 
%fusion.2 = f32[8,128]{1,0} fusion(f32[8,128]{1,0} %p0, f32[128]{0} %p1),
            kind=kLoop, calls=%fused_computation.2
The body is a separate computation named by calls=, printed elsewhere in the module; its parameters line up positionally with the fusion's operands (parameter(i) is positional). The fusion op is the kernel launch boundary. Everything inside the body runs in one kernel, with intermediates staying in registers instead of round-tripping to High bandwidth memory — that is the whole point of Operator fusion. It is therefore the unit that matters for performance work: a name in a profile is a fusion name, and the question "why is this slow" is usually "what ended up inside this body, and what did not". kind= says which emitter generated it (The fusion kind names the emitter).

Card. The fusion kind names the emitter [L148]

  • August 22, 2026
  • Kellen Kanarios

What do the HLO fusion kinds kLoop, kInput, kOutput, and kCustom mean?

Answer
  • kLoop — elementwise-style: one loop nest over the output shape, one element per iteration.
  • kInput — driven by the input iteration space. Used for reductions and transposes, where the operand shape rather than the result shape dictates the loop (reduce removes the dims it lists).
  • kOutput — fuses producers into an op whose output shape drives the loop, keeping a shared operand live in registers across them.
  • kCustom — a hand-written emitter or library-backed pattern: a cuDNN or cuBLAS convolution, a Triton emitter.
The kind names the emitter, which is what you actually want when reading a profile. A slow kLoop is a bandwidth question; a slow kInput is usually a reduction whose layout fights its access pattern; a kCustom means the answer is in a library's tuning, not in XLA.

3. The opcodes

  • August 7, 2026
  • Kellen Kanarios

A small instruction set whose subtlety lives almost entirely in attributes: which dimensions contract, which are removed, which way a permutation reads. The layout-driven ops repay the closest reading, since they are where a layout mistake surfaces as bandwidth.

Card. A dot's output order is batch, lhs free, rhs free [7EEZ]

  • August 22, 2026
  • Kellen Kanarios

Read this matmul. %dot.5 = f32[4,8,32]{2,1,0} dot(f32[4,8,16]{2,1,0} %a, f32[4,16,32]{2,1,0} %b), lhs_batch_dims={0}, lhs_contracting_dims={2}, rhs_batch_dims={0}, rhs_contracting_dims={1}

Answer Batch dimensions pair up and are preserved, contracting dimensions pair up and are summed away, and everything left over is free — the same three-way split as StableHLO (Batch, contract, free, and the output order is fixed) and jaxpr (dimension_numbers is contracting then batch). The output order is always batch, then lhs free in order, then rhs free in order, giving [4, 8, 32] here. You never choose it. Then read the layouts, because that is where the performance question lives. If a contracting dimension is not minor-most for its operand's layout (The layout is minor-to-major), the data has to be moved before the Matrix Multiply Unit (MXU) or tensor core can consume it — so expect a transpose or copy next to the dot (bitcast is free, copy is not), and expect it to cost real bandwidth.

Card. dim_labels spells out three layouts [M3CE]

  • August 22, 2026
  • Kellen Kanarios

Read the convolution annotations window={size=3x3 stride=2x2 pad=1_1x1_1}, dim_labels=b01f_01io->b01f

Answer window describes the spatial sweep: the window size, the stride, and per-dimension padding written low_high. So pad=1_1x1_1 is one before and one after in each of two spatial dimensions. The field can also carry lhs_dilate and rhs_dilate, which is how transposed and atrous convolutions are expressed rather than as separate opcodes. dim_labels gives three layouts at once, as input_kernel->output, with b batch, f feature, i input feature, o output feature, and digits for spatial dimensions. So b01f_01io->b01f is an NHWC input, an HWIO kernel, and an NHWC output. These are logical dimension roles, distinct from the physical minor-to-major layout (The layout is minor-to-major) — and a mismatch between the two is the usual reason a transpose appears beside a convolution.

Card. broadcast dimensions read operand to output [XML3]

  • August 22, 2026
  • Kellen Kanarios

In %b = f32[2,3]{1,0} broadcast(f32[3]{0} %a), dimensions={1}, what does dimensions mean?

Answer For each operand dimension in order, which output dimension it maps to. Operand dim 0 lands at output dim 1; output dimensions not mentioned are the newly broadcast ones. This is the same convention as stablehlo.broadcast_in_dim (broadcast_in_dim maps operand dims onto output dims), which is what it lowers from. Note that it reads the opposite way from transpose (transpose dimensions read output from operand), which lists a source dimension per output position. Both attributes are a list of integers on an op that rearranges dimensions, and confusing them is the single easiest mistake to make in an HLO dump. The tell is length: a broadcast's list has the operand's rank, a transpose's has the output's.

Card. transpose dimensions read output from operand [8721]

  • August 22, 2026
  • Kellen Kanarios

In transpose(%a), dimensions={1,0,2}, which way does the permutation go?

Answer Output dimension i takes operand dimension dimensions[i]. So output dim 0 is operand dim 1 — you read a source per output position, the opposite direction from broadcast (broadcast dimensions read operand to output). Then check whether it moves any data. If the permutation is a no-op given the operands' layouts (The layout is minor-to-major) — the bytes are already in the order the result wants — XLA rewrites it to a bitcast, which is free. A permutation that genuinely reorders bytes stays a transpose or becomes a copy, and costs a full read and write of the array (bitcast is free, copy is not). So a transpose in optimized HLO is worth a second look: either it vanished into a bitcast, or someone is paying for it.

Card. reduce removes the dims it lists [EE3R]

  • August 22, 2026
  • Kellen Kanarios

Read %r = f32[8]{0} reduce(f32[8,128]{1,0} %a, f32[] %zero), dimensions={1}, to_apply=%add_computation

Answer dimensions lists the dimensions that are removed. The second operand is the init value — the identity of the reducer, and the answer for an empty reduction. to_apply names a computation of two scalars to one scalar, so reductions are user-defined rather than drawn from a fixed list (reduce takes a computation, not an enum). Variadic reduce is the part worth knowing. It takes several operand and init pairs and returns a tuple (Tuples are first-class in HLO), with the reducer taking and yielding one scalar per pair. That is how argmax is expressed — reduce the values and the indices together, with a reducer that compares on the value and carries the index — and likewise a fused mean-and-variance. So a reduce with a tuple result is not multiple reductions; it is one pass whose accumulator has several fields.

Card. bitcast is free, copy is not [KG5S]

  • August 22, 2026
  • Kellen Kanarios

Distinguish HLO's reshape, bitcast, and copy.

Answer
  • reshape — a logical shape change. Whether it costs anything depends on the layouts (The layout is minor-to-major) on either side; before layout assignment you cannot yet tell.
  • bitcast — free reinterpretation: the same bytes, a different shape or layout. Emitted after layout assignment, once the compiler has proved no movement is needed. Costs nothing at run time.
  • copy — real data movement, almost always to satisfy a layout or memory-space requirement.
So the three are a progression, not three ways of saying the same thing: a reshape resolves into a bitcast if the layouts cooperate and a copy if they do not. Many copies in optimized HLO is a layout problem worth chasing — usually a dot (A dot's output order is batch, lhs free, rhs free) or a custom call (A custom call is a black box XLA cannot fuse across) that pinned a layout the rest of the program does not want.

Card. get-tuple-element is free aliasing [W0FU]

  • August 22, 2026
  • Kellen Kanarios

What is %gte.1 = f32[8]{0} get-tuple-element(%t), index=0, and why is it everywhere?

Answer It extracts one element of a tuple value. Tuples are how HLO returns more than one thing (Tuples are first-class in HLO), so every multi-output op is followed by a fan of these: while (A while loop's whole state is one tuple), a fusion with several outputs, a custom call, sort, variadic reduce (reduce removes the dims it lists). They are free at run time — pure aliasing into the tuple's buffers, no data moves. So read them as punctuation, not as work. A while body that is half get-tuple-element at the top and tuple at the bottom is not doing anything; it is unpacking and repacking the carry. MLIR avoids the whole idiom by giving ops multiple results natively (A multi-result op binds one name and indexes into it).

Card. A while loop's whole state is one tuple [YXTI]

  • August 22, 2026
  • Kellen Kanarios

Read %w = (s32[], f32[8]{0}) while(%init), condition=%cond, body=%body

Answer A loop whose entire state is one tuple value. %cond is a computation from that tuple to pred[]; %body is a computation from the tuple to the same tuple. Trip counters, carried values, and the arrays being scanned are all packed into that one tuple, which is why loop bodies are full of get-tuple-element and tuple pairs (get-tuple-element is free aliasing) — the body has to unpack the state, work, and repack it. This is what jax.lax.scan and fori_loop lower to (consts, then carry, then xs), and the packing is where their structure gets lost: the jaxpr's clean split into consts, carry, and xs becomes tuple indices you have to recover by counting. Read the jaxpr first when you want to know what the loop means, and the HLO when you want to know what it costs.

Card. dynamic-slice clamps instead of failing [0WMU]

  • August 22, 2026
  • Kellen Kanarios

What is the clamping rule for dynamic-slice(%operand, %i0, %i1), dynamic_slice_sizes={1,128}?

Answer The start indices are scalar operands, one per dimension, and they are clamped so the whole slice stays in bounds: \[\text {start} = \mathrm {clamp}(\text {index},\; 0,\; \text {dim size} - \text {slice size})\] There is no out-of-bounds error — you silently get a shifted slice. That is a deliberate choice: on an accelerator there is nowhere to raise from, so the semantics are total. It is also why an off-by-one in indexing code produces plausible wrong numbers rather than a crash. The sizes must be compile-time constants, since the result shape is part of the type (An HLO line is self-contained) — which is why genuinely dynamic shapes need a different construct entirely. Its dual is dynamic-update-slice, the basis of every in-place buffer update and what x.at[i].set(v) becomes.

Card. iota builds indices without a constant [58OB]

  • August 22, 2026
  • Kellen Kanarios

What do iota(), iota_dimension=1 and constant({...}) do in HLO?

Answer iota generates \(0, 1, 2, \ldots \) along the given dimension and is constant across the others. It is how arange, index comparisons, and position-dependent masks appear — a causal attention mask is an iota on rows compared against an iota on columns. The point is that it materialises nothing. A mask built from iota is computed inside the consuming kernel, so it fuses (A fusion op is a kernel launch boundary) and never occupies High bandwidth memory. The same mask written as a literal would be a constant the size of the attention matrix, read from memory every step. constant embeds a literal, and a large one is elided in the text dump as {...} — present in the module, dropped from the printout, the same courtesy MLIR extends with dense_resource (A scalar inside dense is a splat).

Card. A custom call is a black box XLA cannot fuse across [2MM7]

  • August 22, 2026
  • Kellen Kanarios

Read custom-call(%a, %b), custom_call_target="tpu_custom_call", operand_layout_constraints={...}, backend_config="...", api_version=API_VERSION_STATUS_RETURNING

Answer The escape hatch to code XLA does not generate: library kernels (cuBLAS, cuDNN), Pallas and Mosaic or Triton kernels (A Pallas kernel is an opaque custom call), host callbacks.
  • custom_call_target selects the registered handler by name.
  • backend_config carries the opaque payload — a serialised Mosaic module, a tuning configuration, an algorithm choice.
  • operand_layout_constraints pins the layouts the handler requires (The layout is minor-to-major).
Everything expensive about a custom call follows from XLA not being able to see inside it. It cannot fuse across the boundary, so the operands are materialised to High bandwidth memory and the results read back; it must assume the declared effects, so it cannot reorder freely; and the pinned layouts can force copy ops on both sides (bitcast is free, copy is not). A hand-written kernel has to beat all of that, not just the kernel XLA would have emitted.

4. Collectives and sharding

  • August 7, 2026
  • Kellen Kanarios

On a sharded program the instructions worth reading are the ones that move bytes between chips. Collectives summary covers what they compute; these cover how to read them out of a dump, and how to tell whether the scheduler overlapped them with anything.

Card. replica_groups says who reduces with whom [6SKD]

  • August 22, 2026
  • Kellen Kanarios

Read all-reduce(%a), replica_groups={{0,1},{2,3}}, to_apply=%add, channel_id=1, use_global_device_ids=true

Answer
  • replica_groups — which devices reduce together. Each inner list is an independent group, so this is two separate AllReduces of two devices, not one of four.
  • to_apply — the combiner computation (reduce removes the dims it lists): sum, max, and so on.
  • channel_id present means cross-partition (SPMD, Sharding) rather than pure cross-replica; with use_global_device_ids the numbers in replica_groups are global device ids rather than per-replica ones.
Read the group structure before the opcode: it tells you which mesh axis this collective runs on, and therefore whether it crosses ICI or the slower host network. The family is Collectives summary: AllGather (with dimensions= naming the concatenation axis), ReduceScatter, all-to-all, and collective-permute with source_target_pairs={{0,1},{1,0}}.

Card. The gap between start and done is the overlap [MHQ6]

  • August 22, 2026
  • Kellen Kanarios

Why do you see all-reduce-start / all-reduce-done pairs (and copy-start / copy-done, async-start / async-done)?

Answer Asynchronous decomposition, so the operation can overlap with compute. start issues it and returns a handle — a tuple of buffers and context (Tuples are first-class in HLO) — and done waits and yields the result. The scheduler is then free to place independent work between them. The distance between the pair is the measurement. In a scheduled dump (is_scheduled=true, The entry layout is the ABI) instruction order is execution order, so an adjacent start and done means the compiler found nothing to overlap and you are paying the full collective latency in serial. That is the cheapest read on whether a sharded model is communication-bound: not the presence of AllReduce (replica_groups says who reduces with whom), which is expected, but how much compute the scheduler managed to slide underneath it.

Card. A sharding annotation is a tiling plus a device order [3IWB]

  • August 22, 2026
  • Kellen Kanarios

Decode sharding={replicated}, sharding={devices=[2,4]<=[8]}, sharding={devices=[2,4]<=[4,2]T(1,0)}, sharding={maximal device=0}

Answer
  • replicated — a full copy on every device.
  • devices=[2,4] — the tensor is tiled two ways on dim 0 and four ways on dim 1. The <=[8] is shorthand for the device list being iota over eight devices.
  • <=[4,2]T(1,0) — that iota device list is reshaped to [4,2] and transposed before being laid over the tiles. Same tiling, different device-to-tile assignment.
  • maximal device=0 — computed on exactly one device.
The device order is not cosmetic. It decides which mesh axis is "fast" — whether neighbouring tiles sit on neighbouring chips over ICI or across a slower hop — so two Sharding annotations with identical tilings can differ by a large factor in collective cost (replica_groups says who reduces with whom). A trailing last_tile_dim_replicate means the final tile dimension is replication rather than data.
