Exercise 1.1. int8 matmul

  • August 5, 2026
  • Kellen Kanarios

Multiplying \(X (B \times D)\) and \(Y (D \times F)\) in int8.

  1. How many bytes loaded from memory?
  2. How many total OPs performed?
  3. What is arithmetic intensity?
  4. What is roofline estimate for \(T_{math}\) and \(T_{comms}\)? What are reasonable upper and lower bounds for runtime of whole operation?
Solution
  1. The only difference here from before is that the loaded / written bytes are divided by \(2\). This means we load \(BD\) bytes for \(X\) and \(DF\) bytes for \(Y\), which is a total of \(BD + DF\) bytes.
  2. The same number of total ops is performed. Namely, for each element in the output matrix (\(BF\) of them) we must perform \(2D\) OPs. This leaves a total of \(2DBF\) OPs.
  3. The arithmetic intensity is now just \(2 \times \) the old arithmetic intensity because we are loading half as many bytes i.e. \(\frac {2DBF}{BD + DF + BF}\).
    4. Remark. After looking at the solution, they also mention that the rule on batch size to saturate arithmetic intensity remains unchanged. Namely, using the heuristic \(B \ll D, F\), we can get that the arithmetic intensity \(\approx \frac {2DBF}{DF} = 2B\). One may think that this means that we can use smaller batch size. However, recall that our in8 peak OPs/s has now doubled to \(3.94e14\). Therefore, the computation is effectively \[2B > \frac {2 \cdot \text {Peak OPs / s}}{\text {HBM Bandwidth}} \iff B > \frac {\text {Peak OPs / s}}{\text {HBM Bandwidth}} = 240\]
    Question. So what is the point of int8?
    Answer.Within each batch, we are actually performing FLOPs \(2 \times \) as fast. Therefore, our computation is actually twice as fast wall clock time!
  4. From above, we know that we are performing \(2DBF\) FLOPs. Assuming our int8 peak OPs/s is \(3.94e14\), this gives \(T_{math} = \frac {2DBF}{3.94e14}\). Similarly, we have that \(T_{comm} = \frac {BD + DF + BF}{8.2e11}\). We know that \(\max \{T_{max}, T_{comm}\} \) is a good lower bound, and that \(T_{max} + T_{comm}\) is a good upper bound.

Exercise 1.5. Memory rooflines for GPUs

  • August 5, 2026
  • Kellen Kanarios

For the H100 SXM, calculate the batch size at which a bfloat16 matrix multiplication will become compute-bound. Note that the Tensor Core FLOPs numbers are twice the true value since they’re only achievable with structured sparsity.

Solution

We only need to find two quantities in the spec sheet 1. the bf16 peak FLOPs/s and 2. the HBM bandwidth. From the spec sheet, a bf16 tensor core on the H100 sxm can achieve \(1.979e15\) FLOPs / s and has a memory bandwidth of \(3.35e12\) bytes / s. Using the approximation from above, we will become compute bound when \(B > \frac {1.979e15}{3.35e12} \approx 591\).

Remark. From the solution, the number we used was with sparsity. It turns out the true number is \(9.89e14\), which gives \(295\) instead of \(590\).

Solution

TPU v5e. From the TPU specs, a TPU v5e has a pod size of \(16\times 16\) and a host size of \(4\times 2\). Therefore, I believe this means that there are \(8\) CPU hosts. The v5e is an inference chip, so it only has one tensor core per chip. Across \(16\times 16\) chips this gives \(256\) tensor cores. Remark. After looking at solution, it seems I misunderstood what host size meant. The host size is the topology of the subunit connected to a single host. So the number of hosts is actually the pod size / host size. This gives \((16\cdot 16) / (4\cdot 2)\) for the v5e and \((16\cdot 20\cdot 28) / (2\cdot 2\cdot 1)\) for the v5p.

Exercise 2.4. General matmul latency

  • August 5, 2026
  • Kellen Kanarios
 Let’s say we want to multiply a weight matrix int8[16384, 4096] by an activation matrix of size int8[B, 4096] where B is some unknown batch size. Let’s say we’re on 1 TPU v5e to start.
  1. How long will this multiplication take as a function of B?
  2. What if we wanted to run this operation out of VMEM? How long would it take as a function of B?
Solution

For the first part, we need to load

\[16384 \cdot 4096 + 4096B~\text {bytes}\]

and store \(B \cdot 16384\) bytes. We need to perform

\[2\cdot B\cdot 16384\cdot 4096~\text {FLOPs}\]

Therefore, the communication time is

\[T_{comm} = (16384 \cdot 4096 + 4096\cdot B + 16384\cdot B)/8.2e11\]

and the math time is

\[T_{math} = (2\cdot B\cdot 16384\cdot 4096)/3.94e14\]

The total computation time will then be \(\max \{T_{math}, T_{comm}\}\) and the ridge point is when \(T_{math} = T_{comm}\). This gives us

\[ \begin {align*} \frac {2\cdot B\cdot 16384\cdot 4096}{3.94e14} &= \frac {16384 \cdot 4096 + 4096\cdot B + 16384\cdot B}{8.2e11} \\ &\iff B = 259 \end {align*} \]

For the second part, VMEM is \(10\times \) faster than HBM. Therefore, our batch size can be \(10\times \) smaller.

Remark. The solution says that VMEM is \(22\times \) faster. So the numbers are adjusted accordingly.

Exercise 2.5. ICI Bandwidth

  • August 5, 2026

 Let’s say we have a TPU v5e 4x4 slice. Let’s say we want to send an array of type bf16[8, 128, 8192] from TPU{0,0} to TPU{3, 3}. Let’s say the per-hop latency for TPU v5e is 1μs.
  1. How soon will the first byte arrive at its destination?
  2. How long will total transfer take?
Solution

I believe since we have wrap-around links in the Torus topology we can make it from \((0,0) \to (3,3)\) in \(4\) hops. If each hop latency is \(1\mu s\) then it should take \(4 \mu s\).

From TPU specs, the TPU v5e has ICI bandwidth \(4.5e 10\). We need to transfer \(2\cdot 8\cdot 128\cdot 8192\) bytes. Naively, I am going to say that this means it will take

\[\frac {2\cdot 8\cdot 128\cdot 8192}{4.5e 10} s,\] factoring in latency this gives \(372 + 4 \mu s\).
Remark. So the wraparound links are actually only on pods of \(16 \times 16\) or larger. This means it is actually \(6\) hops from \((0,0) \to (3,3)\). Also, we can use the bi-directional capabilities of the network to half the time it will take to send the whole array.

Exercise 2.6. pulling it all together

  • August 5, 2026
  • Kellen Kanarios
 Imagine you have a big matrix \(A\): int8[128 * 1024, 128 * 1024] sharded evenly across a TPU v5e 4x4 slice but offloaded to host DRAM on each chip. Let’s say you want to copy the entire array to TPU{0, 0} and multiply it by a vector bf16[8, 128 * 1024]. How long will this take?
Solution

From the question wording, we are assuming the vector is already on TPU{0,0}.

From TPU specs, the host configuration for TPU v5e is \(4 \times 2\). I believe this means in a \(4 \times 4\) pod there will be \(2\) CPUs. If this is the case, then for the half of chips on the other host, we first have to transfer to our host via DCN which has bandwidth \(3.125e 9\) for v5e. Since it is sharded evenly, this would be \((1/2) \cdot 128 \cdot 128 \cdot 1024 \cdot 1024\) bytes we must send over DCN, taking

\[\frac {(1/2) \cdot 128 \cdot 128 \cdot 1024 \cdot 1024}{3.125e 9} = 2.75 s\]

However, now looking at the notes again, we only use DCN for chips not connected via ICI (which makes sense because it clearly slow AF).

Instead, we can first transfer all the bytes to the respective chips over PCIe and then to TPU{0,0} over ICI. To load into HBM, PCIe bandwidth is \(1.6e 10\) bytes/second. Since we can divide across all 16 chips, it will take

\[\frac {128 \cdot 128 \cdot 1024 \cdot 1024}{16\cdot 1.6e 10} = 67.1ms\]

Now to actually get all of the weights onto a single chip, we can follow the previous part. Using bi-directional bandwidth \(9e 10\), we have

\[\frac {128 \cdot 128 \cdot 1024 \cdot 1024}{9e 10} = 190.9ms\]

The remaining time comes from \(\max \{T_{comm}, T_{math}\}\), which are \[T_{math} = \frac {2\cdot 128\cdot 1024\cdot 128 \cdot 1024\cdot 8}{1.97e 14} = 1.39ms\] and \[T_{comm} = \frac {128\cdot 1024\cdot 128\cdot 1024 + 2\cdot 8\cdot 128\cdot 1024 + 2\cdot 128\cdot 1024\cdot 8}{8.2e 11} = 20.9ms \]

Thus, the total is \(67.1 + 190.9 + 20.9 = 278.9ms\).

Remark.

I think I might be so fucking him it is actually unbelievable. My numbers are all off, but the process seems pretty much the same. I also SNIPED the DCN stuff.

However, it seems there is a bit more nuance to the ICI links than I thought. In particular, our number is a lower bound dependent on the amount of utilized inbound links. Since \((0,0)\) is a corner, it only has \(2\) links and that is why the denominator is \(2\cdot 4.5e 10\) and is not because of bi-directional bandwidth. I imagine if there were wraparound links then we could divide the ICI time by \(2\) because there are \(4\) total inbound links.

Exercise Pop Quiz. AllGather

  • August 5, 2026
  • Kellen Kanarios
 How long does it take to perform the AllGatherY([EY, F]) → [E, F] on a TPU v5e with a 2D mesh {'X': 8, 'Y': 4}, for \(E = 2048\), \(F = 8192\) in bf16? What about for \(E = F = 256\)?
Solution

For the large \(E\) and \(F\), we will clearly not be latency bound, so we can just perform the ICI cost. We will have \(N = 2\cdot 2048\cdot 8192\) bytes and the TPU v5e uni-directional bandwidth is \(4.5e 10\). Since we are only gathering over \(1\) dimension, we do not get any additional bandwidth. Thus, it will take \(\frac {N}{4.5e10} = 3.72\text {ms}\).

For the small \(E\) and \(F\), we now need to consider the latency time given by

\[T_{\text {latency}} = \frac {|Y|\cdot T_{\min }}{2} = 2\mu s.\]

Computing the ICI cost, we have \(N = 2\cdot 256\cdot 256\) bytes and \(T_{\text {ICI}} = \frac {N}{4.5e 10} = 0.73 \mu s\). Thus, the total time is \(T = \max \{T_{\text {latency}}, T_{\text {ICI}} = 2\mu s\).

Remark. I divided the latency time by \(2\), when once again the TPU v5e sub-mesh does not support wrap-around links and therefore the hop count is NOT upperbounded by \(|Y|\). Also the hop count is actually \(|Y| - 1\) not \(|Y|\), so the correct answer was just \(T_{\text {min}}\cdot (|Y| - 1) = 3\mu s\).

Exercise 3.6. comparing shardings

  • August 5, 2026
  • Kellen Kanarios
 Let’s say we want to perform \(A[I_X,J_Y]\cdot _J B[J_Y,K]\to C[I_X,K]\) on TPU v5e 4x4. What communication do we perform? How much time is spent on communication vs. computation?
  • What about \(A[I_X,J]\cdot _J B[J_X,K_Y]\to C[I_X,K_Y]\)? This is the most standard setting for training where we combine data, tensor, and ZeRO sharding.
  • What about \(A[I_X,J]\cdot _J B[J,K_Y]\to C[I_X,K_Y]\)? This is standard for inference, where we do pure tensor parallelism.
Solution

  1. Since this is a matmul over the sharded axis, we need to perform a reduction at some point. After performing the matmul, we should have \(C[I_X, K]\{U_Y\}\). Therefore, we need to do an AllReduce over \(Y\). This is then a ReduceScatter and an AllGather. For computation, each chip does the partial sum, which takes \(\frac {2IJK}{|X||Y|}\) FLOPs. For communication, the AllReduce is \(2 \times \) an AllGather. We are still sharded over \(X\), so the total bytes is \(N = \frac {2IK}{|X|}\). We do not have bi-directional because the v5e is a 2d topology and \(4 \times 4\) is not full in either axis. Thus, the communication is

    \[\frac {2\cdot N}{W_{\text {ICI}}} = \frac {4IK}{4.5e10\cdot |X|}\]

    To see where we are bound, the v5e can do \(1.97e 14\) bf16 FLOPs/s. Therefore, we are compute bound when

    \[ \begin {align*} \frac {2IJK}{|X|\cdot |Y|\cdot 1.97e 14} > \frac {4IK}{4.5e10\cdot |X|} \iff J > \frac {8 \cdot 1.97e 14}{4.5e10} .\end {align*} \]

    Thus, we are almost surely communication bound because it is determined by the contracting dimension, which is \(d_{\text {model}}\) in practice.

    Remark. No solutions available. Prayers up this right...

  2. This is Case 1 with an additional sharding over the contracting dim in \(B\). I believe this means when we do the matmul, we are gonna end up with scattered partial sums i.e. unlike in the ReduceScatter case, where we have partial sums the same dimension as \(C\), the partial sums will now be \(\frac {I}{|X|} \times \frac {K}{|Y|}\). Another ReduceScatter would cause this smaller matrix to be further divided and scattered, so it is not what we want.

    Instead, we should just perform \(\text {AllGather}_X(B[J_X, K_Y])\). Then, this will directly reduce to Case 1 and we will need no further communication. We only need to send \(N = \frac {2JK}{|Y|}\) bytes. Once again, we do not have bi-directional bandwidth. Thus, the communication is

    \[\frac {N}{W_{\text {ICI}}} = \frac {4JK}{4.5e10\cdot |Y|}\]

    The FLOPs per-device are still \(\frac {2IJK}{|X|\cdot |Y|}\). To see where we are bound, the v5e can do \(1.97e 14\) bf16 FLOPs/s. Therefore, we are compute bound when

    \[ \begin {align*} \frac {2IJK}{|X|\cdot |Y|\cdot 1.97e 14} > \frac {2JK}{4.5e10\cdot |Y|} \iff I > \frac {4 \cdot 1.97e 14}{4.5e10} .\end {align*} \]

    Thus, we have a smaller bound than the previous part but are now dependent on \(I\) instead of \(J\). This is likely in practice because \(I\) corresponds to sequence length, which can get very large.

  3. This is pure case 1 with no communication, so we instead need to worry about memory instead of communication overhead.
