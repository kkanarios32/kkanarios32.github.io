Remark. The int8 column only doubles from v5p onward — v3 and v4p run int8 through the MXU at the same rate as bf16, so quantizing there saves memory traffic but buys no extra OPs/s. The ratio of a FLOPs/s column to the HBM bandwidth column is the roofline ridge point: on v5e, \(3.94e14 / 8.2e11 \approx 480\), i.e. batch \(240\) in the \(2B\) arithmetic-intensity approximation.

Interconnect bandwidth is quoted per link, not per chip — multiply by the number of neighbors a chip has in the topology above to get its aggregate off-chip bandwidth.

Remark. The bidi column is exactly \(2 \times \) the one-way column in every row, so it carries no extra information — it only names whether you are counting both directions of the link. Which one belongs in a cost model depends on the collective: a ring all-reduce drives both directions at once, a one-directional shift does not. Note also that v3 has the highest per-link bandwidth in the table but the smallest neighbor count, since a \(32 \times 32\) pod is a 2D torus — four neighbors per chip rather than the six a 3D torus gives.

Definition 3. Vector Processing Unit [OGCRN]

  • May 22, 2026
  • Kellen Kanarios

A core component of the TPU architecture responsible for elementwise operations.

  • 2D SIMD execution, where each of 1024 sites execute same program in lockstep.
  • Each site contains 4 ALUs, enabling 4096 FLOPs.
  • Fed a 8x128 Vector Register in one cycle.

Card. The VPU is thirty times smaller than the MXU [JFWY]

  • August 10, 2026
  • Kellen Kanarios

Vector Processing Unit: what is its shape and throughput relative to the Matrix Multiply Unit (MXU), and which reductions are cheap?

Answer Shape \((8\ \text {sublanes}, 128\ \text {lanes})\), with 4 independent ALUs per position and most ops at 1/cycle: \[8 \times 128 \times 4 \times 1.75\mathrm {e}9 \approx 7\mathrm {e}12 \text { FLOPs/s}\] on v5p — about \(30\times \) less than the ~\(2e14\) MXU FLOPs/s per core. VPU work is fp32. Reductions along the sublane axis (the 8) are cheap: an intra-lane shuffle by 4/2/1 plus three pairwise adds. Cross-lane reductions need the separate XLU, which is slow and expensive. Control is skewed the other way: a single scalar core fetches and dispatches everything and can issue only one DMA request per cycle. Efficient, but it blocks data-dependent vectorization.

Definition 4. Matrix Multiply Unit (MXU) [OGCRP]

  • May 22, 2026
  • Kellen Kanarios

A core component of the TPU architecture responsible for performing matrix multiplication via a weight stationary Systolic array.

  • \(128 \times 128\) — 16,384 multiply accumulate units, each multiplying and adding in one cycle. v6e/Trillium widens the array to \(256 \times 256\), i.e. 65,536.
  • The native op is one bf16[8,128] @ bf16[128,128] -> f32[8,128] every 8 cycles, or about \(5e13\) bf16 FLOPs/s per MXU at 1.5 GHz. A v5e chip has enough MXUs to reach ~\(2e14\).
Remark. The side length is fixed in hardware, so every dimension has to be tiled down to it and any axis shorter than it is padded up to it, wasting the FLOPs spent on the padding. The order is
  1. Tiling the matrix to load from HBM to VMEM.
  2. Compiler tiles from VMEM to \(128 \times 128\) tiles to load into the MXU.

Card. Why the MXU pads everything to 128 [HPSO]

  • August 10, 2026
  • Kellen Kanarios

What is the native op of one Matrix Multiply Unit (MXU), and why does that force padding to 128?

Answer One bf16[8,128] @ bf16[128,128] -> f32[8,128] every 8 cycles, on a \(128 \times 128\) systolic array — \(256 \times 256\) on v6e/Trillium. The array's side length is fixed in hardware, so any matrix axis shorter than 128 (256 on v6e) is padded up to it, and the FLOPs spent on the padding are simply wasted. With 2–4 MXUs per core, tiling dimensions want to exceed \(128 \times \) the MXU count. Scale: roughly \(5e13\) bf16 FLOPs/s per MXU at 1.5 GHz, so about \(2e14\) per v5e chip. int8 runs ~\(2\times \) faster, int4 ~\(4\times \).
