jaxpr [G981]

  • August 7, 2026
  • Kellen Kanarios

JAX's trace-level representation: the record of what abstract execution captured when your Python ran once on tracers instead of arrays (Lifecycle of a JAX program). Print one with jax.make_jaxpr(f)(x) (Three calls, three IR levels).

Its defining feature is the square bracket. An equation reads outvars = primitive[static_params] invars, and that bracket is exactly the compile-time / runtime line (Brackets are compile-time, operands are runtime) — everything inside it is baked into this compilation, everything outside flows at run time. The same split appears in MLIR as attributes versus operands (Position separates attributes from regions).

So a jaxpr answers a different class of question from the IR below it. Why is a constant baked in, why did a cast appear (A weak type adopts the other operand's dtype), at what precision is this matmul accumulated (dimension_numbers is contracting then batch), what did my custom gradient rule actually do (A grad jaxpr is the forward program plus its transpose) — none of these survive into optimized HLO, where fusion and layout have already scrambled the correspondence. Read the jaxpr for meaning and the HLO for cost.

Not every JAX transformation appears here. jit, scan, cond, while, and shard_map are primitives with nested jaxprs; vmap is a trace-time rewrite that leaves no trace but the shapes (vmap leaves no primitive behind).

The traces below were produced with JAX 0.11 on CPU. The printed form drifts between releases — scan dropped num_consts for ft_in, and pjit now prints as jit — so read a trace from your own installation before trusting the punctuation in anyone's notes, including these.

Example.

A whole function. One dense layer, tanh(x @ w + b), traced with jax.make_jaxpr(f)(x, w, b). Four equations, in dependency order, each one a primitive (Brackets are compile-time, operands are runtime):

{ lambda ; a:f32[8,16] b:f32[16,4] c:f32[4]. let
    d:f32[8,4] = dot_general[
      dimension_numbers=(([1], [0]), ([], []))
      preferred_element_type=float32
    ] a b
    e:f32[1,4] = broadcast_in_dim[broadcast_dimensions=(1,)] c
    f:f32[8,4] = add d e
    g:f32[8,4] = tanh f
  in (g,) }

Nothing before the semicolon, so nothing was captured (constvars before the semicolon, invars after). Note what the source did not say: the broadcast of the bias is explicit, and so is the accumulation type on the matmul (dimension_numbers is contracting then batch). Following this same function down to StableHLO and HLO is worth doing once.

Example.

A closure. The same trace with w captured from the enclosing scope instead of passed in:

{ lambda a:f32[8,4]; b:f32[8]. let
    c:f32[] = reduce_sum[axes=(0, 1) out_sharding=None] a
    d:f32[8] = mul b c
  in (d,) }

a is now a constvar, left of the semicolon — baked into this compilation rather than supplied by the caller. A large array on that side of the semicolon is a closure you probably did not mean to make (constvars before the semicolon, invars after).

Example.

grad. jax.make_jaxpr(jax.grad(f))(x, w) for f = tanh(x @ w).sum() — the forward pass, then its transpose in reverse order (A grad jaxpr is the forward program plus its transpose):

{ lambda ; a:f32[8] b:f32[8,4]. let
    c:f32[4] = dot_general[dimension_numbers=(([0], [0]), ([], []))
                           preferred_element_type=float32] a b
    d:f32[4] = tanh c
    e:f32[4] = sub 1.0:f32[] d
    _:f32[] = reduce_sum[axes=(0,) out_sharding=None] d
    f:f32[4] = broadcast_in_dim 1.0:f32[]
    g:f32[4] = mul f e
    h:f32[4] = mul g d
    i:f32[4] = add_any g h
    j:f32[8] = dot_general[dimension_numbers=(([0], [1]), ([], []))
                           preferred_element_type=float32] i b
  in (j,) }

Three things to read off it. The final dot_general contracts [0] against [1] where the forward one contracted [0] against [0] — that swap is the transpose rule for a matmul. The sub 1.0 d is \(1 - \tanh ^2\) being built from the saved output rather than recomputed. And the reduce_sum is a dropvar (An underscore is an output nobody consumes): the primal value the sum would have produced is not needed, only its gradient, and the cotangent broadcast_in_dim 1.0 is what replaces it.

Example.

vmap leaves nothing behind (vmap leaves no primitive behind). Mapping lambda a, b: a * b over the leading axis of a only:

{ lambda ; a:f32[3,4] b:f32[4]. let
    c:f32[1,4] = broadcast_in_dim[broadcast_dimensions=(1,)] b
    d:f32[3,4] = mul a c
  in (d,) }

There is no vmap equation — only a mul whose avals grew a dimension, plus the broadcast_in_dim that lifted the unmapped argument to match. When vmap can push the batch dimension into an existing primitive it emits nothing at all: jax.vmap(jnp.dot, in_axes=(0, None)) over f32[3,4] and f32[4,2] is a single dot_general, because a batched matvec is a matmul.

Example.

scan (consts, then carry, then xs). Two carries, one scanned input, one const closed over:

{ lambda ; a:f32[] b:f32[] c:f32[4]. let
    d:f32[] e:f32[] f:f32[4] = scan[
      ft_in=((), (None, None), (None,))
      jaxpr={ lambda ; g:f32[] h:f32[] i:f32[]. let
          j:f32[] = mul g 3.0:f32[]
          k:f32[] = add j i
          l:f32[] = add h g
          m:f32[] = mul g 2.0:f32[]
        in (k, l, m) }
      length=4  reverse=False  unroll=1
    ] a b c
  in (d, e, f) }

Read ft_in first: no consts, two carries, one xs. So invars a and b are the carry and c is scanned, and the body returns two new carries then one ys element, which stacks to f32[4]. The captured 3.0 was constant-folded into the body rather than passed as a const.

Example.

cond (The nconsts numbers locate the carry). Note that the predicate is converted to an integer index, and that branch 0 is the false branch:

{ lambda ; a:bool[] b:f32[] c:f32[]. let
    d:i32[] = convert_element_type[new_dtype=int32 weak_type=False] a
    e:f32[] = cond[
      branches=(
        { lambda ; f:f32[] g:f32[]. let h:f32[] = sub f g in (h,) }
        { lambda ; i:f32[] j:f32[]. let k:f32[] = add i j in (k,) }
      )
    ] d b c
  in (e,) }

Both branches take the same operands and return the same type — cond is an \(n\)-way switch on an index, and the two-branch boolean case is the special case.

Example.

Weak types (A weak type adopts the other operand's dtype). A Python literal against a bf16 array:

{ lambda ; a:bf16[3]. let b:bf16[3] = mul a 2.0:bf16[] in (b,) }

The literal adopted bf16 and nothing was promoted. Replace 2.0 with np.float32(2.0) — an explicitly typed scalar, so no longer weak — and the same line becomes:

{ lambda ; a:bf16[3]. let
    b:f32[3] = convert_element_type[new_dtype=float32 weak_type=False] a
    c:f32[3] = mul b 2.0:f32[]
  in (c,) }

The whole array was widened to f32 by one scalar. This is the promotion bug the weak-type rule exists to prevent, and the convert_element_type equation is how you catch it.

Example.

shard_map and pmap (Collectives are primitives parameterised by axis name). A psum over a mesh axis of 8:

{ lambda ; a:f32[8]. let
    b:f32[1] = shard_map[
      in_specs=(P('x',),)  out_specs=(P(),)  check_vma=True
      mesh=Mesh('x': 8, axis_types=(Auto,))
      jaxpr={ lambda ; c:f32[1]{V:x}. let
          d:f32[1] = psum_invariant[axes=('x',)] c
        in (d,) }
    ] a
  in (b,) }

The global shape is f32[8] and the body's is f32[1] — inside the region you are writing per-device code, which is the whole point of shard_map. pmap is not a separate mechanism: it traces to a jit wrapping a shard_map, with a squeeze and a broadcast_in_dim around the body to move between the mapped axis and the per-device rank.

Card. constvars before the semicolon, invars after [2KEW]

  • August 22, 2026
  • Kellen Kanarios

Name every part of { lambda a:f32[8] ; b:f32[8] c:f32[8]. let d:f32[8] = mul b c; e:f32[8] = add d a in (e,) }

Answer 
{ lambda <constvars> ; <invars>. let <equations> in (<outvars>) }
  • Before the semicolon: constvars. Values closed over — captured arrays — supplied by the ClosedJaxpr's consts rather than by the caller.
  • Between semicolon and dot: invars. The traced arguments.
  • The let block: equations in dependency order (Brackets are compile-time, operands are runtime).
  • in (...): the output tuple, always parenthesised even for a single value.
The constvar / invar split is where a performance surprise hides. Anything on the left of the semicolon was captured at trace time and is baked into this compilation, so changing it means retracing (XLA Compilation). Large constvars in a jaxpr you expected to be pure are a closure you did not mean to make.

Card. Brackets are compile-time, operands are runtime [VTPS]

  • August 22, 2026
  • Kellen Kanarios

What is the shape of a single jaxpr equation?

Answer 
outvars = primitive[static_params] invars
for example 
e:f32[1,4] = broadcast_in_dim[broadcast_dimensions=(1,)] c
d:f32[8,4] = dot_general[dimension_numbers=(([1], [0]), ([], []))
                         preferred_element_type=float32] a b
The square brackets hold static parameters — known at trace time and baked into the primitive — and everything after them is a traced operand or a literal. The printer shows only the interesting ones; the equation carries more (broadcast_in_dim also holds shape and sharding), reachable from eqn.params. That bracket-versus-operand split is the most useful thing on the page. A quantity inside the brackets is a constant this compilation is specialised to; move it out and you retrace. It is the same distinction MLIR draws between attributes and operands (Position separates attributes from regions).

Card. An aval is shape and dtype, no value [9M15]

  • August 22, 2026
  • Kellen Kanarios

Read the jaxpr shorthand f32[8,128], i32[], bool[3], key<fry>[2], bf16[8]

Answer Compact aval — abstract value — printing: dtype then shape, with empty brackets for a scalar. key<fry>[2] is a typed PRNG key array using the threefry implementation: the new-style key dtype rather than a raw uint32[2]. Seeing the typed form tells you the key is opaque to shape-manipulating code, which is the point of it. The aval is what tracing actually propagates: shape, dtype, and Sharding — no values. Everything a jaxpr knows, it knows from these, which is why a Python if on a traced value fails and why the shapes in a jaxpr are always fully static. HLO's shapes are the same information in a different notation (Tuples are first-class in HLO), and MLIR adds dynamic dimensions that JAX never produces (Question mark is a dynamic dimension, star is unknown rank).

Card. An underscore is an output nobody consumes [E9J1]

  • August 22, 2026
  • Kellen Kanarios

What is _:f32[8] on the left of a jaxpr equation?

Answer A dropvar: an output that nothing consumes. It shows up for multi-output primitives where only some results are used — a custom_vjp's residuals when you asked only for the primal, an unused scan carry (consts, then carry, then xs), the second output of a primitive whose first is all you wanted. It does not mean the work happens. Dead code elimination may or may not have run when you print a jaxpr, so dropvars are entirely normal in a freshly traced one, and their presence says nothing about the compiled program. XLA will drop the computation if it is genuinely unused. What they do tell you is which primitive produced more than you asked for — useful when you are trying to work out where a residual came from (A grad jaxpr is the forward program plus its transpose).

Card. jit is the pjit primitive [WNHA]

  • August 22, 2026
  • Kellen Kanarios

Why does almost every jaxpr from a jitted function contain a single jit[name=f jaxpr={...}] equation?

Answer Because jax.jit is implemented as a primitive — pjit_p, printed as jit — rather than being inlined. The callee's jaxpr is nested inside as a static parameter, so each jit boundary in your code becomes another level of nesting. That nesting is preserved all the way down. It reappears in HLO as the slash-separated op_name path, jit(f)/jit(g)/... (op_name is the trace path back to Python), which is what lets you attribute an optimized HLO instruction to a particular function in a program full of them. It also means the boundaries are real to the compiler, not just to you: each is a place where donation, Sharding, and compilation caching are decided (XLA Compilation). Nesting jit inside jit is free at run time but is not invisible in the IR.

Card. consts, then carry, then xs [W8NM]

  • August 22, 2026
  • Kellen Kanarios

Read scan[ft_in=((), (None, None), (None,)) length=4 reverse=False unroll=1]. How are the invars laid out?

Answer In one fixed order: first the loop-invariant consts, then the carry, then the xs, each scanned along a leading axis of size length. The inner jaxpr's invars follow the same convention, and it returns (new_carry..., ys...). ft_in is where the split is written down. It is a three-tuple — one group per role — so the group lengths give the counts: none here, then two carries, then one scanned input. Older JAX printed the same information as num_consts and num_carry, and you will still see that form in written material. Counting is the only way to read a scan body. The names carry nothing; the group sizes do. Given ((), (None, None), (None,)), invars 0 and 1 are the carry and invar 2 is scanned. The same explicit carry appears as iter_args in scf.for (iter_args and yield are the mutable accumulator) and as a state tuple in HLO's while (A while loop's whole state is one tuple), where the three-way split is flattened into tuple indices you have to recover by counting.

Card. The nconsts numbers locate the carry [2LKO]

  • August 22, 2026
  • Kellen Kanarios

How do cond and while print in a jaxpr?

Answer 
cond[branches=(...)] index a b
while[cond_jaxpr={...} cond_nconsts=1 body_jaxpr={...} body_nconsts=2] ...
For cond, the first invar is the branch index and the rest are the operands passed to every branch. branches is a tuple of jaxprs, all with the same signature — which is why both sides of a JAX conditional must agree on shapes and dtypes. For while, the invars run: cond consts, then body consts, then the carry. The nconsts numbers are the only thing telling you where the carry starts. There is no punctuation in the operand list and the names are meaningless, so you count: skip cond_nconsts, skip body_nconsts, and everything left is the loop state. Same discipline as scan (consts, then carry, then xs).

Card. Collectives are primitives parameterised by axis name [KWVD]

  • August 22, 2026
  • Kellen Kanarios

What do psum[axes=('x',) axis_index_groups=None] and shard_map look like in a jaxpr?

Answer Collectives are ordinary primitives parameterised by an axis name; they only mean anything inside a mapped context that binds that name. shard_map appears as 
shard_map[jaxpr={...} mesh=Mesh('x': 8, axis_types=(Auto,))
          in_specs=(P('x',),) out_specs=(P(),) check_vma=True]
with the per-device program nested inside (vmap leaves no primitive behind). Inside that body a collective whose result is already replicated may print as psum_invariant rather than psum — same reduction, tagged as producing an axis-invariant value. So the jaxpr level is logical and the physical level is elsewhere. Here you see a named axis and per-device shapes; the device assignment appears only later, as HLO sharding attributes (A sharding annotation is a tiling plus a device order) and concrete all-reduce instructions (replica_groups says who reduces with whom). That separation is why the axis name is the right thing to reason about: it is stable, whereas which devices land in which replica_groups depends on the mesh and the compiler (Sharding).

Card. dimension_numbers is contracting then batch [CCL2]

  • August 22, 2026
  • Kellen Kanarios

Read dot_general[dimension_numbers=(((1,), (0,)), ((), ())) precision=None preferred_element_type=float32]

Answer dimension_numbers is ((lhs_contracting, rhs_contracting), (lhs_batch, rhs_batch)) — contracting pair first, batch pair second. Here lhs dim 1 contracts with rhs dim 0 and there are no batch dims: a plain matmul (Batch, contract, free, and the output order is fixed, A dot's output order is batch, lhs free, rhs free). The two other parameters are where numerics live, and they are easy to skim past.
  • preferred_element_type is the accumulation type. bf16 inputs accumulating into f32 is the standard configuration, and it is what makes low-precision training work at all — the inputs are cheap, the running sum is not.
  • precision controls the backend tradeoff: TF32, bf16x3 passes, or full f32.
So a jaxpr answers "at what precision is this matmul actually done" directly, which the HLO line does not.

Card. A weak type adopts the other operand's dtype [WMKA]

  • August 22, 2026
  • Kellen Kanarios

What does convert_element_type[new_dtype=float32 weak_type=False] mean, and what is a weak type?

Answer An explicit cast that tracing inserted. weak_type marks a value whose dtype came from a Python scalar — 3.0, 2 — rather than from an explicitly typed array. A weakly typed value adopts the other operand's dtype in promotion instead of forcing a widening, so x * 2.0 on a bf16 array stays bf16 rather than becoming f32. That rule exists precisely so writing a literal in your model does not silently change its precision. An unexpected convert_element_type in a jaxpr is therefore worth reading as a diagnosis, not as noise: it is the trace of a promotion you did not intend, usually a NumPy scalar or an f32 constant meeting a lower-precision array. It costs a full pass over the data, and it can defeat the accumulation choice you made on the neighbouring dot_general (dimension_numbers is contracting then batch).

Card. vmap leaves no primitive behind [ROHH]

  • August 22, 2026
  • Kellen Kanarios

Does vmap appear as a primitive in a jaxpr?

Answer No. Batching is a trace-time rewrite, not a wrapper. The jaxpr you get back has no vmap equation at all — just the same primitives with a batch dimension added to their avals (An aval is shape and dtype, no value), plus extra broadcast_in_dim and transpose equations wherever the batch axis had to be moved. So to see what vmap decided, read the shapes; there is no op to look for. Those stray transposes are the mapping decisions, and they are also where a vmapped function quietly costs more than the loop you replaced. Contrast the ones that do appear as primitives with nested jaxprs: pjit (jit is the pjit primitive), scan (consts, then carry, then xs), cond and while (The nconsts numbers locate the carry), custom_jvp_call, and shard_map (Collectives are primitives parameterised by axis name). The distinction is whether the transformation changes the program structure or only the shapes flowing through it.

Card. A grad jaxpr is the forward program plus its transpose [MO87]

  • August 22, 2026
  • Kellen Kanarios

What tells you a jaxpr came from grad?

Answer The layout: the forward equations appear first, then their transposes in reverse order, with residual values threaded between them. Concrete tells — mul and dot_general with swapped dimension_numbers (dimension_numbers is contracting then batch), transpose equations, and custom_vjp_call_jaxpr or remat wrappers. Dropvars (An underscore is an output nobody consumes) mark residuals that this particular jaxpr does not consume. jax.make_jaxpr(jax.grad(f))(x) gives the whole forward-plus-backward program as one jaxpr, and that is the cheapest way to see what a custom rule actually did — far cheaper than reasoning about what it should have done. It is also where you can see, directly, which intermediates the backward pass keeps alive, which is the memory question remat exists to answer. In HLO the same structure is visible through the jvp and transpose scopes in op_name (op_name is the trace path back to Python).
