Card. A custom call is a black box XLA cannot fuse across [2MM7]

  • August 22, 2026
  • Kellen Kanarios

Read custom-call(%a, %b), custom_call_target="tpu_custom_call", operand_layout_constraints={...}, backend_config="...", api_version=API_VERSION_STATUS_RETURNING

Answer The escape hatch to code XLA does not generate: library kernels (cuBLAS, cuDNN), Pallas and Mosaic or Triton kernels (A Pallas kernel is an opaque custom call), host callbacks.
  • custom_call_target selects the registered handler by name.
  • backend_config carries the opaque payload — a serialised Mosaic module, a tuning configuration, an algorithm choice.
  • operand_layout_constraints pins the layouts the handler requires (The layout is minor-to-major).
Everything expensive about a custom call follows from XLA not being able to see inside it. It cannot fuse across the boundary, so the operands are materialised to High bandwidth memory and the results read back; it must assume the declared effects, so it cannot reorder freely; and the pinned layouts can force copy ops on both sides (bitcast is free, copy is not). A hand-written kernel has to beat all of that, not just the kernel XLA would have emitted.
