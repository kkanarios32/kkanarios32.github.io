Definition. KV-cache [TJLA]

  • July 14, 2025
  • Kellen Kanarios

The keys and values of every token seen so far, held in memory across decoding steps so that each is projected once rather than once per step. Attention at step \(t\) needs \(k_j\) and \(v_j\) for every \(j \le t\), and each of those is a function of token \(j\) and the weights alone — nothing about it depends on \(t\). So it is computable once and never again, and the only real question is whether you will spend memory to avoid recomputing it.

The cost of not spending it is quadratic, which is easy to miss because per step it looks merely linear: admitting token \(t\) means rebuilding \(t+1\) key–value pairs, so a sequence of \(S\) tokens costs \(\sum _{t=1}^{S} t = S(S+1)/2\) projections rather than \(S\). The query is the asymmetry that makes the trade available at all — only the newest position needs one, so \(q_t\) is a single row either way, and decoding is a matrix–vector product against a \(K\) and \(V\) that grow by one row a step.

Notation. Following the scaling book: \(S\) is the KV sequence length, \(K\) the number of key/value heads, \(H\) the head dimension, \(L\) the layers, \(B\) the batch. The clash between \(K\) as a matrix and \(K\) as a head count is unfortunate and universal.

What the cache costs is memory, and the shape of that cost is the reason it governs inference planning. Each token contributes a key and a value in every layer, so a batch holds

\[2 \cdot B \cdot S \cdot L \cdot K \cdot H \cdot \mathrm {bytes}\]

which is linear in the sequence length and — unlike the weights — per sequence, so it cannot be amortised over the batch. Context length and batch size are therefore drawn from the same High bandwidth memory budget, and past a certain context the cache dominates residency outright, which is Processing in Memory for ML's framing of the memory wall.

It also decides what decoding is bound by. At step \(t\) the model streams the entire cache through the Matrix Multiply Unit (MXU) to do \(O(S)\) multiply-accumulates against a single query row, so the Arithmetic intensity is roughly one FLOP per byte read — far below the ridge point of any accelerator, and flat in \(S\). Decoding is bandwidth-bound, and the cache is what it is bound by.

Every fix for that attacks a factor in the expression above rather than the idea of caching. MQA sets \(K = 1\) and shares one key/value head across all query heads; Group Query Attention sets it to a group count and interpolates; Sliding Window Attention bounds \(S\) instead by refusing to attend past a window. The FLOPs are unchanged in all three — what changes is how many bytes have to move to supply them.

Card. The KV cache scales with K, and is per-sequence [J65M]

  • August 18, 2026
  • Kellen Kanarios

How large is a KV-cache, and which dimension actually drives it?

Answer The cache has shape \([2, S, L, K, H]\) per sequence — the leading 2 is keys and values — so in int8 it is \(2SLKH\) bytes. Worked: \(S = 8\mathrm {k}\), \(L = 64\), \(KH = D = 8192\) gives \(2 \cdot 8192 \cdot 64 \cdot 8192 \approx 8\) GiB for a single sequence. Two things in that expression decide inference planning. It scales with \(K\), the number of key/value heads, and not with the \(N\) query heads — which is the whole argument for Group Query Attention and MQA at \(K \ll N\). And it is per sequence, so unlike the weights it cannot be amortised over the batch: it competes with batch size for the same High bandwidth memory budget, and generation is bandwidth-bound on streaming it.
