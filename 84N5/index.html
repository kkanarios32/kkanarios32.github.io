StableHLO [84N5]

  • August 22, 2026
  • Kellen Kanarios

The MLIR dialect JAX lowers to and XLA ingests — the versioned, portable contract between frameworks and compilers (Lifecycle of a JAX program). Print it with jax.jit(f).lower(x).as_text() (Three calls, three IR levels).

The word doing the work in the name is stable. It is one of three HLO-family dialects and the only one with compatibility guarantees: chlo above it is sugar that gets decomposed, mhlo below it is XLA's unstable internal dialect (chlo desugars, stablehlo is stable, mhlo is internal). A serialised StableHLO program is expected to keep deserialising across compiler versions, which is what makes it a sensible artifact to ship, cache, or hand to a different backend.

Read it to answer one specific question: what did JAX actually ask for? It sits at the boundary where a JAX bug becomes an XLA bug. Above it the shapes are still recognisably yours; below it, in optimized HLO, fusion and layout assignment have rewritten the program past easy comparison (Only after_optimizations matches the profile).

A hand-written kernel — Pallas or Triton — appears here as an opaque custom_call whose body is serialised into an attribute (A Pallas kernel is an opaque custom call), which is the first place you can see that XLA has been handed something it cannot look inside.

Example.

The same function one level down. tanh(x @ w + b), lowered with jax.jit(f).lower(x, w, b).as_text(). Compare it against the jaxpr of the same function:

module @jit_f attributes {mhlo.num_partitions = 1 : i32, mhlo.num_replicas = 1 : i32} {
  func.func public @main(%arg0: tensor<8x16xf32>, %arg1: tensor<16x4xf32>,
                         %arg2: tensor<4xf32>)
      -> (tensor<8x4xf32> {jax.result_info = "result"}) {
    %0 = stablehlo.dot_general %arg0, %arg1, contracting_dims = [1] x [0],
         precision = [DEFAULT, DEFAULT] : (tensor<8x16xf32>, tensor<16x4xf32>) -> tensor<8x4xf32>
    %1 = stablehlo.broadcast_in_dim %arg2, dims = [1] : (tensor<4xf32>) -> tensor<1x4xf32>
    %2 = stablehlo.broadcast_in_dim %1, dims = [0, 1] : (tensor<1x4xf32>) -> tensor<8x4xf32>
    %3 = stablehlo.add %0, %2 : tensor<8x4xf32>
    %4 = stablehlo.tanh %3 : tensor<8x4xf32>
    return %4 : tensor<8x4xf32>
  }
}

Four things are worth noticing, and each is a card.

  • It is ordinary MLIR: a builtin.module with attributes (Every dump is wrapped in a module), a func.func whose result carries an attribute JAX put there (Three attribute positions on a function), and pretty-printed ops (The pretty form is optional, the generic form always works).
  • The dot_general uses the sugar form contracting_dims = [1] x [0] rather than the #stablehlo.dot<> attribute (Batch, contract, free, and the output order is fixed) — same information, shorter.
  • The bias broadcast became two ops. dims = [1] maps the operand's single dimension to output dim 1, giving 1x4; a second broadcast_in_dim then stretches the size-1 dimension to 8 (broadcast_in_dim maps operand dims onto output dims). One jaxpr equation, two StableHLO ops.
  • No layouts anywhere. Those are assigned later, inside XLA (The layout is minor-to-major).

Card. chlo desugars, stablehlo is stable, mhlo is internal [FLKN]

  • August 22, 2026
  • Kellen Kanarios

In a JAX/XLA dump, what are the chlo, stablehlo, and mhlo dialects, and how do they relate?

Answer
  • chlo — "client" HLO: higher-level sugar that gets decomposed. Implicitly broadcasting binary ops, erf, top-k style helpers.
  • stablehlo — the stable, versioned, portable IR (StableHLO). This is what JAX emits and serialises today, and the compatibility boundary between frameworks and compilers.
  • mhlo — "meta" HLO: XLA's internal, unstable dialect, what stablehlo is converted into before XLA's own HLO proto (HLO).
The pipeline, in full (Lifecycle of a JAX program): 
Python -> jaxpr -> chlo/stablehlo -> mhlo -> HLO -> optimized HLO -> backend (LLVM/PTX, Mosaic/LLO)
Only one of the three is a contract. stablehlo has version guarantees so a serialised program keeps deserialising; chlo and mhlo are implementation details you may read but must not depend on.

Card. broadcast_in_dim maps operand dims onto output dims [5LSA]

  • August 22, 2026
  • Kellen Kanarios

Read %0 = stablehlo.broadcast_in_dim %a, dims = [1] : (tensor<3xf32>) -> tensor<2x3xf32>

Answer dims maps each operand dimension to the output dimension it lands in. Here operand dim 0 (size 3) becomes output dim 1. Every output dimension not listed is a new broadcast dimension, and a listed dimension of size 1 may be stretched. Two invariants make the attribute self-checking: the list length always equals the operand rank, and the values must be strictly increasing — so a broadcast can add and stretch dimensions but never permute them. A permutation needs a separate transpose (transpose dimensions read output from operand). This is one of two dimension-list conventions and they read in opposite directions. Broadcast lists a target per operand dim; transpose lists a source per output dim. HLO's broadcast uses this same convention (broadcast dimensions read operand to output).

Card. Batch, contract, free, and the output order is fixed [BVPY]

  • August 22, 2026
  • Kellen Kanarios

How do you read a dot_general's dimension numbers? #stablehlo.dot<lhs_batching_dimensions = [0], rhs_batching_dimensions = [0], lhs_contracting_dimensions = [2], rhs_contracting_dimensions = [1]>

Answer Every dimension is one of three kinds:
  1. Batching — matched pairwise between lhs and rhs, and kept. These are independent problems solved side by side.
  2. Contracting — matched pairwise and summed away. This is the reduction.
  3. Free — everything else, and it survives into the output.
The output order is fixed, not chosen: batch dimensions, then lhs free dimensions in order, then rhs free dimensions in order. So the result shape is fully determined by the attribute and you never have to guess. Newer printers use the sugar contracting_dims = [2] x [1]. The same three-way split appears at every level — as dimension_numbers in a jaxpr (dimension_numbers is contracting then batch) and as lhs_batch_dims and friends in HLO (A dot's output order is batch, lhs free, rhs free) — which is what makes a matmul traceable straight down the stack.

Card. reduce takes a computation, not an enum [KLBR]

  • August 22, 2026
  • Kellen Kanarios

Why does a stablehlo.reduce body look like a region? %r = stablehlo.reduce(%a init: %zero) applies stablehlo.add across dimensions = [1]

Answer Because reduce takes a reducer computation — a region (A region is nesting, not a flat CFG) taking two scalars and yielding one — rather than an enum of built-in reductions. Any associative operation can therefore be expressed, including ones the dialect never enumerated. The form above is sugar for the common case; the general form spells the region out with a stablehlo.return. dimensions lists the dims removed from the operand shape. The init value is not decoration — it is the identity of the reducer, and it is also what a zero-sized reduction returns. Getting it wrong (0 for a max, say) produces a reduction that is right on non-empty input and silently wrong at the edge. HLO's reduce is the same design with to_apply naming the computation (reduce removes the dims it lists).

Card. A Pallas kernel is an opaque custom call [QRDW]

  • August 22, 2026
  • Kellen Kanarios

How does a Pallas or Triton kernel appear in a StableHLO dump?

Answer As an opaque custom call (XLA custom call): 
stablehlo.custom_call @tpu_custom_call(%a, %b) {backend_config = "...", api_version = 2 : i32}
  : (tensor<8x128xf32>, ...) -> tensor<8x128xf32>
On GPU the target is @triton_kernel_call instead. The kernel body is not in this IR. It is serialised inside backend_config — a Mosaic module, or Triton IR (The prefix says which side of layout assignment) — and XLA treats the whole thing as a black box with declared operands, results, and effects. That is the trade you accept when you write a kernel by hand: you get control of the inner loop, and you give up every cross-op optimisation at the boundary, because the compiler cannot fuse across something it cannot see (A custom call is a black box XLA cannot fuse across).
