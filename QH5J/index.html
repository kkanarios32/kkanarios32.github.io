POTW: 🎂 CAKE: Compiler-Agent Co-Design for Frontier Kernel Evolution [QH5J]

  • August 19, 2026
  • Kellen Kanarios

1. TLDR

  • August 19, 2026
  • Kellen Kanarios

Problem. In this paper, they aim to address the problem of agentic kernel generation or as we refer to it: vibe compilation. Specifically, they target CUDA and raw PTX as a backend.

Technical challenges. There are many issues that arise in vibe compilation. A non-exhaustive list of challenges is as follows:

  • Reward Hacking: A very common theme for any reinforcement learning based approach. In particular, see this paper for some examples of agents hacking KernelBench.
  • Synchronization errors: Even given a list of input output examples to check against, we cannot possibly determine whether there is an underlying race condition that appears rarely enough to pass the checks.
    • This seems to be a main focus of things like TIRx, where they hope to check these things at the IR level.

2. Contributions

  • August 19, 2026
  • Kellen Kanarios

Core contribution. They develop CAKE IR, which is an intermediate representation for writing CUDA kernels. More importantly, they have the agent co-design the IR while trying to generate kernels. This is an iterative process, where the agent must implement existing kernels in its own designed IR. To do so, requires adding necessary features to the IR like Warp Specialization along with the corresponding lowering passes.

They can then iteratively build on this pipeline adding architecture specific features. For example, the IR example they give shows that they have an lm.tmem API for TMEM. This can be thought of as a v3 given below.

How this is actually implemented is a trade secretI suspect one reason that a lot of this is not publicly available is that it is only understood by GPT 5.6.

Evaluation. They evaluate against (their own) well-tuned kernels from FlashInfer.

3. Limitations

  • August 19, 2026
  • Kellen Kanarios

Assumptions.

Where they might struggle. It is unclear how well this would work for ASICs like TPUs or Trainium. I suspect that in order to "converge" to a good IR, you need to reduce the degrees of freedom through a large number of kernel examples. The kernel ecosystem of these accelerators is far less mature, making it much harder to extract useful abstractions.

I believe the layering analogy was meant as adding increasingly specific features, but I wonder whether a vibe MLIR could be developed to allow other accelerators to inherit some of the benefits.

4. Outstanding Questions

  • August 19, 2026
  • Kellen Kanarios

Most of the work in this paper is not publicly available, so I have a lot of outstanding questions.

Question. What are the exact input / outputs in IR developement and during search?

For the IR, they have "IR principles"

  1. Program safety
  2. Hardware conformance
  3. Data consistency
  4. Schedule semantics
  5. Numerical validation
  6. Performance analysis
  7. Optimization guidance

My best guess is that the workflow is roughly 1. prepend these principles to the input via some prompt 2. provide new kernel(s) that likely require some new abstraction and 3. have GPT vibe code IR updates.
