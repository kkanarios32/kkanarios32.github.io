Collectives summary [41OF]

  • August 14, 2026
  • Kellen Kanarios

The four collectives that sharded matmuls actually need, in the [scaling-book] notation: a subscript is a mesh axis the array is split along, and \(\{U_X\}\) marks an array that is unreduced along \(X\) — every device holds a full-size partial sum. A collective is then a rewrite of that decoration, and its cost is a function of how many bytes have to cross the ICI to do it.

Operation Description Syntax Runtime
AllGather Gathers all the shards of a sharded array along an axis, removing a subscript. \([A_X, B] \to [A, B]\) \(\text {bytes} / (W_{\mathrm {ici}}^{\text {bidi}} \cdot \text {num\_axes})\)
ReduceScatter Sums a partially summed array along an axis and shards it along another axis, adding a subscript. \([A, B]\{U_X\} \to [A_X, B]\) Same as AllGather
AllReduce Sums a partially summed array along an axis, removing the \(\{U_X\}\). Combines an AllGather and a ReduceScatter. \([A_X, B]\{U_Y\} \to [A_X, B]\) \(2 \times \) AllGather
AllToAll Gathers (replicates) an axis and shards a different dimension along the same axis. \([A, B_X] \to [A_X, B]\) AllGather / 4 for a bidirectional ring

Only two of these are primitives. An AllReduce is a ReduceScatter followed by an AllGather, which is exactly why it costs twice as much, and the practical consequence is that you should stop at the ReduceScatter whenever the consumer can accept a sharded input. AllGather and ReduceScatter are transposes of each other and hence each other's derivative, so a forward-pass AllGather implies a ReduceScatter on the reverse-mode gradients.

Remark. The runtime column is written relative to the AllGather because every entry is the same ring pass over the same \(V\) bytes — the only thing that changes is how far each byte travels. An AllToAll is \(4\times \) cheaper because a shard's destination is on average a quarter of the ring away rather than all the way around, and no byte is broadcast to every device [scaling-book, Ex 3.10]. The \(\text {num\_axes}\) factor in the AllGather row is the trick from [scaling-book, Ex 3.2]: gathering over two mesh axes at once buys you both axes' bandwidth.
Remark. Notice what is absent from the runtime column: the number of devices. A ring collective moves \(V\) bytes off each chip regardless of how big the ring is, so cost depends on the array and the link, not the mesh size, which is what makes these affordable at pod scale and why the roofline question is comms-vs-FLOPs rather than comms-vs-devices.
