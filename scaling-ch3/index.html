Exercise Pop Quiz. 2D sharding across 1 axis

  • August 5, 2026
  • Kellen Kanarios
 Consider an array fp32[1024, 4096] with sharding \(A[I_{XY},J]\) and mesh {'X': 8, 'Y': 2}. How much data is held by each device? How much time would it take to load this array from HBM on H100s (assuming 3.4e12 memory bandwidth per chip)?
Solution

The notation indicates that we are sharding the first axis \((1024)\) across both \(x\) and \(y\)? This means we are dividing into fp32[64, 4096] chunks or \(4\cdot 64\cdot 4096\) bytes per device, which would then take

\[\frac {4\cdot 64\cdot 4096}{3.4e12} = .308 \mu s\]

Since there is no sharding across the Z axis. I assume this means it is replicated. This still gives \(8\cdot 2048\) bytes per device but now total memory is still multiplied by \(32\) giving \(32\cdot 8\cdot 2048\) bytes across all devices.

Exercise Pop Quiz. AllGather

  • August 5, 2026
  • Kellen Kanarios
 How long does it take to perform the AllGatherY([EY, F]) → [E, F] on a TPU v5e with a 2D mesh {'X': 8, 'Y': 4}, for \(E = 2048\), \(F = 8192\) in bf16? What about for \(E = F = 256\)?
Solution

For the large \(E\) and \(F\), we will clearly not be latency bound, so we can just perform the ICI cost. We will have \(N = 2\cdot 2048\cdot 8192\) bytes and the TPU v5e uni-directional bandwidth is \(4.5e 10\). Since we are only gathering over \(1\) dimension, we do not get any additional bandwidth. Thus, it will take \(\frac {N}{4.5e10} = 3.72\text {ms}\).

For the small \(E\) and \(F\), we now need to consider the latency time given by

\[T_{\text {latency}} = \frac {|Y|\cdot T_{\min }}{2} = 2\mu s.\]

Computing the ICI cost, we have \(N = 2\cdot 256\cdot 256\) bytes and \(T_{\text {ICI}} = \frac {N}{4.5e 10} = 0.73 \mu s\). Thus, the total time is \(T = \max \{T_{\text {latency}}, T_{\text {ICI}} = 2\mu s\).

Remark. I divided the latency time by \(2\), when once again the TPU v5e sub-mesh does not support wrap-around links and therefore the hop count is NOT upperbounded by \(|Y|\). Also the hop count is actually \(|Y| - 1\) not \(|Y|\), so the correct answer was just \(T_{\text {min}}\cdot (|Y| - 1) = 3\mu s\).

Exercise 3.1. replicated sharding

  • August 5, 2026
  • Kellen Kanarios
 An array is sharded \(A[I_X,J,K,…]\) (i.e., only sharded across \(X\) ), with a mesh Mesh({'X': 4, 'Y': 8, 'Z': 2}). What is the ratio of the total number of bytes taken up by \(A\) across all chips to the size of one copy of the array?
Solution It is sharded across \(X\), so that on each chip there is only \(1/4\) of \(A\). However, it must be replicated across \(Y\) and \(Z\) which are \(8\cdot 2 = 16\) copies. This leaves us with \(16 \times \) the total number of bytes across all copies.

Exercise 3.2. AllGather latency

  • August 5, 2026
  • Kellen Kanarios
 How long should \(\text {AllGather}_{X}([B_X,D_Y])\) take on a TPU v4p 4x4x4 slice with mesh Mesh({'X': 4, 'Y': 4, 'Z': 4}) if \(B=1024\) and \(D=4096\) in bfloat16? How about \(\text {AllGather}_{XY}([B_X,D_Y])\) How about \(\text {AllReduce}_{Z}([B_X,D_Y]\{U_Z\})\)?
Solution

  1. We cannot use bi-directional because we are on a non-16 dim axes on TPU v4p. Therefore, the ICI bandwidth is \(W_{\text {ICI}} = 4.5e10\). From AllGather, we know that the communication time is independent of \(|X|\) and is \(\frac {N}{W_{\text {ICI}}}\). For this problem, we have \(N = 1024\cdot 4096\cdot 2\). Thus, it will take \(.186\text {ms}\).

    Remark. I do not understand wrap-around rules at allor maybe they are just highly unintuitive, but we actually do have bi-directional bandwidth. I also needed to take into consideration that \(|X|\) cancels out but we only have \(N/|Y|\) bytes. Correct answer is \[\frac {1024\cdot 4096\cdot 2}{9e10\cdot |Y|}\]

  2. In this case, we now have double the bandwidth because we are reducing across both dimensions. However, the total number of bytes is now \(4\times \), which means this will be double the previous part.

  3. An AllReduce requires each device to send the full \(A\) across \(Z\). This should be \(\frac {2BD}{W_{\text {ICI}}}\) or \(2 \times \) the previous part.
    Remark. Completely misunderstood this question. For starters, when reducing along the \(Z\) axis, we still stay sharded across \(x\) and \(y\) and therefore do not make hops across those links. Therefore, we must divide by \(|X| \cdot |Y|\). Also, I guess the heuristic that AllReduce is roughly \(2 \times \) AllGather is used in calculations, which gives final answer \[\frac {4BD}{|X|\cdot |Y|\cdot W_{\text {ICI}}}\]

Exercise 3.3. latency-bound AllGather

  • August 5, 2026
  • Kellen Kanarios
 Let’s say we’re performing an \(\text {AllGather}_X([B_X])\) but \(B\) is very small (say 128). How long should this take on a TPU v4p 4x4x4 slice with mesh Mesh({'X': 4, 'Y': 4, 'Z': 4}) in bfloat16?
Solution

Since \(|X| = 4\), the hop latency time is \(\approx 4 \mu \)s. We have \(N = 2\cdot 128 = 256\)bytes and \(W_{\text {ICI}} = 9e10\). This gives \(.0028 \mu \)s. So we are severely latency bound.

Remark. Only need to do \(2\) hops in bi-directional case, so true answer is \(\approx 2\mu s\): still latency bound.

Exercise 3.4. matmul strategies

  • August 5, 2026
  • Kellen Kanarios
 To perform \(X[B,D]\cdot _D Y[D_X,F] \to Z[B,F]\), in this section we tell you to perform \(\text {AllGather}_X(Y[D_X,F])\) and multiply the fully replicated matrices (Case 2, Strategy 1). Instead, you could multiply the local shards like \(X[B,D_X]\cdot _D Y[D_X,F] \to Z[B,F]\{U_X\}\) (Case 3, Strategy 2), and then \(\text {AllReduce}_X(Z[B,F]\{U_X\})\). How many FLOPs and comms does each of these perform? Which is better and why?
Solution

Case 2, strategy 1. In this case, the AllGather will take \(\frac {DF}{W_{\text {ICI}}}\) for communication over \(ICI\) and \(BD + DF + BF\) over HBM with \(2BDF\) FLOPs.

Case 3, strategy 2. For local shards, each will only need to do \(\frac {2BDF}{X}\) FLOPs and \(BD + D_X F + BF\) HBM cost. However, the ICI cost would then be the whole matrix which is \(X \times \) as much over ICI.

Remark.

I was roughly correct. However, an important distinction (and gap in my understanding I gues) is that we have been ignoring HBM cost when communicating over ICI because these transfers are done concurrently and are therefore bottlenecked by the slower one (ICI).

Exercise 3.5. minimum latency

  • August 5, 2026
  • Kellen Kanarios
 Let’s say I want to do a matmul \(A[I,J]\cdot JB[J,K]\to C[I,K]\) on a TPU v4p 4x4x4 with the lowest possible latency. Assume the inputs can be sharded arbitrarily but the result should be fully replicated. How should my inputs be sharded? What is the total FLOPs and comms time?
Solution

My initial intuition is we do not want to shard along the contracting dimension. If we have a large enough matrix, then I think the best sharding strategy would be to shard \(A[I_{XYZ}, J], B[J, K]\). The multiplication then requires no communication, and the only communication is an AllGather across all \(3\) axis, which should triple bandwidth. Since we shard over every axis of our mesh, we do not have any additional replicated bytes. This gives us \(N = 2IK\)bytes in bf16. Since we are on a \(4\times 4\times 4\) cube, we have bi-directional bandwidth availability. Therefore, the communication time on TPU v4p is \(\frac {2IK}{3\cdot 9e10}\). The total flops is still just \(2IJK\).

Exercise 3.6. comparing shardings

  • August 5, 2026
  • Kellen Kanarios
 Let’s say we want to perform \(A[I_X,J_Y]\cdot _J B[J_Y,K]\to C[I_X,K]\) on TPU v5e 4x4. What communication do we perform? How much time is spent on communication vs. computation?
  • What about \(A[I_X,J]\cdot _J B[J_X,K_Y]\to C[I_X,K_Y]\)? This is the most standard setting for training where we combine data, tensor, and ZeRO sharding.
  • What about \(A[I_X,J]\cdot _J B[J,K_Y]\to C[I_X,K_Y]\)? This is standard for inference, where we do pure tensor parallelism.
Solution

  1. Since this is a matmul over the sharded axis, we need to perform a reduction at some point. After performing the matmul, we should have \(C[I_X, K]\{U_Y\}\). Therefore, we need to do an AllReduce over \(Y\). This is then a ReduceScatter and an AllGather. For computation, each chip does the partial sum, which takes \(\frac {2IJK}{|X||Y|}\) FLOPs. For communication, the AllReduce is \(2 \times \) an AllGather. We are still sharded over \(X\), so the total bytes is \(N = \frac {2IK}{|X|}\). We do not have bi-directional because the v5e is a 2d topology and \(4 \times 4\) is not full in either axis. Thus, the communication is

    \[\frac {2\cdot N}{W_{\text {ICI}}} = \frac {4IK}{4.5e10\cdot |X|}\]

    To see where we are bound, the v5e can do \(1.97e 14\) bf16 FLOPs/s. Therefore, we are compute bound when

    \[ \begin {align*} \frac {2IJK}{|X|\cdot |Y|\cdot 1.97e 14} > \frac {4IK}{4.5e10\cdot |X|} \iff J > \frac {8 \cdot 1.97e 14}{4.5e10} .\end {align*} \]

    Thus, we are almost surely communication bound because it is determined by the contracting dimension, which is \(d_{\text {model}}\) in practice.

    Remark. No solutions available. Prayers up this right...

  2. This is Case 1 with an additional sharding over the contracting dim in \(B\). I believe this means when we do the matmul, we are gonna end up with scattered partial sums i.e. unlike in the ReduceScatter case, where we have partial sums the same dimension as \(C\), the partial sums will now be \(\frac {I}{|X|} \times \frac {K}{|Y|}\). Another ReduceScatter would cause this smaller matrix to be further divided and scattered, so it is not what we want.

    Instead, we should just perform \(\text {AllGather}_X(B[J_X, K_Y])\). Then, this will directly reduce to Case 1 and we will need no further communication. We only need to send \(N = \frac {2JK}{|Y|}\) bytes. Once again, we do not have bi-directional bandwidth. Thus, the communication is

    \[\frac {N}{W_{\text {ICI}}} = \frac {4JK}{4.5e10\cdot |Y|}\]

    The FLOPs per-device are still \(\frac {2IJK}{|X|\cdot |Y|}\). To see where we are bound, the v5e can do \(1.97e 14\) bf16 FLOPs/s. Therefore, we are compute bound when

    \[ \begin {align*} \frac {2IJK}{|X|\cdot |Y|\cdot 1.97e 14} > \frac {2JK}{4.5e10\cdot |Y|} \iff I > \frac {4 \cdot 1.97e 14}{4.5e10} .\end {align*} \]

    Thus, we have a smaller bound than the previous part but are now dependent on \(I\) instead of \(J\). This is likely in practice because \(I\) corresponds to sequence length, which can get very large.

  3. This is pure case 1 with no communication, so we instead need to worry about memory instead of communication overhead.

Exercise 3.7. transformer block

  • August 5, 2026
  • Kellen Kanarios
 A typical Transformer block has two matrices \(W_{in}[D,F]\) and \(W_{out}[F,D]\) where \(F \gg DF \gg D\) . Say we have a batch size B. Then the full block is \(In[B,D]\cdot W_{in}[D,F]\cdot W_{out}[F,D]\). Let’s pick D=8192 , F=32768, and B=128 and assume everything is in bfloat16. Assume we’re running on a TPU v5e 2x2 slice but let’s pretend each TPU only has 300MB of free memory. How should In, \(W_{in}\), \(W_{out}\), and Out be sharded to stay below the memory limit while minimizing overall time? How much time is spent on comms and FLOPs? Hint: the final output doesn’t need to be fully replicated, but it should be sharded the same as the input so the “layer” can be repeated.
Solution

To start, lets compute how big everything is.

\[ \begin {align*} In &= 2\cdot B\cdot D \\ &= 2\cdot 8192\cdot 128 = 2^{21} \\ W_{in} &= 2\cdot D\cdot F \\ &= 2\cdot 8192\cdot 32768 = 2^{29} \\ W_{out} &= 2\cdot D\cdot F \\ &= 2\cdot 8192\cdot 32768 = 2^{29} \end {align*} \]

and each TPU has \(300\)MB \(\approx 300 \cdot 2^{20} \approx 2^{28}\) in this example. Therefore, each TPU can fit just over one half of \(W_{in}\) and \(W_{out}\), which leads us to have to fully shard both across \(X\) and \(Y\). The remaining \(11 \cdot 2^{22}\) can fit \(\text {In}\). However, we need to satisfy the constraint that \(\text {Out}\) is sharded in the same way as \(\text {In}\). I propose first

  • Shard \(\text {In}[B_{XY}, D]\), \(W_{in}[D,F_{XY}]\)

Then, we are in case 1 and have an output of \(W_{mid}[B_{XY}, F_{XY}]\) with no communication necessary. However, we now need to multiply \(W_{mid}\) with \(W_{out}\). I propose to

  • Shard \(W_{out}[F, D_{XY}]\)

This then requires two AllGather's. First, we have to AllGather \(W_{mid}\) along \(F\). Then we perform the matmul between \(W_{mid}\) and \(W_{out}\), which gives \(Out[B_{XY}, D_{XY}]\). To provide \(\text {Out}\) as \(\text {In}\) to the next layer, we then must \(\text {AllGather}_{XY}\) along \(D\).
