NVIDIA architecture targets [UT52]

  • August 14, 2026
  • Kellen Kanarios

An sm_XX target is the compute capability a GPU kernel is compiled against — nvcc -arch=sm_90a — and it names an instruction surface, not a performance tier. What follows is the coverage a tensor-core kernel actually has to care about: which MMA instruction family exists, and which of the asynchronous data-movement features it depends on came with it.

Target SKU Tensor-core path and notable features
sm_80 A100 mma.sync, ldmatrix, cp.async; no TMA, clusters, or TMEM
sm_89 L40S / RTX 6000 Ada mma.sync, ldmatrix, cp.async; FP8 tensor cores, no TMA or TMEM
sm_90a H100 / H200 wgmma + mma.sync; TMA, thread-block clusters, async barriers, DSM
sm_100a B200 tcgen05.mma + TMEM; 2-CTA MMA (cta_group::2), tcgen05.ld / .cp / .shift
sm_103a B300 adds tcgen05.ld.red, \(K = 96\) block-scaled MMA
sm_120a RTX 5090 / RTX PRO 6000 mma.sync + ldmatrix, TMA, clusters, DSM; no tcgen05 or TMEM
sm_121a DGX Spark (GB10) same instruction surface as sm_120a, separate cubin, different SFU rates

Read down the third column and the datacenter line tells one story: each generation moves the matrix multiply further away from the individual thread. mma.sync is issued by a warp and the operands live in its registers; wgmma is issued by a warpgroup of four and can read the \(A\) operand straight out of shared memory; tcgen05.mma is issued by a single thread on behalf of a CTA pair and keeps its accumulator in Tensor Memory (TMEM), a memory the register file does not see. The data movement follows the same arc — cp.async is a per-thread copy, Tensor Memory Accelerator (TMA) is a descriptor a single thread hands to a hardware engine.

The trap in the table is sm_120a. Consumer Blackwell shares the marketing generation with B200 but not the tensor-core path: it has Hopper-era conveniences (TMA, clusters, Distributed Shared Memory (GPU)) and Ampere-era MMA, with no tcgen05 and no TMEM at all. A kernel written against sm_100a does not merely run slower on a 5090 — it does not compile. Treat sm_120a as the branch point in a kernel's dispatch, not as a small delta from sm_100a.

Remark. The trailing a means architecture-specific: the target enables instructions exclusive to that exact chip and gives up forward compatibility, so the resulting cubin will not PTX-JIT onto a later architecture the way a plain sm_90 binary would. Every generation from Hopper on ships its tensor-core ISA only behind an a target, which is why a real build matrix has one entry per row above rather than one per generation. sm_121a is the extreme case — the same instruction surface as sm_120a and still its own cubin.
