Triton [CQ6W]

  • August 22, 2026
  • Kellen Kanarios

A Python-embedded DSL for GPU kernels in which you write block-level code — load a tile, do arithmetic on it, store it — and the compiler decides how the tile maps onto threads [tilletTritonIntermediateLanguage2019]. That is the trade against CUDA: you give up control of the thread indexing that memory coalescing depends on, and in exchange you stop writing it.

The compiler is built on MLIR, with two custom dialects, and the boundary between them is the single most useful thing to know when a kernel is slow (The prefix says which side of layout assignment). ttir (tt. ops) is the target-independent tensor level — roughly what you wrote. ttgir (ttg. ops) is after layout assignment, where every tensor carries an encoding saying which lane holds which element (An encoding tiles the block across threads and warps).

So a Triton performance problem is one of two things, and the dialect prefix tells you which. At the tt. level it is your algorithm — the tiling, the loop structure, the arithmetic. At the ttg. level it is the compiler's distribution of it, and the usual culprit is a ttg.convert_layout that round-trips a tensor through shared memory inside a loop (A convert_layout round-trips through shared memory). The second kind is invisible in your source and obvious in the IR, which is the argument for reading the IR.

From XLA's side a Triton kernel is an opaque @triton_kernel_call custom call (XLA custom call, A custom call is a black box XLA cannot fuse across), so nothing fuses across it — the same bargain Pallas makes on TPU.

What do the tt. and ttg. (triton_gpu) prefixes separate in Triton IR?

Answer tt. is the target-independent tensor level: tt.load, tt.store, tt.dot, tt.make_range, and pointer arithmetic on !tt.ptr<f32> over block shapes. This is roughly what you wrote. ttg. is after layout assignment: the same tensors now carry an encoding attribute saying how their elements are distributed across warps, lanes, and registers (An encoding tiles the block across threads and warps), plus ops like ttg.convert_layout (A convert_layout round-trips through shared memory) and shared-memory allocation (Shared memory (GPU)). So the prefix tells you which side of layout assignment you are on, and that is the division that matters when a Triton kernel is slow: a problem at the tt. level is your algorithm, and a problem that only appears at ttg. is the compiler's distribution of it. Same use of the dialect prefix as a marker of pipeline stage as chlo / stablehlo / mhlo (chlo desugars, stablehlo is stable, mhlo is internal).

Card. An encoding tiles the block across threads and warps [RI0V]

  • August 22, 2026
  • Kellen Kanarios

Read tensor<128x64xf16, #blocked> where #blocked = #ttg.blocked<{sizePerThread=[1,4], threadsPerWarp=[8,4], warpsPerCTA=[4,1], order=[1,0]}>

Answer The encoding says how the logical \(128 \times 64\) tile is distributed:
  • sizePerThread — elements each thread holds per dimension; the minor-dimension entry is the vectorisation width.
  • threadsPerWarp — how the 32 lanes of a Warp (GPU) are arranged in two dimensions.
  • warpsPerCTA — how warps tile the block.
  • order — minor-to-major, so which dimension is contiguous per thread (The layout is minor-to-major).
Multiply the three lists out and you get the tile one CTA covers in one pass: \(1 \times 8 \times 4 = 32\) rows and \(4 \times 4 \times 1 = 16\) columns here, so the \(128 \times 64\) shape takes \(4 \times 4\) repeats. That arithmetic is the whole content of the attribute, and it is how you check by hand whether loads coalesce.

Card. A convert_layout round-trips through shared memory [B4XO]

  • August 22, 2026
  • Kellen Kanarios

Why is ttg.convert_layout the op to look for in a slow Triton kernel?

Answer It re-distributes a tensor from one encoding to another (An encoding tiles the block across threads and warps) — typically #blocked to a #ttg.dot_op or #mma operand layout, because the tensor core wants its operands arranged differently from the way the loads produced them. Unless the conversion happens to be a pure register permutation, it round-trips through shared memory and inserts barriers. That is a store, a sync across the block, and a load — for data that never changed value. One unnecessary convert_layout inside a loop body is a classic Triton performance bug, and it is visible in the IR long before it is visible in a profile. The layout-propagation passes exist to hoist these out of loops or eliminate them, so one that survives in the body is worth understanding rather than accepting.
