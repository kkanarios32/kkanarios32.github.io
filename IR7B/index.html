MLIR [IR7B]

  • July 15, 2026
  • Kellen Kanarios

An extensible compiler infrastructure: rather than one instruction set, a framework in which each domain defines its own dialect of operations, types, and attributes, all sharing one syntax and one pass infrastructure. That shared syntax is why an unfamiliar dialect is still readable on sight: the op grammar is fixed even when the ops are not, and Five sigils make any dialect readable is most of what reading one takes.

Collection of resources

  • https://llvm.org/devmtg/2020-09/slides/MLIR_Tutorial.pdf
  • https://www.lei.chat/posts/mlir-linalg-dialect-and-patterns/
  • https://www.lei.chat/posts/mlir-vector-dialect-and-patterns/

Dialects. This is effectively a syntax. For your given DSL, you must write each of the operations in this MLIR dialect in order to inherit the benefits of the MLIR ecosystem.

The whole structured CodeGen paradigm in MLIR prefers co-designing op semantics and transformations and let ops structurally encode and guarantee certain properties to simplify analyses and transformations.
— Lei Zhang

The general paradigm. It seems that when you are writing a DSL backed by MLIR that you

  1. Write an MLIR dialect for your DSL
  2. You can write custom compiler passes for your MLIR dialect.
    • This is what is done in Triton.
    • Triton has two custom MLIR dialects: ttir and ttgir.
      • The ttir dialect is the backend agnostic IR.
      • The ttgir dialect is the Triton GPU IR.
  3. Write a lowering pass from your MLIR dialect to the MLIR dialect of an MLIR with codegen backing i.e.
    • MLIR has an LLVM dialect
    • Alternatively, XLA ingests StableHLO, which is an MLIR dialect. In theory, this means that if your DSL is similar to that of a JAX / LinAlg dialect, then you can get a lot of the optimizations Google has come up with for free.
      • However, XLA works by translating StableHLO to HLO (via the internal mhlo dialect, chlo desugars, stablehlo is stable, mhlo is internal), which is then optimized by XLA. HLO is NOT an MLIR dialect and therefore in order to use XLA your backend needs to have an appropriate conversion from HLO to an executable on their backend.
      • This is what is done for trainium. Namely, the neuronx-cc compiler performs the translation from optimized HLO to optimized executable code on their ASIC.
    • Triton and the GPU backend for XLA are the LLVM + NVVM MLIR, which is the MLIR dialect for LLVM with added GPU instructions.

1. Reading a dump

  • July 15, 2026
  • Kellen Kanarios

Because the dialect is open-ended, what you can rely on is the structure: one op syntax (One shape for every op), five sigils (Five sigils make any dialect readable), regions for nesting, attributes for compile-time data, and a location on every op. That fixed part is enough to read a dialect whose documentation you have never opened.

Card. One shape for every op [JE7W]

  • August 22, 2026
  • Kellen Kanarios

In MLIR's generic form, what does each part of %0 = "foo.add"(%a, %b) : (i32, i32) -> i32 mean?

Answer Every op, in every dialect, prints to one shape: 
results = "dialect.opname"(operands) ({regions}) {attributes} : (operand types) -> result types
  • The quoted name is always dialect.op. The prefix is what makes an unfamiliar op findable — it names the dialect whose docs define it.
  • The type after the colon is a function type: operand types before the arrow, result types after. So the signature is always readable off the one line.
  • Only operands sit in the parens. Attributes are the brace dictionary and are compile-time constants, not Static single assignment values — that split is exactly what is known at compile time versus what flows at runtime.
Learn this shape once and any dialect is parseable; the pretty forms are sugar over it (The pretty form is optional, the generic form always works).

Card. The pretty form is optional, the generic form always works [T1YS]

  • August 22, 2026
  • Kellen Kanarios

Why does the same op print two different ways — arith.addi %a, %b : i32 versus "arith.addi"(%a, %b) : (i32, i32) -> i32?

Answer An op may define a custom pretty printer and parser; the generic form (One shape for every op) is the fallback that always works. Most dialects define one, so most dumps are pretty. The consequence when reading a dump. The type after the colon in pretty form is whatever the op's printer chose to show — usually just the element or result type, not the full signature. Operands, regions, and attributes may all be elided or rearranged. When a pretty form is ambiguous, re-dump with --mlir-print-op-generic (Print generic, print locations, disable threading) and read the unambiguous version.

Card. Five sigils make any dialect readable [KWH2]

  • August 22, 2026
  • Kellen Kanarios

What do the five MLIR sigils %, ^, @, #, ! mark?

Answer
  • % — an Static single assignment value (SSA names are printing hints).
  • ^ — a block label (Block arguments replace phi nodes).
  • @ — a symbol: function, global (Symbols are looked up, values are defined).
  • # — an attribute or attribute alias: #map0, #stablehlo.dot<...>, #tpu.memory_space<vmem>.
  • ! — a type or type alias: !llvm.ptr, !tt.ptr<f32>.
This is the whole trick to reading an unfamiliar dialect. MLIR is extensible in ops, types, and attributes, so you will constantly meet names you do not know — but the sigil tells you which kind of thing it is, and therefore where it may legally appear. # and ! in particular are the escape hatches every dialect uses for its own metadata (The prefix says which side of layout assignment, Mosaic is explicit memory spaces and explicit copies).

Card. A multi-result op binds one name and indexes into it [OBP3]

  • August 22, 2026
  • Kellen Kanarios

In an MLIR dump, what is %2#1?

Answer The second result — index 1 — of the op that defined the value group %2. A multi-result op binds one name and you index into it: 
%2:3 = "foo.split"(%x) : (tensor<6xf32>) -> (tensor<2xf32>, tensor<2xf32>, tensor<2xf32>)
then %2#0, %2#1, %2#2. The declaration syntax %2:3 means "three results named %2", not a type annotation. This is MLIR's alternative to HLO's tuple-plus-get-tuple-element idiom (get-tuple-element is free aliasing): multiple results are native, so no packing op is needed.

Card. SSA names are printing hints [MOVC]

  • August 22, 2026
  • Kellen Kanarios

Are MLIR value names like %arg0, %c0_i32, %lhs semantically meaningful?

Answer No. They are printing hints only. Internally Static single assignment values are positional and unnamed; the asm printer reconstructs a name from a name-hint interface, which is why constants come out as %c0_i32 or %cst and block arguments as %arg0. Two things follow, and both bite when reading dumps:
  • %arg0 in two different functions or regions are unrelated. The name is scoped to its region and carries no identity across one.
  • The numbering is not stable across passes. Diffing two per-pass dumps (Per-pass dumps find the pass that broke it) on value names produces noise; diff on structure instead.
The Locations are the provenance of an op is the stable thing to key on — it survives the passes that renumber values.

Card. Block arguments replace phi nodes [QZFU]

  • August 22, 2026
  • Kellen Kanarios

Read this line: ^bb1(%arg0: i32, %arg1: f32):

Answer A block label with block arguments. MLIR has no phi nodes — instead each predecessor passes the merged values as branch operands: 
cf.br ^bb1(%x, %y : i32, f32)
Block arguments are the Static single assignment merge mechanism. The trade is that a value's incoming edges are recorded at the branches rather than collected at the merge, which makes CFG edits local: rewriting one predecessor touches one op. The entry block of a function-like op takes the function's parameters this same way, which is why %arg0 is the conventional name for a function argument.

Card. A region is nesting, not a flat CFG [MKYF]

  • August 22, 2026
  • Kellen Kanarios

What is a region in MLIR, and which ops have them?

Answer A region is an ordered list of blocks nested inside an op, written in braces. It is how MLIR encodes structured control flow and nesting instead of flattening everything into one CFG.
  • func.func — one region, the body.
  • scf.for — one region (iter_args and yield are the mutable accumulator); scf.if — two, then and else (Both scf.if regions must yield the same types).
  • stablehlo.reduce — one region holding the reducer (reduce takes a computation, not an enum).
Every block in a region ends in a terminator: scf.yield, func.return, cf.br. Regions are the structural reason MLIR can host both high-level tensor dialects and low-level CFGs in one module — a pass lowering scf.for to blocks is just replacing a region with a CFG.

Card. Position separates attributes from regions [CZBE]

  • August 22, 2026
  • Kellen Kanarios

In an MLIR dump, how do you tell an attribute dictionary from a region?

Answer By what is inside, and in generic form by position. Content. An attribute dict is {name = value, name2 = value2} — every entry is key = constant. A region contains operations, and possibly block labels (Block arguments replace phi nodes). Position. In generic form (One shape for every op) the slots are fixed: 
"scf.if"(%cond) ({ ...then... }, { ...else... }) {some_attr = 1} : (i1) -> ()
Regions come in parens straight after the operands; attributes come after the regions, before the colon type. The distinction matters because it is the compile-time / runtime line: an attribute is known to the compiler now, a region is code that runs.

Card. Symbols are looked up, values are defined [45LB]

  • August 22, 2026
  • Kellen Kanarios

In MLIR, what is @foo versus %foo?

Answer @foo is a symbol reference — a name resolved by lookup in a SymbolTable (a func.func, a global). %foo is an Static single assignment value defined earlier in the same region. Nested symbols use @parent::@child. The distinction shows up in the type list, which is the tell when reading a call: 
func.call @foo(%a) : (i32) -> i32
The callee is a symbol, not an operand, so it does not appear in the operand types — only %a does. A symbol is resolved at compile time; a value flows at runtime.

Card. Every dump is wrapped in a module [R2O9]

  • August 22, 2026
  • Kellen Kanarios

What wraps every MLIR dump, and what does a named one look like?

Answer A builtin.module. Printed bare as module { ... }, or with a name and attributes: 
module @jit_f attributes {mhlo.num_partitions = 1 : i32} { ... }
The outer braces are a region (A region is nesting, not a flat CFG), so the module is an ordinary op — there is nothing special about the top level. Read the module attributes first. In a JAX or XLA dump they carry the information the body assumes: partition and replica counts, Sharding configuration, target features. A body that looks like it does too little often makes sense once you see num_partitions up here.

Card. Three attribute positions on a function [ZZHW]

  • August 22, 2026
  • Kellen Kanarios

Decode the three annotation positions in func.func @main(%arg0: tensor<8xf32> {jax.arg_info = "x"}) -> (tensor<8xf32> {jax.result_info = ""}) attributes {llvm.emit_c_interface}

Answer Three different kinds of attribute, distinguished only by where they sit:
  1. Argument attributes — braces after an argument's type. Per-argument metadata.
  2. Result attributes — braces after a result's type, inside the result parens. Per-result metadata.
  3. Op attributes — after the keyword attributes. These belong to the function op itself.
JAX uses the first two to record what tracing threw away: the original Python argument names, donation, and per-argument Sharding. When you need to know which HLO parameter (parameter(i) is positional) was which Python argument, jax.arg_info is the record.

Card. An affine map separates dimensions from symbols [51XY]

  • August 22, 2026
  • Kellen Kanarios

Read #map = affine_map<(d0, d1)[s0] -> (d0 * s0 + d1)>

Answer An affine map: a multi-dimensional affine function used for indexing and loop bounds.
  • (d0, d1) — dimension operands: loop induction variables, indices. These vary within the iteration space.
  • [s0] — symbol operands: quantities loop-invariant over the map's use, such as sizes and strides.
  • The results are affine expressions over both — addition, subtraction, multiplication by a constant, floordiv, ceildiv, mod.
The dimension/symbol split is the point. Restricting to affine expressions of dims and symbols is what makes dependence analysis decidable, which is what lets the affine dialect tile, fuse, and interchange loops automatically. You will meet these on affine.load, affine.for bounds, and linalg indexing_maps, where the map says how the iteration space lands in memory.

Card. An unrealized cast that survives is a missing pattern [Y070]

  • August 22, 2026
  • Kellen Kanarios

What does builtin.unrealized_conversion_cast mean when you see it in an MLIR dump?

Answer A placeholder bridging two type systems mid-conversion — tensor to memref (A memref names storage, a tensor is a value), a dialect type to !llvm.ptr. The dialect conversion framework inserts them so that a partial conversion still verifies while some ops are converted and others are not. If one survives to the end of the pipeline, that is the bug. It means no pattern claimed the op on one side of the cast, so the conversion never closed. Chase the missing pattern rather than the cast. Mid-pipeline, in a --mlir-print-ir-after-all dump (Per-pass dumps find the pass that broke it), they are expected noise; at the boundary where the IR is supposed to be one dialect, they are a failure.

2. Locations

  • July 15, 2026
  • Kellen Kanarios

Value names are printing hints and instruction order changes every pass, so provenance has to be carried explicitly. The location is the only thing in the IR that survives rewriting well enough to answer "which line of Python produced this op".

Card. Locations are the provenance of an op [NRD2]

  • August 22, 2026
  • Kellen Kanarios

What does loc("model.py":42:8) on an MLIR op tell you, and how do you get locations printed?

Answer It is the op's Location — the provenance the compiler carries for diagnostics and for mapping generated code back to source. An op that was never given one prints loc(unknown). Print them with --mlir-print-debuginfo, or --mlir-print-debuginfo --mlir-pretty-debuginfo for a compact form (Print generic, print locations, disable threading). Why it is the tool that matters. Value names are unstable (SSA names are printing hints) and op ordering changes every pass, but a location survives rewrites — passes are expected to propagate it, fusing into fused and inlining into callsite (Fused means merged, callsite means inlined). So "which line of Python produced this op" is a location question, and only a location question. It is the MLIR analogue of HLO's metadata field (op_name is the trace path back to Python).

Card. Fused means merged, callsite means inlined [SE0U]

  • August 22, 2026
  • Kellen Kanarios

What do these two location forms mean? loc(fused["a.py":1:1, "b.py":2:2]) and loc(callsite("inner" at "outer"))

Answer fused — the op came from several source ops that a pass merged: Operator fusion, canonicalization, a rewrite that collapsed a chain. A fused location may carry a tag naming the culprit, loc(fused<"fusion">[...]). callsite — an inlining chain. Read it inner-to-outer: the callee's location first, then the site it was called from. Chains nest one level per inlining. Both are how a Locations are the provenance of an op stays honest under transformation: rather than picking one survivor and losing the rest, the location grows to record what happened. So a long fused location is itself the evidence that this op is several of your source ops.

Card. Aliases are deduplicated printing [7Z9D]

  • August 22, 2026
  • Kellen Kanarios

What are the #loc3 = loc(...) lines at the bottom of an MLIR dump?

Answer Location aliases. The printer hoists a repeated Locations are the provenance of an op into a named definition, and ops then reference it as ... loc(#loc3). It is the same mechanism as attribute aliases (#map0, An affine map separates dimensions from symbols) and type aliases (!my_type): purely printing deduplication, with no semantic content. Two ops sharing #loc3 have equal locations, nothing more. Practically: when you jump to an op and find loc(#loc3), the answer is at the bottom of the file, not missing.

3. The type system

  • July 15, 2026
  • Kellen Kanarios

The type grammar is where a dump's abstraction level is written down. Tensors mean you are above bufferization, memrefs mean storage and therefore aliasing, vectors mean register width and proximity to the hardware.

Card. Question mark is a dynamic dimension, star is unknown rank [L3F6]

  • August 22, 2026
  • Kellen Kanarios

What do tensor<4x?xf32>, tensor<*xf32>, and tensor<f32> mean?

Answer
  • 4x?xf32 — ranked, with the second dimension dynamic: ? means unknown at compile time.
  • *xf32 — unranked; even the rank is unknown.
  • tensor<f32> — a rank-0 tensor, which is not the same type as a bare f32.
The rank-0 distinction is the one that catches people. A scalar tensor is still a tensor and takes tensor ops; f32 is a scalar and takes arith ops. Conversions between them are explicit. A tensor is a value with no memory location — it cannot alias, so a pass may duplicate or reorder it freely. That freedom is exactly what a memref gives up (A memref names storage, a tensor is a value). By contrast HLO has no dynamic shapes at all: every dimension is known at compile time (An HLO line is self-contained).

Card. A memref names storage, a tensor is a value [B1A1]

  • August 22, 2026
  • Kellen Kanarios

Read memref<8x128xf32, strided<[128, 1], offset: ?>, #tpu.memory_space<vmem>>

Answer A buffer reference: shape and element type, then two optional slots.
  • strided<[128, 1], offset: ?> — the layout. Strides are in elements, not bytes; the offset is dynamic. Strides of [128, 1] on an 8x128 shape is the contiguous row-major case, the MLIR spelling of HLO's {1,0} (The layout is minor-to-major).
  • #tpu.memory_space<vmem> — which memory this lives in (VMEM / smem / hbm on TPU; 1 and 3 for shared and global on GPU).
The difference from a tensor is aliasing. A memref names storage, so two of them may refer to the same bytes and a pass must prove otherwise before reordering. A tensor is a value and cannot alias (Question mark is a dynamic dimension, star is unknown rank). Bufferization is the pass that trades the second for the first, and it is where most "why did a copy appear" questions live.

Card. Vectors are register-level, tensors are abstract [1XJ4]

  • August 22, 2026
  • Kellen Kanarios

Distinguish vector<4x8xf32>, vector<[4]xf32>, and tensor<4x8xf32>

Answer A vector is a fixed-size, register-level SIMD value — always ranked, always static. A tensor is an abstract n-dimensional value that still needs bufferization and lowering (Question mark is a dynamic dimension, star is unknown rank). Brackets around a dimension, [4], mark it scalable: the length is 4 * vscale, fixed by the hardware at run time rather than compile time. That is the SVE / RVV style of vector target, where the register width is not known when you compile. What seeing vector types tells you about the dump. You are past the tensor level and close to hardware — the shapes are now register tiles, not logical arrays. On TPU that is the 8x128 native tile you see all through a Mosaic dump (Mosaic is explicit memory spaces and explicit copies).

Card. Signedness lives in the op, not the type [I4UP]

  • August 22, 2026
  • Kellen Kanarios

Why is it arith.divsi and arith.divui rather than one divide over a signed type?

Answer Because integer types in MLIR are signless: i32 is thirty-two raw bits and nothing more. Signedness lives in the operation, not the type. So the op suffix is the interpretation — si signed, ui unsigned — and it appears exactly on the ops where it changes the answer: divide, remainder, comparison, widening extension, shift right. Addition and multiplication need no suffix, because two's complement makes them agree. Why design it this way. One type means one canonical form, so a pattern that matches i32 matches everything, and frontends with different signedness rules can share the dialect. Some dialects do carry si32 and ui32 for frontend fidelity, but core arith is signless plus typed ops.

Card. index is the type of sizes and offsets [2QC3]

  • August 22, 2026
  • Kellen Kanarios

What is the index type in MLIR and where does it show up?

Answer A target-dependent-width integer for sizes, offsets, and loop induction variables. It lowers to i32 or i64 depending on the target, so the IR does not have to commit to a pointer width. You will see it constantly in the shape of 
%c0 = arith.constant 0 : index
feeding memref.dim, scf.for bounds (iter_args and yield are the mutable accumulator), tensor.extract indices, and memref.subview offsets. Read it as a type-level statement of intent: this value addresses the iteration space, it is not data. That is why index and i32 do not implicitly convert — arith.index_cast is required, and its appearance in a dump marks the boundary where an index became a number or the reverse.

Card. A scalar inside dense is a splat [5B7I]

  • August 22, 2026
  • Kellen Kanarios

Read these three MLIR constants: dense<[1, 2, 3, 4]> : tensor<4xi32>, dense<0.000000e+00> : tensor<8x128xf32>, dense_resource<__elided__> : tensor<1024x1024xf32>

Answer
  • Bracketed list — a full elementwise literal, one entry per element, with one level of bracket nesting per dimension: a rank-2 constant is a list of rows.
  • A single scalar inside dense<> — a splat: every element takes that value. This is the common case and is stored as one number, not as the expanded array.
  • dense_resource<__elided__> — the printer dropped the payload because it was large. The data still exists in the real module; only the text you are reading lost it.
Elision is controlled by --mlir-elide-elementsattrs-if-larger=N. Raise it when you actually need to see the weights, and leave it alone otherwise — a dump of a real model is otherwise mostly constants. HLO does the same thing, printing a big constant as {...} (iota builds indices without a constant).

4. Structured control flow

  • July 15, 2026
  • Kellen Kanarios

The scf dialect keeps a loop as one op with a region rather than as a CFG, which is what lets a pass reason about it as a loop. The carry is explicit and typed — the same design the jaxpr scan (consts, then carry, then xs) and the HLO while (A while loop's whole state is one tuple) arrive at independently.

Card. iter_args and yield are the mutable accumulator [ON39]

  • August 22, 2026
  • Kellen Kanarios

Read this loop: %r = scf.for %i = %c0 to %c8 step %c1 iter_args(%acc = %init) -> (f32) { %n = arith.addf %acc, %x : f32; scf.yield %n : f32 }

Answer A structured loop that carries state.
  • %i is a block argument of the loop body (Block arguments replace phi nodes), not a value from the enclosing scope.
  • iter_args(%acc = %init) declares the loop-carried values and initialises them once, before the first iteration.
  • scf.yield supplies the next iteration's iter_args and, on the final iteration, the loop's results %r.
So iter_args plus scf.yield is the functional spelling of a mutable accumulator. Nothing is stored; each iteration produces a new value. That is what keeps the loop in Static single assignment form and lets it be analysed and rewritten as a pure region (A region is nesting, not a flat CFG). Both the jaxpr scan (consts, then carry, then xs) and the HLO while (A while loop's whole state is one tuple) use the same idea — the carry is explicit and typed — differing only in how the carried values are packed.

Card. Both scf.if regions must yield the same types [1U5S]

  • August 22, 2026
  • Kellen Kanarios

How does an scf.if produce a value?

Answer By declaring result types on the op and having both regions (A region is nesting, not a flat CFG) terminate in scf.yield with matching types: 
%v = scf.if %pred -> (f32) { scf.yield %a : f32 } else { scf.yield %b : f32 }
If the op has no results, the else region may be omitted entirely and the yields are empty. The type match is the invariant worth remembering. It is what makes the construct an expression rather than control flow — the op has one well-defined type regardless of which branch runs, so it composes like any other value-producing op (iter_args and yield are the mutable accumulator). A verifier error on scf.if is almost always the two branches disagreeing.

5. Debugging a lowering

  • July 15, 2026
  • Kellen Kanarios

Card. Print generic, print locations, disable threading [7R2Y]

  • August 22, 2026
  • Kellen Kanarios

Which MLIR debugging flags do you reach for when a lowering looks wrong?

Answer
  • --mlir-print-ir-after-all (or --mlir-print-ir-after-change, or -before=<pass>) — IR snapshots per pass. The MLIR counterpart to --xla_dump_hlo_pass_re (Per-pass dumps find the pass that broke it).
  • --mlir-print-op-generic — removes pretty-printer ambiguity (The pretty form is optional, the generic form always works).
  • --mlir-print-debuginfo — locations, so ops trace back to source (Locations are the provenance of an op).
  • --mlir-disable-threading — serialises the pass manager so per-pass output is ordered and readable.
  • --debug-only=<pass-name> — pattern-level tracing, in a debug build only.
Turn off threading first. Without it, per-pass dumps from parallel op processing interleave, and you spend the session reading a file whose disorder is the tooling's, not the compiler's.
