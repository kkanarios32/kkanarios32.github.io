exec() [YHJR]

  • May 12, 2026
  • Kellen Kanarios

Replaces the calling Process's program with a new executable. exec() does not return on success — the original code, data, stack, and heap are discarded and the new program runs in their place. The PID is unchanged.

What exec() does internally:

  1. Loads the new executable's code and static data, overwriting the current.
  2. Re-initializes stack and heap.
  3. Jumps to the new program's entry point with arguments passed as argv.

The canonical Unix pattern is fork() then exec() — the shell uses this to launch a command without becoming that command:

int main()
  while (true) {
    command = getcommand();
    int rc = fork();
    if (rc < 0)
      printf("error with fork");
    else if (rc == 0)
      exec(command);            // child becomes the command
    else
      int rc = wait(NULL);      // parent waits for it
  }

Redirection is implemented by opening a file in the child between fork() and exec(), attached to STDOUT_FILENO:

if (rc == 0)
  close(STDOUT_FILENO);
  open("output.txt");
  exec(command);
Remark. The many variants — execl, execle, execlp, execv, execvp, execvP — differ in how they take arguments (list vs. vector), whether they use the PATH environment variable, and whether they take an explicit environment.

    The cache controller

    • August 3, 2026
    • Kellen Kanarios

    Silent upgrades. If a cache in \(E\) may upgrade to \(M\) silently, the directory never learns the line went dirty, and the value it hands to the next GetS or GetM is stale. There are two consistent ways out: forbid the silent upgrade, in which case no forwarding is needed; or allow it and treat \(E\) exactly like \(M\), forwarding everything. Neither requires a writeback on PutE. I take the first, matching the table.

    Signaling exclusivity. The directory needs a way to tell a requester "you are the first reader, take the line exclusive." That is a new ExclusiveData message: receiving it in \(IS^D\) lands the cache in \(E\) rather than \(S\). It turns out to also be the key to the second race below.

    Remark. Once PutE or PutM has been sent, \(EI^A\) and \(MI^A\) are functionally identical. Both appear above for completeness, but transitioning from \(E\) straight into \(MI^A\) verifies the same.

    • August 3, 2026

    The nastier version of the same race: the invalidation arrives before the forward. By the \(II^A\) rule inherited from MSI, a PutAck in that state drops the line to \(I\) — discarding data a forwarded request is about to ask for.

    Example.
    1. Proc_1 load-misses → \(IS^D\)
    2. Home takes the first GetS from Proc_1 → \(E\), sends ExclusiveData
    3. Proc_2 issues GetM → \(IM^{AD}\)
    4. Home sends Inv to Proc_1
    5. Home forwards Fwd-GetM to Proc_1
    6. Proc_1 receives Inv → \(II^D\)
    7. Proc_1 receives ExclusiveData → \(I\), and the data is lost

    Fix. ExclusiveData pays for itself a second time. Because the message is distinguishable from ordinary Data, a cache receiving it in \(II^D\) knows it was the first reader and transitions to \(E\) instead of \(I\) — from which the pending Fwd-GetM or Fwd-GetS is handled correctly.

    Flash Attention (Bwd) [OGCRZ]

    • May 27, 2026
    • Kellen Kanarios

    The forward pass of flash attention avoids materializing the \(N \times N\) attention matrix by streaming an online softmax. The backward pass has to pull the same trick twice over, because the naive gradient computation wants two \(N \times N\) matrices — \(\mathbf {P}\) and \(d\mathbf {P}\). Getting there means first writing down every gradient we need, then finding a way to recompute rather than store each one.

    Notation. Following the notation in the original paper, \[\mathbf {S} = \mathbf {Q} \mathbf {K}^T, \quad \mathbf {P} = \mathrm {softmax}(\mathbf {S}), \quad \mathbf {O} = \mathbf {P} \mathbf {V},\] where \(\mathbf {Q}, \mathbf {K}, \mathbf {V}, \mathbf {O}\) are \(N \times d\) and \(\mathbf {S}, \mathbf {P}\) are \(N \times N\). For a scalar loss \(\phi \) we abbreviate the gradient with respect to any matrix \(\mathbf {X}\) as \[d\mathbf {X} = \frac {\partial \phi }{\partial \mathbf {X}},\] and write \(\mathbf {L}_i\) for the softmax denominator of row \(i\) saved by the forward pass, so that \(\mathbf {P}_{ij} = \exp (\mathbf {Q}_i \cdot \mathbf {K}_j) / \mathbf {L}_i\).

    The gradients we need for FlashAttention [4QZE]

    • August 3, 2026
    • Kellen Kanarios

    Everything downstream is chain rule; the only step with any content is differentiating through the softmax. We take the gradients in dependency order, starting from \(d\mathbf {O}\) which arrives from the layer above.

    \(d\mathbf {P}\) and \(d\mathbf {V}\) from \(\mathbf {O} = \mathbf {P}\mathbf {V}\)

    • August 3, 2026
    • Kellen Kanarios

    Both fall straight out of the product rule for matrices:

    \[ d\mathbf {P} = \frac {\partial \phi }{\partial \mathbf {O}} \frac {\partial \mathbf {O}}{\partial \mathbf {P}} = d\mathbf {O} \mathbf {V}^T, \qquad d\mathbf {V} = \frac {\partial \phi }{\partial \mathbf {O}} \frac {\partial \mathbf {O}}{\partial \mathbf {V}} = \mathbf {P}^T d\mathbf {O}. \]

    The shapes are a useful sanity check. \(d\mathbf {O}\) has one entry per output, so it is \(N \times d\); \(\mathbf {V}^T\) is \(d \times N\); their product is \(N \times N\), matching \(\mathbf {P}\). Likewise \(\mathbf {P}^T d\mathbf {O}\) is \(N \times d\), matching \(\mathbf {V}\).

    Componentwise, from \(\mathbf {O}_{ik} = \sum _j \mathbf {P}_{ij} \mathbf {V}_{jk}\),

    \[ \begin {align*} d\mathbf {P}_{ij} &= \sum _{k} \frac {\partial \phi }{\partial \mathbf {O}_{ik}} \cdot \frac {\partial \mathbf {O}_{ik}}{\partial \mathbf {P}_{ij}} = \sum _{k} d\mathbf {O}_{ik} \mathbf {V}_{jk}, \\ d\mathbf {V}_{jk} &= \sum _{i} \frac {\partial \phi }{\partial \mathbf {O}_{ik}} \cdot \frac {\partial \mathbf {O}_{ik}}{\partial \mathbf {V}_{jk}} = \sum _{i} d\mathbf {O}_{ik} \mathbf {P}_{ij} = \sum _{i} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} d\mathbf {O}_{ik} .\end {align*} \]

    That last line is worth noting already: \(d\mathbf {V}\) never needs \(\mathbf {P}\) stored, only the ability to re-evaluate \(\mathbf {P}_{ij}\) from \(\mathbf {Q}\), \(\mathbf {K}\), and \(\mathbf {L}\).

    \(d\mathbf {S}\) through the softmax

    • August 3, 2026
    • Kellen Kanarios

    Softmax acts row by row, so drop into the scalar case with \(\mathbf {s}\) and \(\mathbf {p}\) single rows. The softmax Jacobian is \(\partial \mathbf {p}_i / \partial \mathbf {s}_j = \mathbf {p}_i(\delta _{ij} - \mathbf {p}_j)\), giving

    \[ \begin {align*} d\mathbf {s}_j &= \sum _{i} d\mathbf {p}_i \cdot \frac {\partial \mathbf {p}_i}{\partial \mathbf {s}_j} \\ &= \sum _{i} d\mathbf {p}_i \cdot \mathbf {p}_i (\delta _{ij} - \mathbf {p}_{j}) \\ &= d\mathbf {p}_{j} \mathbf {p}_{j} - \mathbf {p}_{j}\sum _{i} d\mathbf {p}_{i} \mathbf {p}_{i} .\end {align*} \]

    As a row vector this is \(d\mathbf {s} = \mathbf {p} \odot (d\mathbf {p} - \mathbf {p} \cdot d\mathbf {p})\), where the subtracted term is the scalar \(\mathbf {p} \cdot d\mathbf {p}\) broadcast across the row. Collecting those scalars into a column \(\mathbf {D}\) with \(\mathbf {D}_i = \mathbf {P}_i \cdot d\mathbf {P}_i\) recovers the matrix form

    \[d\mathbf {S} = \mathbf {P} \odot (d\mathbf {P} - \mathbf {D}).\]

    \(\mathbf {D}\) is the piece that will cause trouble later: it is a dot product over an entire row of \(\mathbf {P}\), which is exactly the thing we refuse to materialize.

    \(d\mathbf {Q}\) and \(d\mathbf {K}\) from \(\mathbf {S} = \mathbf {Q}\mathbf {K}^T\)

    • August 3, 2026
    • Kellen Kanarios

    One more chain rule, and the sums run over opposite indices:

    \[ \begin {align*} d\mathbf {Q}_{i} &= \sum _{j} d\mathbf {S}_{ij} \mathbf {K}_{j} = \sum _{j} \mathbf {P}_{ij} \left (d\mathbf {P}_{ij} - \mathbf {D}_i\right ) \mathbf {K}_{j}, \\ d\mathbf {K}_{j} &= \sum _{i} d\mathbf {S}_{ij} \mathbf {Q}_{i} = \sum _{i} \mathbf {P}_{ij} \left (d\mathbf {P}_{ij} - \mathbf {D}_i\right ) \mathbf {Q}_{i} .\end {align*} \]

    Recomputing instead of storing

    • August 3, 2026
    • Kellen Kanarios

    Every gradient above is expressed through \(\mathbf {P}_{ij}\) and \(d\mathbf {P}_{ij}\), both \(N \times N\). Materializing either one is exactly the quadratic memory cost the forward pass went to such lengths to avoid, so the backward pass has to be able to produce those entries on demand.

    💡 Insight. Both are recoverable from the \(N \times d\) tensors already resident in memory. The forward pass saved \(\mathbf {L}\), so \[\mathbf {P}_{ij} = \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}},\] and \(d\mathbf {P}\) is just an inner product of two rows, \[d\mathbf {P}_{ij} = \sum _{k} d\mathbf {O}_{ik} \mathbf {V}_{jk} = d\mathbf {O}_{i} \cdot \mathbf {V}_j.\] Neither ever requires an \(N \times N\) intermediate.

    Substituting both into the previous section leaves \(d\mathbf {Q}\) and \(d\mathbf {K}\) in terms of \(\mathbf {Q}\), \(\mathbf {K}\), \(\mathbf {V}\), \(d\mathbf {O}\), \(\mathbf {L}\), and \(\mathbf {D}\) alone:

    \[ \begin {align*} d\mathbf {Q}_{i} &= \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \left (d\mathbf {O}_{i} \cdot \mathbf {V}_j - \mathbf {D}_i\right ) \mathbf {K}_{j}, \\ d\mathbf {K}_{j} &= \sum _{i} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \left (d\mathbf {O}_{i} \cdot \mathbf {V}_j - \mathbf {D}_i\right ) \mathbf {Q}_{i}. .\end {align*} \]

    Getting \(\mathbf {D}\) for free

    • August 3, 2026
    • Kellen Kanarios

    One problem survives. \(\mathbf {D}_i = \mathbf {P}_i \cdot d\mathbf {P}_i\) is a dot product over a full row, so computing it inside the streaming loop would mean a reduction over all \(j\) before any tile of \(d\mathbf {Q}_i\) could be finished. This is the same global dependency the online softmax was designed to break.

    The way out is that the row sum has already been computed once, in the forward pass. Expanding and pulling \(d\mathbf {O}_i\) out of the sum:

    \[ \begin {align*} \mathbf {D}_i &= \mathbf {P}_{i} \cdot d\mathbf {P}_{i} \\ &= \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} d\mathbf {P}_{ij} \\ &= \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \left (d\mathbf {O}_{i} \cdot \mathbf {V}_{j}\right ) \\ &= d\mathbf {O}_{i} \cdot \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \mathbf {V}_{j} \\ &= d\mathbf {O}_{i} \cdot \mathbf {O}_{i} .\end {align*} \]

    The inner sum is precisely the definition of \(\mathbf {O}_i\). So \(\mathbf {D}\) is a single elementwise product of \(d\mathbf {O}\) and \(\mathbf {O}\) summed along the head dimension — one \(O(Nd)\) pass over tensors we already have, done once before the backward loop begins.

    Summary

    • May 27, 2026
    • Kellen Kanarios

    Forward pass. Store \(\mathbf {O}\) and the softmax denominators \(\mathbf {L}\), both \(O(Nd)\).

    Between the passes. Receive \(d\mathbf {O}\) from the layer above (automatic in JAX), then precompute \(\mathbf {D}_i = d\mathbf {O}_i \cdot \mathbf {O}_i\) in \(O(N)\) memory.

    Backward pass. Stream over tiles, recomputing \(\mathbf {P}_{ij}\) from \(\mathbf {Q}, \mathbf {K}, \mathbf {L}\) and \(d\mathbf {P}_{ij}\) from \(d\mathbf {O}, \mathbf {V}\) as needed:

    1. \(d\mathbf {V}_j = \sum _i \mathbf {P}_{ij} d\mathbf {O}_i\), accumulated over query tiles.
    2. \(d\mathbf {Q}_i = \sum _j \mathbf {P}_{ij}(d\mathbf {O}_i \cdot \mathbf {V}_j - \mathbf {D}_i)\mathbf {K}_j\), accumulated over key tiles.
    3. \(d\mathbf {K}_j = \sum _i \mathbf {P}_{ij}(d\mathbf {O}_i \cdot \mathbf {V}_j - \mathbf {D}_i)\mathbf {Q}_i\), accumulated over query tiles.

    Each accumulator is \(O(d)\) per row or column, so the whole backward pass stays linear in \(N\).

    Implementing Directory-based MESI in Murphi [HHZO]

    • March 24, 2026
    • Kellen Kanarios

    Murphi is an explicit-state model checker: you describe a system as guarded transition rules, state the invariants, and it enumerates every reachable interleaving looking for a violation. That makes it a natural fit for cache coherence, where the steady-state behavior is easy and the races are not. This post builds a directory-based MESI protocol in Murphi, starting from MSI and adding state every time the checker finds a way to break it.

    The state tables come from A Primer on Memory Consistency and Cache Coherence, which doubles as the source for these notes. The recurring lesson is that the published tables are not quite enough: every protocol below needs transient states the tables leave implicit.

    Why three virtual channels

    • March 24, 2026
    • Kellen Kanarios

    The valid-invalid protocol shipped with the Murphi docs uses two Virtual Channels. A directory protocol needs three: one each for requests, forwarded requests, and responses. The reason is that deadlock is a cycle in the dependency graph, so it suffices to exhibit one.

    • A node issues GetS to the directory, giving an edge \(N_1 \to D\).
    • The directory forwards Fwd-GetS to the owner, extending the chain to \(N_1 \to D \to N_2\).
    • The owner sends data back to the requester, closing the cycle \(N_1 \to D \to N_2 \to N_1\).

    The data closing that cycle would travel on the same channel as the requests waiting behind it, so a full request buffer wedges the response that would drain it. Partitioning by message class breaks the cycle:

    • Request: GetS, GetM, PutS, PutM
    • Forwarded: Fwd-GetS, Fwd-GetM, Inv, PutAck
    • Response: Data, InvAck

    These are enumerated directly in the model's MessageType.

    msi.m
    MessageType: enum {
  GetS,           -- request for shared copy
  GetM,           -- request for modified (exclusive) copy
  PutS,           -- evict shared copy
  PutM,           -- evict modified copy (w/ data)

  FwdGetS,        -- forwarded GetS to owner
  FwdGetM,        -- forwarded GetM to owner
  Inv,            -- invalidation request

  Data,           -- data response
  InvAck,         -- invalidation acknowledgment
  PutAck          -- put acknowledgment
};

    Losing data to a PutM/Fwd-GetM race

    • August 3, 2026
    • Kellen Kanarios

    Consider the PutM rule that downgrades a cache from modified to invalid. The evicting cache must not drop the data when it sends PutM, because it may still have to service a forwarded request; it transitions to \(MI^A\) and keeps the value. But nothing stops the PutAck from arriving first, taking it to \(I\) before the Fwd-GetM shows up. The data is gone and the forwarded request has nobody to answer it.

    Fix. Add the \(M^D\) state to the directory controller. While in \(M^D\), a PutM from a node that is not the current owner stalls until the data arrives. Leaving \(M^D\) for \(M\) requires the new owner to send data back to the directory even on a three-hop transaction, so the directory learns that the forward actually completed. I have not found a cleaner way to close this race without the extra state.

    Deadlocking two stores against a load

    • August 3, 2026
    • Kellen Kanarios

    The \(M^D\) fix introduces a deadlock of its own. Take two processors that store-miss and a third that load-misses. The second store wins at the directory: the first store gets data and moves \(IM^{AD} \to IM^{A}\), then the second triggers a Fwd-GetM that takes ownership away from it.

    Meanwhile the load miss sits in \(IS^D\). When its Inv arrives, the table says to stall — and because Inv and Fwd-GetM share the forwarded channel, that stall blocks the Fwd-GetM behind it. The winning processor never receives the data, and nothing ever drains the channel.

    Fix. Another transient state absent from the table: \(II^A\), meaning "was in \(IS^A\), got invalidated, now waiting on PutAck before settling in \(I\)". The invalidation is processed rather than stalled, so the forwarded channel keeps moving.

    Not clearing the owner too eagerly

    • August 3, 2026
    • Kellen Kanarios

    One more correction to the table: when the home directory is in \(M\) and receives a GetS, it must not clear the owner field as the figure directs. Once in \(S^D\), the directory can no longer tell whether an incoming PutM came from the owner (and should stall) or from a stale node. The owner is only cleared once the data has actually arrived.

    Softmax acts row by row, so drop into the scalar case with \(\mathbf {s}\) and \(\mathbf {p}\) single rows. The softmax Jacobian is \(\partial \mathbf {p}_i / \partial \mathbf {s}_j = \mathbf {p}_i(\delta _{ij} - \mathbf {p}_j)\), giving

    \[ \begin {align*} d\mathbf {s}_j &= \sum _{i} d\mathbf {p}_i \cdot \frac {\partial \mathbf {p}_i}{\partial \mathbf {s}_j} \\ &= \sum _{i} d\mathbf {p}_i \cdot \mathbf {p}_i (\delta _{ij} - \mathbf {p}_{j}) \\ &= d\mathbf {p}_{j} \mathbf {p}_{j} - \mathbf {p}_{j}\sum _{i} d\mathbf {p}_{i} \mathbf {p}_{i} .\end {align*} \]

    As a row vector this is \(d\mathbf {s} = \mathbf {p} \odot (d\mathbf {p} - \mathbf {p} \cdot d\mathbf {p})\), where the subtracted term is the scalar \(\mathbf {p} \cdot d\mathbf {p}\) broadcast across the row. Collecting those scalars into a column \(\mathbf {D}\) with \(\mathbf {D}_i = \mathbf {P}_i \cdot d\mathbf {P}_i\) recovers the matrix form

    \[d\mathbf {S} = \mathbf {P} \odot (d\mathbf {P} - \mathbf {D}).\]

    \(\mathbf {D}\) is the piece that will cause trouble later: it is a dot product over an entire row of \(\mathbf {P}\), which is exactly the thing we refuse to materialize.

    \(d\mathbf {Q}\) and \(d\mathbf {K}\) from \(\mathbf {S} = \mathbf {Q}\mathbf {K}^T\)

    • August 3, 2026
    • Kellen Kanarios

    One more chain rule, and the sums run over opposite indices:

    \[ \begin {align*} d\mathbf {Q}_{i} &= \sum _{j} d\mathbf {S}_{ij} \mathbf {K}_{j} = \sum _{j} \mathbf {P}_{ij} \left (d\mathbf {P}_{ij} - \mathbf {D}_i\right ) \mathbf {K}_{j}, \\ d\mathbf {K}_{j} &= \sum _{i} d\mathbf {S}_{ij} \mathbf {Q}_{i} = \sum _{i} \mathbf {P}_{ij} \left (d\mathbf {P}_{ij} - \mathbf {D}_i\right ) \mathbf {Q}_{i} .\end {align*} \]

    Recomputing instead of storing

    • August 3, 2026
    • Kellen Kanarios

    Every gradient above is expressed through \(\mathbf {P}_{ij}\) and \(d\mathbf {P}_{ij}\), both \(N \times N\). Materializing either one is exactly the quadratic memory cost the forward pass went to such lengths to avoid, so the backward pass has to be able to produce those entries on demand.

    💡 Insight. Both are recoverable from the \(N \times d\) tensors already resident in memory. The forward pass saved \(\mathbf {L}\), so \[\mathbf {P}_{ij} = \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}},\] and \(d\mathbf {P}\) is just an inner product of two rows, \[d\mathbf {P}_{ij} = \sum _{k} d\mathbf {O}_{ik} \mathbf {V}_{jk} = d\mathbf {O}_{i} \cdot \mathbf {V}_j.\] Neither ever requires an \(N \times N\) intermediate.

    Substituting both into the previous section leaves \(d\mathbf {Q}\) and \(d\mathbf {K}\) in terms of \(\mathbf {Q}\), \(\mathbf {K}\), \(\mathbf {V}\), \(d\mathbf {O}\), \(\mathbf {L}\), and \(\mathbf {D}\) alone:

    \[ \begin {align*} d\mathbf {Q}_{i} &= \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \left (d\mathbf {O}_{i} \cdot \mathbf {V}_j - \mathbf {D}_i\right ) \mathbf {K}_{j}, \\ d\mathbf {K}_{j} &= \sum _{i} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \left (d\mathbf {O}_{i} \cdot \mathbf {V}_j - \mathbf {D}_i\right ) \mathbf {Q}_{i}. .\end {align*} \]

    Getting \(\mathbf {D}\) for free

    • August 3, 2026
    • Kellen Kanarios

    One problem survives. \(\mathbf {D}_i = \mathbf {P}_i \cdot d\mathbf {P}_i\) is a dot product over a full row, so computing it inside the streaming loop would mean a reduction over all \(j\) before any tile of \(d\mathbf {Q}_i\) could be finished. This is the same global dependency the online softmax was designed to break.

    The way out is that the row sum has already been computed once, in the forward pass. Expanding and pulling \(d\mathbf {O}_i\) out of the sum:

    \[ \begin {align*} \mathbf {D}_i &= \mathbf {P}_{i} \cdot d\mathbf {P}_{i} \\ &= \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} d\mathbf {P}_{ij} \\ &= \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \left (d\mathbf {O}_{i} \cdot \mathbf {V}_{j}\right ) \\ &= d\mathbf {O}_{i} \cdot \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \mathbf {V}_{j} \\ &= d\mathbf {O}_{i} \cdot \mathbf {O}_{i} .\end {align*} \]

    The inner sum is precisely the definition of \(\mathbf {O}_i\). So \(\mathbf {D}\) is a single elementwise product of \(d\mathbf {O}\) and \(\mathbf {O}\) summed along the head dimension — one \(O(Nd)\) pass over tensors we already have, done once before the backward loop begins.

    POTW: Multi-Level Discovery of Deep Options [ZUAG]

    • July 22, 2026
    • Kellen Kanarios

    The setup for Multi-Level Discovery of Deep Options:

    • We have a meta-controller that outputs the skill \(z\) given the state \(s\) i.e. \(z_t \sim \eta (\cdot \mid s_t)\)
    • We have the skill, which is a skill-conditioned policy \(a_t \sim \pi (\cdot \mid s_t, z_t)\)
    • We have the termination function \(\psi (\cdot \mid s_t, z_{t - 1})\), which is per skill and evaluates the previous skill \(z_{t - 1}\) at the new state \(s_t\), such that \(b_t \sim \mathrm {Ber}\big (\psi (s_t, z_{t - 1})\big ) \in \{0, 1\} \)
      • For \(b_t = 1\), we resample a new skill \(z_t \sim \eta (\cdot \mid s_t)\)
      • Otherwise, \(z_{t} = z_{t - 1}\)

    Assuming there is a true underlying latent history \(\xi = \{b_{0}, z_{0}, b_{1}, z_{1}, \ldots \} \) and the observable history \(\mathcal {H} = \{s_{0}, a_{0}, s_{1}, a_{1}, \ldots \} \), the likelihood according to the above generative model is given by

    \[\mathbb {P}(\mathcal {H}, \xi ) = p(s_{0})\delta _{\{b_{0} = 1\}}\eta (z_{0} \mid s_{0}) \prod _{t=1}^{T - 1} \mathbb {P}(b_t, z_t \mid z_{t - 1}, s_t) \prod _{t = 0}^{T - 1} \pi (a_t \mid s_t, z_t) p(s_{t+1} \mid s_t, a_t)\]

    Furthermore, according to our model, we have that

    \[ \begin {align*} \mathbb {P}(b_t = 0, z_t \mid z_{t - 1}, s_t) &= (1 - \psi (s_t, z_{t - 1})) \cdot \delta _{\{z_{t} = z_{t - 1}\}} \\ \mathbb {P}(b_t = 1, z_t \mid z_{t - 1}, s_t) &= \psi (s_t, z_{t - 1}) \cdot \eta (z_t \mid s_t) .\end {align*} \]

    Up to this point, we have assumed this is the ground truth model and we are given each of the components. Instead we want to learn these components. To do so, we introduce our set of parameters \(\mathbf {\theta } \), such that each component is parametrized by a subset of \(\mathbf {\theta } \) i.e. \(\eta _{\theta }, \pi _{\theta }, \psi _{\theta }\).

    Goal. We want to learn some \(\theta \) that maximized the likelihood of the observable data.

    To do so, first consider the log-likelihood of our new parametrized model

    \[ \begin {align*} \log \mathbb {P}_{\theta }(\mathcal {H}, \xi ) &= \log \left [p(s_{0})\delta _{\{b_{0} = 1\}}\eta _{\theta }(z_{0} \mid s_{0}) \prod _{t=1}^{T - 1} \mathbb {P}_{\theta }(b_t, z_t \mid z_{t - 1}, s_t) \prod _{t = 0}^{T - 1} \pi _{\theta }(a_t \mid s_t, z_t) p(s_{t+1} \mid s_t, a_t)\right ] \\ &= \log p(s_{0})\delta _{\{b_{0} = 1\}} + \log \left [\eta _{\theta }(z_{0} \mid s_{0}) \prod _{t=1}^{T - 1} \mathbb {P}_{\theta }(b_t, z_t \mid z_{t - 1}, s_t) \prod _{t = 0}^{T - 1} \pi _{\theta }(a_t \mid s_t, z_t) \right ] + \sum _{t=0}^{T-1} \log \left [p(s_{t+1} \mid s_t, a_t)\right ] \\ &= \underbrace {\log p(s_{0})\delta _{\{b_{0} = 1\}} + \sum _{t=0}^{T-1} \log \left [p(s_{t+1} \mid s_t, a_t)\right ]}_{\text {independent of } \theta } + \log \left [\eta _{\theta }(z_{0} \mid s_{0}) \prod _{t=1}^{T - 1} \mathbb {P}_{\theta }(b_t, z_t \mid z_{t - 1}, s_t) \prod _{t = 0}^{T - 1} \pi _{\theta }(a_t \mid s_t, z_t)\right ] .\end {align*} \]

    Since we are only concerned with learning \(\theta \), we can disregard the \(\theta \) independent terms leaving

    \[\begin {align*} \nabla _{\theta } \log \mathbb {P}_{\theta }(\mathcal {H}, \xi ) &= \nabla _{\theta } \left [ \log \left [\eta _{\theta }(z_{0} \mid s_{0}) \prod _{t=1}^{T - 1} \mathbb {P}_{\theta }(b_t, z_t \mid z_{t - 1}, s_t) \prod _{t = 0}^{T - 1} \pi _{\theta }(a_t \mid s_t, z_t)\right ] \right ]\\ &= \nabla _{\theta } \log \left [\eta _{\theta }(z_{0} \mid s_{0})\right ] + \sum _{t=1}^{T - 1} \nabla _{\theta } \log \left [\mathbb {P}_{\theta }(b_t, z_t \mid z_{t - 1}, s_t)\right ] + \sum _{t = 0}^{T - 1} \nabla _{\theta } \log \left [\pi _{\theta }(a_t \mid s_t, z_t)\right ]. \end {align*}\]
    Problem. This requires samples \((\mathcal {H}, \xi ) \sim P_{\theta }(\mathcal {H}, \xi )\), but we only have samples \(\mathcal {H} \sim P_{\theta }(\mathcal {H})\)!!!
    Solution. We can use the trick from Expectation Maximization. Referred to in the paper as the expectation gradient trick. Namely, \[\nabla _{\theta } \log P_{\theta }(\mathcal {H}) = \mathbb {E}_{\xi \sim P_{\theta }(\xi \mid \mathcal {H})} \left [ \nabla _{\theta } \log P_{\theta }(\mathcal {H}, \xi ) \right ]\]

    Now it remains to compute the expectation from \(P_{\theta }(\xi \mid \mathcal {H})\)

    Remark. Note that \(P_{\theta }(\xi \mid \mathcal {H})\) is a distribution over \((K, \{0,1\})^{T} \) i.e. over each \((z_t, b_t)\). To efficiently compute, we need to use Forward-backward algorithm.

    Computing the expectation

    • July 22, 2026
    • Kellen Kanarios

    For,

    \[\begin {aligned} u_t(z) &= \mathbb {P}_{\theta }(z_t = z | \xi ) \\ v_t(z) &= \mathbb {P}_{\theta }(b_t = 1, z_t = z | \xi ) \\ w_t(z) &= \mathbb {P}_{\theta }(z_t = z, b_{t+1} = 0 | \xi ). \end {aligned}\]

    We have that

    \[\nabla _{\theta } L[\theta ; \xi ] = \sum _{h \in \mathcal {H}} \left ( \sum _{t=0}^{T-1} \left ( v_t(z) \nabla _{\theta } \log \eta (z|s_t) + u_t(z) \nabla _{\theta } \log \pi _h(a_t|s_t) \right ) + \sum _{t=0}^{T-2} \left ( (u_t(z) - w_t(z)) \nabla _{\theta } \log \psi _h(s_{t+1}) + w_t(z) \nabla _{\theta } \log (1 - \psi _h(s_{t+1})) \right ) \right ).\]

    Following the Forward-backward algorithm, we can get the posterior for the latent i.e. \(\mathbb {P}((z_{t}, b_{t}) \mid \mathcal {H})\). We have the corresponding forward and backward components

    \[\begin {align*} \phi _t(z, b) &= \mathbb {P}(s_{0}, a_{0}, \ldots , s_{t}, z_{t} = z, b_{t} = b) \\ \beta _t(z, b) &= \mathbb {P}(s_{t + 1}, a_{t + 1}, \ldots , s_{T} \mid z_{t} = z, b_{t} = b), .\end {align*}\]

    which can then be written as

    \[\begin {align*} \phi _t(z, b) &= \mathbb {P}(s_t, a_t \mid z, b) \sum _{(z', b')} \phi _{t - 1}(z', b') \mathbb {P}(z, b \mid z', b') \\ \beta _t(z, b) &= \sum _{(z', b')} \beta _{t + 1}(z', b') \mathbb {P}(s_{t + 1}, a_{t + 1} \mid z', b') \mathbb {P}(z', b' \mid z, b) .\end {align*}\]

    Forward pass. For the forward pass, we have the initial condition

    \[\phi _0(z, b) = p_{0}(s_{0}) \delta _{\{b = 1\}} \eta (z \mid s_{0})\]

    Here \((z', b')\) ranges over the possible values of \((z_{t - 1}, b_{t - 1})\). It is sufficient to expand the remaining two terms in terms of our generative model as defined above. First, note that \((z_{t}, b_{t})\) are independent of \(b_{t - 1}\). Therefore, we can drop the \(b_{t - 1}\) term and are left with the following two cases:

    \[\begin {align*} \mathbb {P}_{\theta }(z, b = 0 \mid z') &= \delta _{\{z = z'\}} (1 - \psi _{\theta }(s_{t}, z')) \\ \mathbb {P}_{\theta }(z, b = 1 \mid z') &= \eta _{\theta }(z \mid s_{t}) \psi _{\theta }(s_{t}, z') .\end {align*}\]

    Plugging this in, we now have

    \[\begin {align*} \phi _t(z, b) = \mathbb {P}_{\theta }(s_t, a_t \mid z, b) \sum _{(z', b')} \phi _{t - 1}(z', b') \Big (&\eta _{\theta }(z \mid s_{t}) \psi _{\theta }(s_{t}, z') \\ &+ \delta _{\{z = z'\}} (1 - \psi _{\theta }(s_{t}, z'))\Big ) .\end {align*}\]

    It remains to find \(\mathbb {P}_{\theta }(s_t, a_t \mid z, b)\). Once again, given \(z_t\) we no longer care about \(b_t\). Therefore, this becomes

    \[\begin {align*} \mathbb {P}_{\theta }(s_t, a_t \mid z) &= \pi _{\theta }(a_t \mid s_t, z) p(s_t \mid s_{t - 1}, a_{t - 1}) .\end {align*}\]

    This gives us our final expression

    \[\begin {align*} \phi _t(z, b) = &\pi _{\theta }(a_t \mid s_t, z) p(s_t \mid s_{t - 1}, a_{t - 1}) \\ &\times \sum _{(z', b')} \phi _{t - 1}(z', b') \Big (\eta _{\theta }(z \mid s_{t}) \psi _{\theta }(s_{t}, z') + \delta _{\{z = z'\}} (1 - \psi _{\theta }(s_{t}, z'))\Big ) .\end {align*}\]
    Remark. We have abused notation here, allowing \(\mathbb {P}(s_t, a_t \mid z_t, b_t)\) to depend on \(s_{t - 1}, a_{t - 1}\), etc. This is to align with the notation from Forward-backward algorithm. It makes no difference in practice as long as the backward dependence is finite / bounded. However, in practice you would want the history dependence to be small and here it is only one-step.

    Backward pass. For the backward pass, we define the end term as

    \[\beta _{T-1}(z, b) = \pi (a_{T - 1} \mid z, s_{T - 1}) p(s_{T} \mid s_{T - 1}, a_{T - 1})\]

    Here \((z', b')\) ranges over the possible values of \((z_{t + 1}, b_{t + 1})\). The other terms are analagous i.e.

    \[\begin {align*} \mathbb {P}_{\theta }(z', b' = 0 \mid z) &= \delta _{\{z' = z\}} (1 - \psi _{\theta }(s_{t + 1}, z)) \\ \mathbb {P}_{\theta }(z', b' = 1 \mid z) &= \eta _{\theta }(z' \mid s_{t + 1}) \psi _{\theta }(s_{t + 1}, z) .\end {align*}\]

    and

    \[\begin {align*} \mathbb {P}_{\theta }(s_{t + 1}, a_{t + 1} \mid z') &= \pi _{\theta }(a_{t + 1} \mid s_{t + 1}, z') p(s_{t + 1} \mid s_t, a_t) .\end {align*}\]

    POTW: Learning Options via Compression [G27U]

    The setup for Learning Options via Compression.

    • A state abstraction posterior \(q_{\theta }(s_{t} \mid z_{t}, x_{t})\) and decoder \(p_{\theta }(a_{t} \mid s_{t})\), where \(\pi _{\theta }(a_t \mid s_t, x_t) = \mathbb {E}_{q_{\theta }(s_{t} \mid x_{t}, z_{t})}[p_{\theta }(a_t \mid s_t)]\)
      • This seems to be needed to ensure that the decoder cannot overfit to the offline data?
    • A termination network \(\beta _{\theta }(b_t \mid x_{1}, \ldots , x_{t})\)
    • A skill posterior \(\eta _{\theta }(z_{t} \mid z_{t - 1}, b_{t}, x_{1:T},a_{1:T})\).

    Unlike in DDO, where they do exact posterior inference, here we do variational inference. Namely, they directly try to model the posterior via the neural network \(\eta _{\theta }(z_{t} \mid z_{t - 1}, b_{t}, x_{1:T},a_{1:T})\). This has a few consequences:

    • The expectation gradient is now true Expectation Maximization. In particular, we need to optimize the ELBO.

    The ELBO of LOVE can be written as

    \[\begin {align*} \mathcal {L}_{\text {ELBO}}(\theta ) \approx \sum _{t=1}^{T} \log &p_{\theta }(\mathbf {a}_{t} \mid \mathbf {s}_{t}) + D_{\text {KL}}(q_{\theta }(m_{t} \mid \mathbf {x}_{1:t}) \parallel p_{\theta }(m_{t} \mid \mathbf {s}_{t})) \\ &+ D_{\text {KL}}(q_{\theta }(z_{t} \mid m_{t}, \mathbf {x}_{1:T}, \mathbf {a}_{1:T}) \parallel p(z_{t})) + D_{\text {KL}}(q_{\theta }(s_{t} \mid z_{t}, \mathbf {x}_{t}) \parallel p_{\theta }(s_{t} \mid s_{t-1}, m_{t-1})) .\end {align*}\]

    Notably this requires a few additional prior networks for the KL regularization term in the ELBO.

    • A boundary prior \(\beta (b_t \mid s_{t})\).
    • A skill prior \(p(z)\).
    • A state abstraction transition prior \(p(s_t | s_{t-1}, z_t)\).

    Additionally, we also need to sample the \(z\)'s. This is done via Gumbel softmax and causes much higher variance.

    Frankenstein-ing LOVE and DDO

    • July 23, 2026
    • Kellen Kanarios

    We find ourselves in-between LOVE and DDO. In particular, in DDO, they are concerned with learning a hierarchy of policies where the higher-level meta policy \(\eta \) must be usable online only given the current state.

    • (+) The learned termination conditions \(\beta \) are dependent on the active skill.
    • (+) Exact inference \(\implies \) lower variance.
    • (-) Weak skill model \(\eta (z \mid s)\).
    • (-) No explicit encouragement for temporally-extended skills.

    On the contrary, in LOVE, they treat skills as a pure sequence-modeling problem. The posterior \(q_{\theta }(z_{t} \mid z_{t - 1}, b_{t}, x_{0}, \ldots , x_{T})\) is purely used to label offline trajectories and give the skills meaning. To make them usable online, it is then required to learn an additional hierarchical policy over these skills.

    • (+) The skill-labeler is allowed to use not only the current state but also the future visited states.
    • (+) Compression objective encourages temporally extended skills.
    • (-) Design inherently does not allow the terminations to be skill-dependent.
    • (-) Need to sample \(z\)'s to compute gradients \(\implies \) higher-variance.

    Our graphical model. We try to combine the desirable properties.

    We essentially combine the insight of LOVE where instead of trying to model the full joint distribution i.e. \(\mathbb {P}(\mathcal {H}, \xi )\) we instead model \(\mathbb {P}(\mathcal {A}, \xi \mid \mathcal {S})\), where we treat the entire state history as known.

    In the language of HMMs, the emission probabilities only correspond to the actions. Therefore, we can perform the Forward-backward algorithm and condition on whatever component of the state we want without breaking the exactness.

    Remark. This is only a good idea for us because we do not need to use the meta controller during evaluation.

    Deliberation cost. In LOVE, they encourage temporal extension through the compression loss. This requires an empirical approximation of the skillmarginal \(p(z)\). For me, this caused the skill entropy to just collapse to zero instead of encouraging temporally extended options. Instead, we use a deliberation cost more common in the options literature The Option-Critic Architecture, where we just add the switch-rate as an additional loss term.

    • We are given the posterior \(\mathbb {P}(z_t = z, b_t = 1 \mid \mathcal {H})\). In our implementation this would be \((B, T, K)\)
    • We marginalize over skills \(z\) by summing to get \(\mathbb {P}(b_t = 1 \mid \mathcal {H})\)
    • Then average over batch \(B\) and time \(T\) to get expected reads.

    As in LOVE, we need to balance minimizing log-likelihood with compression / switching cost. To do so, we do dual descent.

    • First, without compression, we run the algorithm and observe what is approximately the best attainable log-likelihood loss is.
    • Then, we minimize the deliberation cost subject to \(\mathcal {L}_{\text {likelihood}} \leq C + \epsilon \)

    Planning over learned skills

    • July 23, 2026
    • Kellen Kanarios

    Setup. Assume we are given a set of skills \(\mathbf {z} \in \{0, \ldots , K\}\) along with a skill-conditioned lower-level policy \(\pi (s \mid z)\). Then what we want is to be able to learn the optimal goal-reaching policy over these skills. To do so, we must go beyond traditional offline skill-learning algorithms. We must Learn a value function over learned skills purely from offline data

    Skill-conditioned GCIQL. If we now define the analagous skill-conditioned GCIQL losses, we have \[\begin {align} \mathcal {L}_{V}(\theta _{V}) &= \mathbb {E}_{(s_{t}, z_{t}, g) \sim \mathcal {D}} \Big [L_{2}^{\tau }\big (Q_{\overline {\theta }_{Q}}(s_{t},z_{t},g) - V_{\theta _{V}}(s_{t},g)\big )\Big ] \\ \mathcal {L}_{Q}(\theta _{Q}) &= \mathbb {E}_{(s_{t}, z_{t}, s_{t+\kappa }) \sim \mathcal {D}} \Big [\big (r(s_{t}, z_{t}, g) + \gamma V_{\overline {\theta }_{V}}(s_{t+\kappa }, g) - Q_{\theta _{Q}}(s_{t},z_{t},g) \big )^2\Big ] \end {align}\] This introduces a few changes and constraints on the final algorithm.

    • \(\kappa \) is a random variable dependent on the termination condition of \(z\).
    • It is not immediately obvious how we should design \(r(s_t, z_t, g)\).
    Future states. For the first point, there are two options with trade-offs. In LOVE, they learn a model over trajectories that partitions them into unique skills. We can directly use this to get the intermediate \(s_{t + \kappa }\) just based off the termination output by the model.
    • This is the simplest approach and basically a generalization of HIQL to varying length skills, where they just use a state \(k\) steps away in the trajectory.
    • However, this approach would be limited on stitching datasets, where all of the trajectories are short.

    The second approach, assuming we already have skills (given termination function), to perform better in the stitching setting is instead to learn a generative model over the state \(s_{t+\kappa }\). Then we could just use \(s_{t + \kappa } \sim p(s_{t+\kappa } \mid s_t, z_t)\) as our next state. There is new work on universal horizon models[chungOfflineReinforcementLearning2026] focused on this for \(n\)-step models. Alternatively, it seems there is work directly learning the value function for a sequence of skills [farebrotherCompositionalPlanningJumpy2026], but this seems to only work for a fixed (per skill) discount factor.

    Reward. Here, I propose a modified reward function based on the observation that goal-conditioned policies work well for short-horizon goal-reaching. One of our skills is hardcoded to instead be a learned goal-conditioned policy \(\pi (a \mid s, g)\) with associated value function \(V(s, g)\). Denote this skill as \(z_g\). Then we can define the reward function as

    \[\begin {align*} r(s, z, g) &= \begin {cases} 1, & \text {if } z = z_g \text { and } V(s, g) < \epsilon \\ 0, & \text {otherwise} \end {cases} .\end {align*} \]

    Note that it may be the case that the high-level policy learns to just choose \(z_g\) everytime, so we may want to penalize that decision somehow for \((s,g)\) pairs with large \(V(s,g)\). Intuitively, this would end up with a higher-level policy that best utilizes the temporally-extended skills to reach the nearby region of \(g\) then concedes to the lower-level policy.

    Outstanding Problems / Future directions

    • July 23, 2026
    • Kellen Kanarios

    Extending beyond pointmaze in locomotion. The main issue faced here is that our discriminator is too powerful in high dimensional state space. Namely, we score options based on their ability to reconstruct actions i.e. if \(\mathbb {P}(a_t \mid s_t, z_t = z)\) is high then we further increase the probability of selecting that option \(z\). In higher-dimensional state spaces, the skill network \(\pi _{\theta }(a_t \cdot \mid s_t, z)\) is powerful enough to reconstruct \(a_t\) purely from \(s_t\) without using \(z\). This basically provides no signal for which \(z\) to use, and we end up just selecting \(z\) uniformly every time step.

    • I have seen a little sign of life from trying \(\pi (a \mid f_{\theta }(s), z)\) i.e. compressing \(s\) to a lower dimensional representation.
    • It may also be worth trying a really small network. Right now \((256, 256)\) already gets very low reconstruction loss, so maybe we can go smaller?

    Conquering manipulation. In OGBench: Benchmarking Offline Goal-Conditioned RL, they provide a suite of manipulation environments in addition to the standard locomotion.     Stack vs. Heap [0025]

    • December 28, 2024
    • Kellen Kanarios

    I often hear this question come up amongst performance-driven developers, and for the longest time I could never get a straight answer as to why the stack was so much better?     Why stack is faster.

    • December 28, 2024
    • Kellen Kanarios
     This all comes down to what happens during each memory allocation. Prior to actually running the program, the operating system allocates some amount of memory for both the stack and the heap (I think around 2-4MB?). When you allocate memory on the stack i.e. int x = 1;
    • Stack just increments stack pointer.
    • Writes value to new address pointed to by stack pointer.
    When you allocate memory on the heap i.e. int *x = malloc(sizeof(int)), we must instead choose how best to fulfill the request, which is a whole research direction in itself.
    • One such implementation is the buddy algorithm
    However, malloc itself is not a system call and therefore is not terribly slow. A real issue occurs when we run out of pre-allocated heap memory. This requires invoking a system call like sbrk to increment the size of the allocated memory for the heap.
    • If no available pages, OS must evict and write to disk...
    • Formally, this is known as "heap growth".
    Generally, if you know how much memory you need it is good practice to just allocated all up front to minimize any potential system calls. With this, the performance difference is not too drastic :)

    Online Softmax [PI7N]

    • May 20, 2026
    • Kellen Kanarios

    This covers the math behind the online softmax algorithm required by Flash Attention (v1).

    Safe softmax

    • May 20, 2026
    • Kellen Kanarios

    The first thing we must consider is numerical precision. Namely, the original softmax operation is given by

    \[\mathrm {softmax}(\mathbf {x}) = \frac {\exp (\mathbf {x})}{\sum _{i=1}^n \exp (\mathbf {x}_i)}\]

    However, when operating with low precision data types (i.e. float16) the maximum value is \(65536\). Therefore, with \(\exp \) we can easily get numerically overflow.

    To get around this, the online softmax algorithm adheres to the safe softmax. For safe softmax, we simply multiply the numerator and denominator by \(\exp (-m)\), where \(m = \max \{x_{1}, \ldots , x_n\}\). This gives

    \[\mathrm {softmax}(\mathbf {x}) = \frac {\exp (\mathbf {x} - m)}{\sum _{i=1}^n \exp (\mathbf {x}_i - m)}\]

    Since \(x_i - m \leq 0\), this ensures that each \(\exp (x_i - m)\) is bounded in a safe range.

    Problem. Note that computing the \(\max \) over \(\mathbf {x}\) means that we must have all of the logits in a row of \(QK^T\) materialized in SMEM, or first loop over all of them to compute the max before computing the normalization constant.

    Fusing the max and normalization

    • May 20, 2026
    • Kellen Kanarios

    The online softmax algorithm fuses the max reduction into the normalization pass, so a single sweep over the row suffices to compute the normalization with the max. The key difficulty is that the denominator depends on \(n\) for each \(i\) i.e.

    \[d = \sum _{i=1}^{n} \exp (x_i - m_n)\]

    Therefore, we must find a recursive relationship such that \(d_{i+1} = f(d_i, m_i, x_{i+1})\) for some function \(f\). This would then allow us to locally compute \(d_{i+1}\) with only the local information of current \(x_{i+1}\) and the two running statistics \(d_i\) and \(m_i\). This is exactly the kind of algorithm that is conducive to memory tiling.

    Question. What is \(f(d_i, m_i, x_{i+1})\)?
    Answer. Consider \(d_{i+1} = d_i \cdot \exp (m_{i} - m_{i + 1}) + \exp (x_{i + 1} - m_{i + 1})\).
    Proof. This can be seen by directly rewriting \(d_{i + 1}\). \[ \begin {align*} d_{i + 1} &= \sum _{j = 1}^{i+1} \exp (x_j - m_{i + 1}) \\ &= \left (\sum _{j = 1}^{i} \exp (x_j - m_{i+1})\right ) + \exp (x_{i+1} - m_{i+1}) \\ &= \left (\sum _{j = 1}^{i} \exp (x_j - m_{i})\right )\exp (m_{i} - m_{i + 1}) + \exp (x_{i+1} - m_{i+1}) \\ &= d_{i} \exp (m_{i} - m_{i + 1}) + \exp (x_{i+1} - m_{i+1}) \end {align*} \]

    The running denominator \(d\) is rescaled by \(e^{m - m_{\text {new}}}\) each time a new maximum is found, keeping it consistent with the safe-softmax shift.

    online_softmax.py
    m = float("-inf")                    # running max of the logits
d = 0.0                              # running softmax denominator
for i in range(n):                   # one fused sweep for the stats
    m_new = max(m, x[i])
    d = d * exp(m - m_new) + exp(x[i] - m_new)
    m = m_new
p = [exp(x[i] - m) / d for i in range(n)]   # second pass: normalized probs
    Remark. Unfortunately, we cannot get around the second pass to compute the normalized output for \(\mathbf {p}\). However, this is not the case in Flash Attention (v1).

    Flash Attention (Fwd) [OGCS0]

    • May 27, 2026
    • Kellen Kanarios

    Unlike in the online softmax, we are not interested in the outputted probability vector \(\mathbf {p}\). Instead we are interested in the entire output matrix \(O\) given by

    \[O = \mathrm {softmax}(QK^T) V\]

    For more details see self-attention.

    Notation. In correspondence with the notation in the online softmax, we define the following: \[x_{i,j} = \mathbf {q}_i \cdot \mathbf {k}_j,\] where \(\mathbf {q}_i\) is the \(i\)th row of \(Q\) and \(\mathbf {k}_j\) is the \(j\)th row of \(K\). Similarly, \(\mathbf {o}_i\) is the \(i\)th row of the output matrix \(O\) given by \[\mathbf {o}_i = \sum _{j = 1}^{n} \frac {\exp (x_{i,j} - m_n)}{d_n} \cdot \mathbf {v}_j \]

    Now following the template provided by the online softmax, we must find a recurrence for \(\mathbf {o}_i\). Namely, we will consider the sequence \(\mathbf {o}_{i,k}'\) given by \[\mathbf {o}_{i,k}' = \sum _{j = 1}^{k} \frac {\exp (x_{i,j} - m_k)}{d_k} \cdot \mathbf {v}_j, \] such that \(\mathbf {o}_{i,n}' = \mathbf {o}_n\)

    Claim. We have the following recurrence for \(\mathbf {o}_{i,k}'\): \[ \mathbf {o}_{i,k}' = \mathbf {o}_{i, k-1} \cdot \frac {d_{k - 1} \cdot \exp (m_{k-1} - m_{k})}{d_k} + \frac {\exp (x_{i,j} - m_k)}{d_k} \cdot \mathbf {v}_k \]
    Proof. We will proceed by directly rewriting the recurrence for \(\mathbf {o}_{i,k}'\) as \[ \begin {align*} \mathbf {o}_{i,k}' &= \sum _{j = 1}^{k} \frac {\exp (x_{i,j} - m_k)}{d_k} \cdot \mathbf {v}_j \\ &= \left (\sum _{j = 1}^{k - 1} \frac {\exp (x_{i,j} - m_{k-1})}{d_{k-1}} \cdot \mathbf {v}_j\right ) \frac {d_{k - 1} \cdot \exp (m_{k-1} - m_{k})}{d_k} + \frac {\exp (x_{i,k} - m_k)}{d_k} \cdot \mathbf {v}_k \\ &= \mathbf {o}_{i, k-1} \cdot \frac {d_{k - 1} \cdot \exp (m_{k-1} - m_{k})}{d_k} + \frac {\exp (x_{i,k} - m_k)}{d_k} \cdot \mathbf {v}_k .\end {align*} \]

    Thus, we are left with the following algorithm

    flash_attention.py
    for i in range(N):                      # one query row at a time
    m = float("-inf")                    # running max of the logits
    d = 0.0                              # running softmax denominator
    o = zeros(head_dim)                  # running output accumulator
    for j in range(M):                   # stream over keys/values
        x = q[i] @ k[j]                  # logit x_{i,j}
        m_new = max(m, x)
        d_new = d * exp(m - m_new) + exp(x - m_new)
        o = o * (d * exp(m - m_new) / d_new) + (exp(x - m_new) / d_new) * v[j]
        m, d = m_new, d_new
    out[i] = o
    Remark. A key benefit of this algorithm is that it is entirely parallelizable across rows. This means that we can loop across entire tiles like in the GEMM case.

    Flash Attention (Bwd) [OGCRZ]

    • May 27, 2026
    • Kellen Kanarios

    The forward pass of flash attention avoids materializing the \(N \times N\) attention matrix by streaming an online softmax. The backward pass has to pull the same trick twice over, because the naive gradient computation wants two \(N \times N\) matrices — \(\mathbf {P}\) and \(d\mathbf {P}\). Getting there means first writing down every gradient we need, then finding a way to recompute rather than store each one.

    Notation. Following the notation in the original paper, \[\mathbf {S} = \mathbf {Q} \mathbf {K}^T, \quad \mathbf {P} = \mathrm {softmax}(\mathbf {S}), \quad \mathbf {O} = \mathbf {P} \mathbf {V},\] where \(\mathbf {Q}, \mathbf {K}, \mathbf {V}, \mathbf {O}\) are \(N \times d\) and \(\mathbf {S}, \mathbf {P}\) are \(N \times N\). For a scalar loss \(\phi \) we abbreviate the gradient with respect to any matrix \(\mathbf {X}\) as \[d\mathbf {X} = \frac {\partial \phi }{\partial \mathbf {X}},\] and write \(\mathbf {L}_i\) for the softmax denominator of row \(i\) saved by the forward pass, so that \(\mathbf {P}_{ij} = \exp (\mathbf {Q}_i \cdot \mathbf {K}_j) / \mathbf {L}_i\).

    The gradients we need for FlashAttention [4QZE]

    • August 3, 2026
    • Kellen Kanarios

    Everything downstream is chain rule; the only step with any content is differentiating through the softmax. We take the gradients in dependency order, starting from \(d\mathbf {O}\) which arrives from the layer above.

    \(d\mathbf {P}\) and \(d\mathbf {V}\) from \(\mathbf {O} = \mathbf {P}\mathbf {V}\)

    • August 3, 2026
    • Kellen Kanarios

    Both fall straight out of the product rule for matrices:

    \[ d\mathbf {P} = \frac {\partial \phi }{\partial \mathbf {O}} \frac {\partial \mathbf {O}}{\partial \mathbf {P}} = d\mathbf {O} \mathbf {V}^T, \qquad d\mathbf {V} = \frac {\partial \phi }{\partial \mathbf {O}} \frac {\partial \mathbf {O}}{\partial \mathbf {V}} = \mathbf {P}^T d\mathbf {O}. \]

    The shapes are a useful sanity check. \(d\mathbf {O}\) has one entry per output, so it is \(N \times d\); \(\mathbf {V}^T\) is \(d \times N\); their product is \(N \times N\), matching \(\mathbf {P}\). Likewise \(\mathbf {P}^T d\mathbf {O}\) is \(N \times d\), matching \(\mathbf {V}\).

    Componentwise, from \(\mathbf {O}_{ik} = \sum _j \mathbf {P}_{ij} \mathbf {V}_{jk}\),

    \[ \begin {align*} d\mathbf {P}_{ij} &= \sum _{k} \frac {\partial \phi }{\partial \mathbf {O}_{ik}} \cdot \frac {\partial \mathbf {O}_{ik}}{\partial \mathbf {P}_{ij}} = \sum _{k} d\mathbf {O}_{ik} \mathbf {V}_{jk}, \\ d\mathbf {V}_{jk} &= \sum _{i} \frac {\partial \phi }{\partial \mathbf {O}_{ik}} \cdot \frac {\partial \mathbf {O}_{ik}}{\partial \mathbf {V}_{jk}} = \sum _{i} d\mathbf {O}_{ik} \mathbf {P}_{ij} = \sum _{i} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} d\mathbf {O}_{ik} .\end {align*} \]

    That last line is worth noting already: \(d\mathbf {V}\) never needs \(\mathbf {P}\) stored, only the ability to re-evaluate \(\mathbf {P}_{ij}\) from \(\mathbf {Q}\), \(\mathbf {K}\), and \(\mathbf {L}\).

    \(d\mathbf {S}\) through the softmax

    • August 3, 2026
    • Kellen Kanarios

    Softmax acts row by row, so drop into the scalar case with \(\mathbf {s}\) and \(\mathbf {p}\) single rows. The softmax Jacobian is \(\partial \mathbf {p}_i / \partial \mathbf {s}_j = \mathbf {p}_i(\delta _{ij} - \mathbf {p}_j)\), giving

    \[ \begin {align*} d\mathbf {s}_j &= \sum _{i} d\mathbf {p}_i \cdot \frac {\partial \mathbf {p}_i}{\partial \mathbf {s}_j} \\ &= \sum _{i} d\mathbf {p}_i \cdot \mathbf {p}_i (\delta _{ij} - \mathbf {p}_{j}) \\ &= d\mathbf {p}_{j} \mathbf {p}_{j} - \mathbf {p}_{j}\sum _{i} d\mathbf {p}_{i} \mathbf {p}_{i} .\end {align*} \]

    As a row vector this is \(d\mathbf {s} = \mathbf {p} \odot (d\mathbf {p} - \mathbf {p} \cdot d\mathbf {p})\), where the subtracted term is the scalar \(\mathbf {p} \cdot d\mathbf {p}\) broadcast across the row. Collecting those scalars into a column \(\mathbf {D}\) with \(\mathbf {D}_i = \mathbf {P}_i \cdot d\mathbf {P}_i\) recovers the matrix form

    \[d\mathbf {S} = \mathbf {P} \odot (d\mathbf {P} - \mathbf {D}).\]

    \(\mathbf {D}\) is the piece that will cause trouble later: it is a dot product over an entire row of \(\mathbf {P}\), which is exactly the thing we refuse to materialize.

    \(d\mathbf {Q}\) and \(d\mathbf {K}\) from \(\mathbf {S} = \mathbf {Q}\mathbf {K}^T\)

    • August 3, 2026
    • Kellen Kanarios

    One more chain rule, and the sums run over opposite indices:

    \[ \begin {align*} d\mathbf {Q}_{i} &= \sum _{j} d\mathbf {S}_{ij} \mathbf {K}_{j} = \sum _{j} \mathbf {P}_{ij} \left (d\mathbf {P}_{ij} - \mathbf {D}_i\right ) \mathbf {K}_{j}, \\ d\mathbf {K}_{j} &= \sum _{i} d\mathbf {S}_{ij} \mathbf {Q}_{i} = \sum _{i} \mathbf {P}_{ij} \left (d\mathbf {P}_{ij} - \mathbf {D}_i\right ) \mathbf {Q}_{i} .\end {align*} \]

    Recomputing instead of storing

    • August 3, 2026
    • Kellen Kanarios

    Every gradient above is expressed through \(\mathbf {P}_{ij}\) and \(d\mathbf {P}_{ij}\), both \(N \times N\). Materializing either one is exactly the quadratic memory cost the forward pass went to such lengths to avoid, so the backward pass has to be able to produce those entries on demand.

    💡 Insight. Both are recoverable from the \(N \times d\) tensors already resident in memory. The forward pass saved \(\mathbf {L}\), so \[\mathbf {P}_{ij} = \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}},\] and \(d\mathbf {P}\) is just an inner product of two rows, \[d\mathbf {P}_{ij} = \sum _{k} d\mathbf {O}_{ik} \mathbf {V}_{jk} = d\mathbf {O}_{i} \cdot \mathbf {V}_j.\] Neither ever requires an \(N \times N\) intermediate.

    Substituting both into the previous section leaves \(d\mathbf {Q}\) and \(d\mathbf {K}\) in terms of \(\mathbf {Q}\), \(\mathbf {K}\), \(\mathbf {V}\), \(d\mathbf {O}\), \(\mathbf {L}\), and \(\mathbf {D}\) alone:

    \[ \begin {align*} d\mathbf {Q}_{i} &= \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \left (d\mathbf {O}_{i} \cdot \mathbf {V}_j - \mathbf {D}_i\right ) \mathbf {K}_{j}, \\ d\mathbf {K}_{j} &= \sum _{i} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \left (d\mathbf {O}_{i} \cdot \mathbf {V}_j - \mathbf {D}_i\right ) \mathbf {Q}_{i}. .\end {align*} \]

    Getting \(\mathbf {D}\) for free

    • August 3, 2026
    • Kellen Kanarios

    One problem survives. \(\mathbf {D}_i = \mathbf {P}_i \cdot d\mathbf {P}_i\) is a dot product over a full row, so computing it inside the streaming loop would mean a reduction over all \(j\) before any tile of \(d\mathbf {Q}_i\) could be finished. This is the same global dependency the online softmax was designed to break.

    The way out is that the row sum has already been computed once, in the forward pass. Expanding and pulling \(d\mathbf {O}_i\) out of the sum:

    \[ \begin {align*} \mathbf {D}_i &= \mathbf {P}_{i} \cdot d\mathbf {P}_{i} \\ &= \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} d\mathbf {P}_{ij} \\ &= \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \left (d\mathbf {O}_{i} \cdot \mathbf {V}_{j}\right ) \\ &= d\mathbf {O}_{i} \cdot \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \mathbf {V}_{j} \\ &= d\mathbf {O}_{i} \cdot \mathbf {O}_{i} .\end {align*} \]

    The inner sum is precisely the definition of \(\mathbf {O}_i\). So \(\mathbf {D}\) is a single elementwise product of \(d\mathbf {O}\) and \(\mathbf {O}\) summed along the head dimension — one \(O(Nd)\) pass over tensors we already have, done once before the backward loop begins.

    Summary

    • May 27, 2026
    • Kellen Kanarios

    Forward pass. Store \(\mathbf {O}\) and the softmax denominators \(\mathbf {L}\), both \(O(Nd)\).

    Between the passes. Receive \(d\mathbf {O}\) from the layer above (automatic in JAX), then precompute \(\mathbf {D}_i = d\mathbf {O}_i \cdot \mathbf {O}_i\) in \(O(N)\) memory.

    Backward pass. Stream over tiles, recomputing \(\mathbf {P}_{ij}\) from \(\mathbf {Q}, \mathbf {K}, \mathbf {L}\) and \(d\mathbf {P}_{ij}\) from \(d\mathbf {O}, \mathbf {V}\) as needed:

    1. \(d\mathbf {V}_j = \sum _i \mathbf {P}_{ij} d\mathbf {O}_i\), accumulated over query tiles.
    2. \(d\mathbf {Q}_i = \sum _j \mathbf {P}_{ij}(d\mathbf {O}_i \cdot \mathbf {V}_j - \mathbf {D}_i)\mathbf {K}_j\), accumulated over key tiles.
    3. \(d\mathbf {K}_j = \sum _i \mathbf {P}_{ij}(d\mathbf {O}_i \cdot \mathbf {V}_j - \mathbf {D}_i)\mathbf {Q}_i\), accumulated over query tiles.

    Each accumulator is \(O(d)\) per row or column, so the whole backward pass stays linear in \(N\).

    POTW: Multi-Level Discovery of Deep Options [ZUAG]

    • July 22, 2026
    • Kellen Kanarios

    The setup for Multi-Level Discovery of Deep Options:

    • We have a meta-controller that outputs the skill \(z\) given the state \(s\) i.e. \(z_t \sim \eta (\cdot \mid s_t)\)
    • We have the skill, which is a skill-conditioned policy \(a_t \sim \pi (\cdot \mid s_t, z_t)\)
    • We have the termination function \(\psi (\cdot \mid s_t, z_{t - 1})\), which is per skill and evaluates the previous skill \(z_{t - 1}\) at the new state \(s_t\), such that \(b_t \sim \mathrm {Ber}\big (\psi (s_t, z_{t - 1})\big ) \in \{0, 1\} \)
      • For \(b_t = 1\), we resample a new skill \(z_t \sim \eta (\cdot \mid s_t)\)
      • Otherwise, \(z_{t} = z_{t - 1}\)

    Assuming there is a true underlying latent history \(\xi = \{b_{0}, z_{0}, b_{1}, z_{1}, \ldots \} \) and the observable history \(\mathcal {H} = \{s_{0}, a_{0}, s_{1}, a_{1}, \ldots \} \), the likelihood according to the above generative model is given by

    \[\mathbb {P}(\mathcal {H}, \xi ) = p(s_{0})\delta _{\{b_{0} = 1\}}\eta (z_{0} \mid s_{0}) \prod _{t=1}^{T - 1} \mathbb {P}(b_t, z_t \mid z_{t - 1}, s_t) \prod _{t = 0}^{T - 1} \pi (a_t \mid s_t, z_t) p(s_{t+1} \mid s_t, a_t)\]

    Furthermore, according to our model, we have that

    \[ \begin {align*} \mathbb {P}(b_t = 0, z_t \mid z_{t - 1}, s_t) &= (1 - \psi (s_t, z_{t - 1})) \cdot \delta _{\{z_{t} = z_{t - 1}\}} \\ \mathbb {P}(b_t = 1, z_t \mid z_{t - 1}, s_t) &= \psi (s_t, z_{t - 1}) \cdot \eta (z_t \mid s_t) .\end {align*} \]

    Up to this point, we have assumed this is the ground truth model and we are given each of the components. Instead we want to learn these components. To do so, we introduce our set of parameters \(\mathbf {\theta } \), such that each component is parametrized by a subset of \(\mathbf {\theta } \) i.e. \(\eta _{\theta }, \pi _{\theta }, \psi _{\theta }\).

    Goal. We want to learn some \(\theta \) that maximized the likelihood of the observable data.

    To do so, first consider the log-likelihood of our new parametrized model

    \[ \begin {align*} \log \mathbb {P}_{\theta }(\mathcal {H}, \xi ) &= \log \left [p(s_{0})\delta _{\{b_{0} = 1\}}\eta _{\theta }(z_{0} \mid s_{0}) \prod _{t=1}^{T - 1} \mathbb {P}_{\theta }(b_t, z_t \mid z_{t - 1}, s_t) \prod _{t = 0}^{T - 1} \pi _{\theta }(a_t \mid s_t, z_t) p(s_{t+1} \mid s_t, a_t)\right ] \\ &= \log p(s_{0})\delta _{\{b_{0} = 1\}} + \log \left [\eta _{\theta }(z_{0} \mid s_{0}) \prod _{t=1}^{T - 1} \mathbb {P}_{\theta }(b_t, z_t \mid z_{t - 1}, s_t) \prod _{t = 0}^{T - 1} \pi _{\theta }(a_t \mid s_t, z_t) \right ] + \sum _{t=0}^{T-1} \log \left [p(s_{t+1} \mid s_t, a_t)\right ] \\ &= \underbrace {\log p(s_{0})\delta _{\{b_{0} = 1\}} + \sum _{t=0}^{T-1} \log \left [p(s_{t+1} \mid s_t, a_t)\right ]}_{\text {independent of } \theta } + \log \left [\eta _{\theta }(z_{0} \mid s_{0}) \prod _{t=1}^{T - 1} \mathbb {P}_{\theta }(b_t, z_t \mid z_{t - 1}, s_t) \prod _{t = 0}^{T - 1} \pi _{\theta }(a_t \mid s_t, z_t)\right ] .\end {align*} \]

    Since we are only concerned with learning \(\theta \), we can disregard the \(\theta \) independent terms leaving

    \[\begin {align*} \nabla _{\theta } \log \mathbb {P}_{\theta }(\mathcal {H}, \xi ) &= \nabla _{\theta } \left [ \log \left [\eta _{\theta }(z_{0} \mid s_{0}) \prod _{t=1}^{T - 1} \mathbb {P}_{\theta }(b_t, z_t \mid z_{t - 1}, s_t) \prod _{t = 0}^{T - 1} \pi _{\theta }(a_t \mid s_t, z_t)\right ] \right ]\\ &= \nabla _{\theta } \log \left [\eta _{\theta }(z_{0} \mid s_{0})\right ] + \sum _{t=1}^{T - 1} \nabla _{\theta } \log \left [\mathbb {P}_{\theta }(b_t, z_t \mid z_{t - 1}, s_t)\right ] + \sum _{t = 0}^{T - 1} \nabla _{\theta } \log \left [\pi _{\theta }(a_t \mid s_t, z_t)\right ]. \end {align*}\]
    Problem. This requires samples \((\mathcal {H}, \xi ) \sim P_{\theta }(\mathcal {H}, \xi )\), but we only have samples \(\mathcal {H} \sim P_{\theta }(\mathcal {H})\)!!!
    Solution. We can use the trick from Expectation Maximization. Referred to in the paper as the expectation gradient trick. Namely, \[\nabla _{\theta } \log P_{\theta }(\mathcal {H}) = \mathbb {E}_{\xi \sim P_{\theta }(\xi \mid \mathcal {H})} \left [ \nabla _{\theta } \log P_{\theta }(\mathcal {H}, \xi ) \right ]\]

    Now it remains to compute the expectation from \(P_{\theta }(\xi \mid \mathcal {H})\)

    Remark. Note that \(P_{\theta }(\xi \mid \mathcal {H})\) is a distribution over \((K, \{0,1\})^{T} \) i.e. over each \((z_t, b_t)\). To efficiently compute, we need to use Forward-backward algorithm.

    Definition. Crossbar [YV5J]

    • May 12, 2026
    • Kellen Kanarios

    The simplest indirect network: an \(n \times m\) grid of switch points connecting \(n\) inputs to \(m\) outputs. Any input can be connected to any free output simultaneously — non-blocking.

    • One hop per transit (minimum possible).
    • Serializes if multiple senders target the same receiver.
    • Switch area grows as \(O(n \cdot m)\) — the dominant cost as systems grow.
    Remark. Crossbar router area scales as the square of the port count, which is why high-radix routers are dramatically more expensive than low-radix ones.

    Crossbars are common as the inner switch of larger structured networks (Clos network, Fat tree) — large flat crossbars are impractical at scale, but small crossbars are cheap.

    Definition. Clos network [YKAN]

    • May 12, 2026
    • Kellen Kanarios

    A three-stage indirect network parameterized by \((m, n, r)\): \(r\) input switches and \(r\) output switches each of size \(n \times m\), with \(m\) middle-stage switches each \(r \times r\). Total terminal nodes \(N = nr\). Non-blocking when \(m \geq 2n - 1\).

    • Number of total switching elements scales as \(N^{1.5}\) versus \(N^2\) for a flat Crossbar while preserving non-blocking.
    • Path diversity is \(m\) — multiple distinct paths between any source and destination.
    Proof. There are \(rmn\) input-switch elements, \(mr^2\) middle-switch elements, and \(rmn\) output-switch elements: \[S = 2rmn + mr^2.\] With \(r = N/n\): \[S = 2Nm + m(N/n)^2.\] Choosing \(n = \sqrt {N}\) and \(m \geq 2n - 1 = O(\sqrt {N})\): \[S = 4mN = O(N^{1.5}).\]
    Remark. A folded Clos network — input and output stages combined, making \(n\) input ports and \(m\) output ports bidirectional — is structurally the same as a Fat tree.

    exec() [YHJR]

    • May 12, 2026
    • Kellen Kanarios

    Replaces the calling Process's program with a new executable. exec() does not return on success — the original code, data, stack, and heap are discarded and the new program runs in their place. The PID is unchanged.

    What exec() does internally:

    1. Loads the new executable's code and static data, overwriting the current.
    2. Re-initializes stack and heap.
    3. Jumps to the new program's entry point with arguments passed as argv.

    The canonical Unix pattern is fork() then exec() — the shell uses this to launch a command without becoming that command:

    int main()
  while (true) {
    command = getcommand();
    int rc = fork();
    if (rc < 0)
      printf("error with fork");
    else if (rc == 0)
      exec(command);            // child becomes the command
    else
      int rc = wait(NULL);      // parent waits for it
  }

    Redirection is implemented by opening a file in the child between fork() and exec(), attached to STDOUT_FILENO:

    if (rc == 0)
  close(STDOUT_FILENO);
  open("output.txt");
  exec(command);
    Remark. The many variants — execl, execle, execlp, execv, execvp, execvP — differ in how they take arguments (list vs. vector), whether they use the PATH environment variable, and whether they take an explicit environment.

    Transactional memory [Y8JE]

    • May 12, 2026
    • Kellen Kanarios

    An alternative to fine-grained Locks: mark code regions as transactions that should appear atomic, execute them speculatively in parallel, and detect conflicts after the fact. Aims at the performance of fine-grained locking with the programming ergonomics of coarse-grained locking.

    Conflict detection

    • May 12, 2026
    • Kellen Kanarios

    Two transactions conflict if they access the same memory location and at least one of them is a write. The implementation tracks per-transaction read and write sets.

    • Lazy detection. Build the entire read/write set as the transaction runs; check for conflicts only at commit time. If conflict, roll back.
    • Eager detection. Check on every access against other transactions' sets; abort immediately on conflict.

    Eager detection can piggyback on the cache coherence protocol: add read/write bits to each cache line, set them during a transaction, and let a coherence invalidation signal a conflict.

    Version management (rollback)

    • May 12, 2026
    • Kellen Kanarios

    Two operations: commit and abort. Implementations:

    1. Lazy. stores go to a "write table" rather than memory; loads check the table first, falling back to memory. Commit writes the table back (slow); abort just clears the table (fast).
    2. Eager (coherence-backed). stores write through but track read/write sets per cache line. Commit clears the sets (fast); abort clears the sets (also fast — work already on overwrite if not aborted before commit).
    Problem. If a transaction touches more cache lines than the cache holds, the tracking overflows.
    Solution. Fall back to software transactional memory (STM) on overflow — a hybrid scheme that keeps hardware fast-path for common cases.

    The abstraction

    Process [FCHM]

    • May 12, 2026
    • Kellen Kanarios

    A running program, plus all the state the OS needs to pause it and resume it later. A process consists of:

    1. Memory: an Address space holding the program's code, stack, and heap.
    2. Registers: general-purpose registers carrying current computation, plus special-purpose registers:
      • Program counter (PC): the next instruction to run.
      • Stack pointer and frame pointer: where the process sits on its stack.

    A process moves between three states:

    • running: currently on a CPU.
    • ready: runnable, waiting for the Scheduling to give it a CPU.
    • blocked: waiting on I/O or another event, not runnable.
    Remark. Threads (see Concurrency Intro) share an address space within a process but each have their own PC, register set, and stack.

    Process API [JJ45]

    • May 12, 2026
    • Kellen Kanarios

    The minimum operations any OS must expose for working with Processes:

    1. Create: load a program from disk, set up its address space (stack, heap, code), and jump to main. The OS also initializes argc/argv.
    2. Destroy: kill a misbehaving or unwanted process.
    3. Wait: block until another process completes — useful for ordering dependent work.
    4. Miscellaneous control: e.g. suspend / resume.
    5. Status: report on running processes.
    Remark. The stack is allocated up front. The heap starts small and grows via malloc, which calls into the OS (brk/sbrk) when it runs out of headroom.

    On Unix, the concrete realization of this API uses fork(), wait(), and exec() — covered separately.

    Process control block [JE53]

The PCB is what the OS reads and writes during a Context switch: the saved register set lives here, as does the process state, the open files, the parent pointer, and so on.

    fork() [O1S9]

    • May 12, 2026
    • Kellen Kanarios

    The Unix system call that duplicates the calling Process. After fork() returns, two processes exist where there was one. The child gets its own copy of:

    1. Address space.
    2. General-purpose registers.
    3. Program counter — the child returns from fork() at the same instruction the parent does.

    The two processes are distinguished by fork()'s return value:

    int main()
  int rc = fork();
  if (rc < 0)
    printf("error with fork");
  else if (rc == 0)
    printf("in child");
  else
    printf("in parent");        // rc holds child PID
    Remark. Which process is scheduled first after fork() is non-deterministic. Use wait() if you need ordering.
    Remark. The copy is logical, not physical: real implementations use Copy-on-write so the duplicated address space only allocates fresh pages when one side writes to them.

    wait() [J6VZ]

    • May 12, 2026
    • Kellen Kanarios

    Blocks the calling Process until one of its children terminates. The OS marks the child's PCB ZOMBIE on exit, keeping enough state (exit status, resource usage) for the parent to retrieve via wait(); only when the parent collects it is the child fully reaped.

    wait() returns the PID of the child that died. Variant waitpid(pid, ...) blocks on a specific child — useful when a parent has multiple children and only one is interesting.

    Used to enforce ordering between parent and child code paths after fork(), or to know when an exec()'d program finishes.

    Remark. Calling wait() with no children to wait on returns -1.

    Unix signals [9V3H]

    • May 12, 2026
    • Kellen Kanarios

    An asynchronous notification delivered to a Process. A process sends a signal with kill(pid, signum) (the name is misleading — most signals don't kill); the recipient can install a handler with signal(signum, handler) to "catch" it, otherwise the default action runs (often termination).

    Limited Direct Execution [VE8C]

    • July 19, 2025
    • Kellen Kanarios

    The OS lets user code run directly on the CPU for speed, but with hardware-enforced limits that prevent a buggy or malicious program from compromising the rest of the system. Two questions motivate the mechanism:

    Question.
    1. How do we make sure a program doesn't do what we don't want it to do?
    2. How do we enable time-sharing?

    The first question is answered by hardware User mode vs kernel mode enforced via the Trap table, with a controlled Syscall mechanism as the only path from one to the other. The second is answered by periodic timer interrupts that trap to the OS, which performs a Context switch and runs the scheduler.

    The whole stack is bootstrapped during the Boot sequence, when the kernel installs the trap table and starts the timer before handing control to user space.

    User mode vs kernel mode [QUQC]

    • May 12, 2026
    • Kellen Kanarios

    Two privilege levels supported by the CPU. User mode restricts the running process to a limited set of instructions and a limited view of memory — usually just its own address space. Kernel mode runs the OS with full access to all instructions and all of physical memory.

    Switching between modes is mediated by hardware via a Trap table populated at boot. The OS sets up the table; the CPU enforces it. A process cannot promote itself to kernel mode arbitrarily — it must invoke a Syscall mechanism, which traps to a fixed entry point in the OS.

    Remark. Kernel mode is dangerous because the address space is effectively the entire machine. The mode bit + the trap table together are what makes it safe to time-share a CPU between mutually distrusting programs.

    Trap table [0NVY]

    • May 12, 2026
    • Kellen Kanarios

    A hardware-readable table installed by the OS at boot that maps each kind of exceptional control-flow event (syscall, interrupt, page fault, illegal instruction, ...) to the address of an OS handler. When the CPU takes a trap, it consults this table to decide where to jump, switches into kernel mode, and runs the handler.

    The table is what makes it safe to expose privileged operations to user mode: user code never gets to pick the destination of a mode-switch, only the trap number. The OS controls every entry point, the CPU enforces the indirection.

    Remark. Installing the trap table is itself a privileged operation. It happens once, early in boot, before any user process exists.

    Syscall mechanism [A5S6]

    • May 12, 2026
    • Kellen Kanarios

    A syscall is a user-mode-initiated request for a privileged service from the kernel. Because user code cannot jump into kernel code directly, the mechanism is built around a single trap instruction plus a pre-agreed register convention identifying which service to perform.

    The end-to-end sequence:

    1. User code places the syscall number in a pre-defined register and invokes the trap instruction.
    2. Hardware saves enough state to resume the process and switches to kernel mode.
    3. Hardware jumps to the OS-installed handler via the Trap table.
    4. The handler reads the syscall number from the agreed register and dispatches to the corresponding OS routine.
    5. The OS validates the request, performs the work, and arranges return values per the calling convention.
    6. The OS restores user state and returns the process to user mode.
    Remark. Because the register convention is fixed by ABI, the user-mode side of a syscall is typically hand-written in assembly within libc.
    Remark. Interrupts work via a similar trap-handler mechanism, but are initiated by hardware (timer, device) rather than user code.
    Remark. The kernel must validate any pointers or arguments the user supplies — user code cannot be trusted not to ask the kernel to read kernel memory on its behalf.

    Context switch [OKCI]

    • May 12, 2026
    • Kellen Kanarios

    The operation of saving the full execution state of one process (or thread) and restoring another's so the CPU can resume it as if it had never been interrupted. On a trap into the kernel, the hardware stashes the user-visible state (PC, condition codes, stack pointer) into a known location, and the OS saves the remaining general-purpose registers as part of the switching code.

    Two flavors of state are involved:

    1. User registers: the current program's context (general-purpose registers, stack vars).
    2. Kernel registers: meta-information used to resume the trap correctly (PC at trap, syscall number, etc.).

    Context switches are not free — they incur the cost of cache and TLB pollution in addition to the direct cost of saving/restoring state. This is the cost amortized by larger scheduling quanta and a recurring concern for any Concurrency system.

    Boot sequence [XSFO]

    • May 12, 2026
    • Kellen Kanarios

    The fixed series of steps a machine performs from power-on until a usable operating system is running. Each stage runs from a known location and hands off control to the next.

    1. Power signal resets the CPU to a known state.
    2. The CPU fetches from a hard-wired address — the BIOS (or UEFI firmware). The BIOS runs basic hardware checks (POST).
    3. The BIOS loads and jumps to the bootloader (e.g. GRUB) from a known location on disk.
    4. The bootloader places the kernel image at the correct address and jumps to its entry point.
    5. The kernel performs early setup: installs the Trap table (a special privileged instruction), starts the timer interrupt, sets up memory management, and finally enters user space.
    Remark. The hardware is hard-wired only to find the BIOS. Everything past that is software the user can replace, which is why dual-booting and custom bootloaders work.

    Scheduling [B8GC]

    • July 26, 2025
    • Kellen Kanarios

    The scheduler decides which runnable Process to put on the CPU at each moment. There is no single right answer because the metrics conflict:

    1. Turnaround time: time from arrival to completion, \(T_{\text {completion}} - T_{\text {arrival}}\). Minimized by running short jobs first.
    2. Response time: time from arrival to first scheduling. Minimized by frequent rotation.
    3. Fairness: every job makes progress; nobody starves.

    FIFO scheduling [JA6Z]

    • May 12, 2026
    • Kellen Kanarios

    First-in, first-out. Jobs are run to completion in the order they arrive. Trivially fair under any reasonable notion of fairness, but suffers from the convoy effect: a single long-running job at the head delays every shorter job behind it, inflating average turnaround time.

    Problem. If the first arriving job is much longer than the rest, all subsequent jobs wait at least its full duration before getting any CPU.

    SJF scheduling [VJ4F]

    • May 12, 2026
    • Kellen Kanarios

    Shortest job first. Run the job with the smallest total work first, run-to-completion. If all jobs arrive at the same time, SJF provably minimizes average turnaround time.

    Problem. Real workloads don't all arrive at \(t = 0\). A long job that arrives slightly before a short one still gets to monopolize the CPU until it finishes — SJF degenerates to FIFO scheduling under sequential arrivals.

    Removing the run-to-completion constraint and allowing preemption gives STCF scheduling.

    STCF scheduling [7R07]

    • May 12, 2026
    • Kellen Kanarios

    Shortest time-to-completion first. A preemptive refinement of SJF scheduling: whenever the scheduler is invoked, it picks the job with the least remaining work. A short job arriving mid-execution can preempt a long one.

    STCF is provably optimal for minimizing average turnaround time over all preemptive schedulers.

    Problem. Long jobs starve in response time. The lowest-priority work might not get a CPU slice for a very long time, which is unacceptable for interactive workloads.

    Round-robin scheduling [NEL8]

    • May 12, 2026
    • Kellen Kanarios

    Cycle through all runnable jobs, giving each a fixed time slice — the stride, time slice, or quantum length — before preempting and moving to the next. The best you can do at minimizing response time: every job sees the CPU within at most \(N\) quanta where \(N\) is the runnable-job count.

    The quantum length is a tradeoff:

    • Short quantum: better response time, more frequent context switches, worse cache locality.
    • Long quantum: amortizes context-switch cost, worse response time.

    Worst-case response time for \(N\) jobs at quantum \(S\) is \(S(N-1)\).

    Remark. Round-robin minimizes response time but is poor for turnaround time relative to STCF scheduling. A scheduler that wants both has to combine ideas — see Multi-level feedback queue.

    Multi-level feedback queue [4WG5]

    • May 12, 2026
    • Kellen Kanarios

    A practical scheduler that approximates STCF scheduling's turnaround properties and Round-robin scheduling's response properties without requiring foreknowledge of job lengths. Maintain multiple priority queues; within a queue, schedule round-robin. Never service a lower-priority queue while a higher-priority queue has a runnable job.

    The priority of a job is not assigned by the user — it is learned from behavior:

    • New jobs enter at the top priority.
    • Each priority level has an allotment — the total CPU time a job may consume before being demoted.
    • Once a job exhausts its allotment at a level, it drops to the next level.

    Short jobs that finish quickly never leave the top queue (good turnaround). Interactive jobs that yield often stay at the top (good response time). CPU-bound jobs sink to the bottom and get scheduled when nothing better is runnable.

    Problem. Gaming the allotment: a job can issue I/O just before its allotment expires to avoid demotion, since I/O time doesn't count.
    Solution. Charge the job's allotment for total time at the priority level, including time spent blocked.
    Problem. Starvation of low-priority queues if higher queues never empty.
    Solution. Periodically reset all jobs to the top priority. Cheap and effective.

    Lottery scheduling [AM8U]

    • May 12, 2026
    • Kellen Kanarios

    A proportional-share scheduler. Each runnable job holds some number of tickets, drawn from a fixed total. On each scheduling decision, the scheduler picks a random ticket and runs the job that owns it. Over time, a job receives CPU time proportional to its share of the tickets.

    The implementation is trivial: one random number per decision, plus a sum table. No global state about historical CPU usage is needed.

    Mechanisms layered on top:

    • Ticket currency — give each user a fixed number of tickets to split among their processes however they like.
    • Ticket transfer — a client process can hand tickets to a server to boost its priority while servicing the request.
    • Ticket inflation — a process can grow its share temporarily, with bounds set by trust.
    Remark. The unsolved problem is how to assign tickets in the first place. The mechanism is simple; the policy is not.

    A deterministic version of the same idea is Stride scheduling, which avoids the variance of random sampling at the cost of needing global state.

    Stride scheduling [HCJ7]

    • May 12, 2026
    • Kellen Kanarios

    A deterministic proportional-share scheduler. Each job has a stride inversely proportional to its ticket count (the more tickets, the smaller the stride) and a running pass counter that accumulates its stride every time it's scheduled.

    The decision is:

    1. Pick the job with the lowest pass.
    2. Run it for one quantum.
    3. Increment its pass by its stride.

    A job with twice as many tickets has half the stride, so its pass grows half as fast, so it gets scheduled twice as often. Same long-run behavior as Lottery scheduling, but with zero variance.

    Problem. New jobs need an initial pass value. Setting it to 0 lets them dominate; setting it to the global minimum lets them merge in cleanly but requires tracking that minimum.
    Remark. Each context switch is not free. Choosing a longer time slice amortizes that cost at the price of response time.
    Remark. I/O-bound jobs are commonly handled by splitting a job into its non-I/O segments and scheduling them individually — turning one long-but-mostly-blocked job into many short, runnable ones.

      wait() [J6VZ]

      • May 12, 2026
      • Kellen Kanarios

      Blocks the calling Process until one of its children terminates. The OS marks the child's PCB ZOMBIE on exit, keeping enough state (exit status, resource usage) for the parent to retrieve via wait(); only when the parent collects it is the child fully reaped.

      wait() returns the PID of the child that died. Variant waitpid(pid, ...) blocks on a specific child — useful when a parent has multiple children and only one is interesting.

      Used to enforce ordering between parent and child code paths after fork(), or to know when an exec()'d program finishes.

      Remark. Calling wait() with no children to wait on returns -1.

      Copy-on-write [DEJB]

      • May 12, 2026
      • Kellen Kanarios

      An optimization where two address spaces share the same physical page until one writes to it. Both processes have PTEs pointing at the same PPN, but with the write bit cleared. The first write traps to the OS, which allocates a fresh page, copies the contents, points the writing process's PTE at the new page (with writes re-enabled), and resumes.

      Used pervasively:

      • fork() — the child shares the parent's pages until either modifies one. Avoids the cost of copying an entire address space the child often immediately overwrites with exec().
      • Shared libraries — many processes map the same library text pages.
      • Kernel mapped into every process — same physical kernel code seen from every address space.

        Process [FCHM]

        • May 12, 2026
        • Kellen Kanarios

        A running program, plus all the state the OS needs to pause it and resume it later. A process consists of:

        1. Memory: an Address space holding the program's code, stack, and heap.
        2. Registers: general-purpose registers carrying current computation, plus special-purpose registers:
          • Program counter (PC): the next instruction to run.
          • Stack pointer and frame pointer: where the process sits on its stack.

        A process moves between three states:

        • running: currently on a CPU.
        • ready: runnable, waiting for the Scheduling to give it a CPU.
        • blocked: waiting on I/O or another event, not runnable.
        Remark. Threads (see Concurrency Intro) share an address space within a process but each have their own PC, register set, and stack.
