The process abstraction, what the OS has to support to maintain it, and the data structure that holds it together.

1. Process [FCHM]

  • May 12, 2026
  • Kellen Kanarios

A running program, plus all the state the OS needs to pause it and resume it later. A process consists of:

  1. Memory: an Address space holding the program's code, stack, and heap.
  2. Registers: general-purpose registers carrying current computation, plus special-purpose registers:
    • Program counter (PC): the next instruction to run.
    • Stack pointer and frame pointer: where the process sits on its stack.

A process moves between three states:

  • running: currently on a CPU.
  • ready: runnable, waiting for the Scheduling to give it a CPU.
  • blocked: waiting on I/O or another event, not runnable.
Remark. Threads (see Concurrency Intro) share an address space within a process but each have their own PC, register set, and stack.

2. Process API [JJ45]

  • May 12, 2026
  • Kellen Kanarios

The minimum operations any OS must expose for working with Processes:

  1. Create: load a program from disk, set up its address space (stack, heap, code), and jump to main. The OS also initializes argc/argv.
  2. Destroy: kill a misbehaving or unwanted process.
  3. Wait: block until another process completes — useful for ordering dependent work.
  4. Miscellaneous control: e.g. suspend / resume.
  5. Status: report on running processes.
Remark. The stack is allocated up front. The heap starts small and grows via malloc, which calls into the OS (brk/sbrk) when it runs out of headroom.

On Unix, the concrete realization of this API uses fork(), wait(), and exec() — covered separately.

3. Process control block [JE53]

  • May 12, 2026
  • Kellen Kanarios

The kernel-side data structure holding all per-process state. There is one PCB per Process, threaded together into the process list. The PCB is what the OS reads and writes during a Context switch: the saved register set lives here, as does the process state, the open files, the parent pointer, and so on.

An example from xv6:

// the registers xv6 will save and restore
// to stop and subsequently restart a process
struct context {
  int eip;
  int esp;
  int ebx;
  int ecx;
  int edx;
  int esi;
  int edi;
  int ebp;
};
// the different states a process can be in
enum proc_state { UNUSED, EMBRYO, SLEEPING, RUNNABLE, RUNNING, ZOMBIE };
// the information xv6 tracks about each process
// including its register context and state
struct proc {
  char *mem;                 // Start of process memory
  uint sz;                   // Size of process memory
  char *kstack;              // Bottom of kernel stack for this process
  enum proc_state state;     // Process state
  int pid;                   // Process ID
  struct proc *parent;       // Parent process
  void *chan;                // If non-zero, sleeping on chan
  int killed;                // If non-zero, have been killed
  struct file *ofile[NOFILE]; // Open files
  struct inode *cwd;         // Current directory
  struct context context;    // Switch here to run process
  struct trapframe *tf;      // Trap frame for the current interrupt
};
Remark. Threads need an analogous thread control block; see Concurrency Intro.

    • August 5, 2026

    Multiplying \(X (B \times D)\) and \(Y (D \times F)\) in int8.

    1. How many bytes loaded from memory?
    2. How many total OPs performed?
    3. What is arithmetic intensity?
    4. What is roofline estimate for \(T_{math}\) and \(T_{comms}\)? What are reasonable upper and lower bounds for runtime of whole operation?
    Solution.
    1. The only difference here from before is that the loaded / written bytes are divided by \(2\). This means we load \(BD\) bytes for \(X\) and \(DF\) bytes for \(Y\), which is a total of \(BD + DF\) bytes.
    2. The same number of total ops is performed. Namely, for each element in the output matrix (\(BF\) of them) we must perform \(2D\) OPs. This leaves a total of \(2DBF\) OPs.
    3. The arithmetic intensity is now just \(2 \times \) the old arithmetic intensity because we are loading half as many bytes i.e. \(\frac {2DBF}{BD + DF + BF}\).
      4. Remark. After looking at the solution, they also mention that the rule on batch size to saturate arithmetic intensity remains unchanged. Namely, using the heuristic \(B \ll D, F\), we can get that the arithmetic intensity \(\approx \frac {2DBF}{DF} = 2B\). One may think that this means that we can use smaller batch size. However, recall that our in8 peak OPs/s has now doubled to \(3.94e14\). Therefore, the computation is effectively \[2B > \frac {2 \cdot \text {Peak OPs / s}}{\text {HBM Bandwidth}} \iff B > \frac {\text {Peak OPs / s}}{\text {HBM Bandwidth}} = 240\]
      Question. So what is the point of int8?
      Answer.Within each batch, we are actually performing FLOPs \(2 \times \) as fast. Therefore, our computation is actually twice as fast wall clock time!
    4. From above, we know that we are performing \(2DBF\) FLOPs. Assuming our int8 peak OPs/s is \(3.94e14\), this gives \(T_{math} = \frac {2DBF}{3.94e14}\). Similarly, we have that \(T_{comm} = \frac {BD + DF + BF}{8.2e11}\). We know that \(\max \{T_{max}, T_{comm}\} \) is a good lower bound, and that \(T_{max} + T_{comm}\) is a good upper bound.

    In \(\epsilon \)-greedy action selection with two actions, how often is the greedy action selected?

    Solution.

    Exercise 2.2. Which exploration rate wins in the long run

    • November 24, 2024
    • Kellen Kanarios

    On the 10-armed testbed, which value of \(\epsilon \) achieves the highest reward in the long run, and by how much?

    Solution.

    \(\epsilon = 0.01\). Expected reward under an \(\epsilon \)-greedy policy that has converged is

    \[ \begin {align*} R^* = \max _{a} q^*(a) + \frac {\epsilon }{n}\sum _{i \neq a}^{n} q^*(i) \end {align*} \]

    so a smaller \(\epsilon \) pays less exploration tax once the right arm is identified. The exception is \(\epsilon = 0\), which comes with no guarantee at all: with zero initialization, a suboptimal arm whose empirical average stays positive is never abandoned. Some \(\epsilon > 0\) is what buys convergence to the optimal arm.

    Exercise 2.6. The spikes in the optimistic-initialization curve

    • November 24, 2024
    • Kellen Kanarios

    Optimistic initialization produces oscillations and a pronounced early spike in the optimal-action curve. Why?

    Solution.

    Every arm on the testbed has support well below \(5\), so an unpulled arm's optimistic estimate beats the empirical estimate of anything already pulled. The early steps are therefore a round robin over all arms, and — with rewards deterministic — the optimal arm keeps being pulled until its estimate falls below the remaining optimistic ones. That alternation between "sweep the untried" and "exploit the best so far" is the oscillation.

    Exercise 2.8. The UCB spike at step 11

    • November 24, 2024
    • Kellen Kanarios

    UCB performance shows a pronounced spike on the 11th step of the 10-armed testbed, then drops. Why?

    Solution.

    With \(10\) arms at equal initialization the exploration bonus forces the first \(10\) pulls to be a round robin. On step \(11\) all bonuses are equal again, so the tie is broken by empirical reward and the best-so-far arm is pulled — the spike. It drops immediately after, because that pull shrinks the chosen arm's bonus and hands the next steps to other, possibly worse, arms.

    Exercise 2.10. The value of knowing which case you are in

    • November 24, 2024
    • Kellen Kanarios

    A two-armed bandit alternates between two cases with equal probability. In case A, \(q_*(1) = 10\) and \(q_*(2) = 20\); in case B, \(q_*(1) = 90\) and \(q_*(2) = 80\). What is the best expected reward achievable, and how does it change if you are told which case you are in?

    Solution.

    Without the case label, the two arms are indistinguishable in expectation:

    \[ \begin {align*} \mathbb {E}[R(1)] &= 0.5 \cdot 10 + 0.5 \cdot 90 = 50, \\ \mathbb {E}[R(2)] &= 0.5 \cdot 20 + 0.5 \cdot 80 = 50 \end {align*} \]

    so the ceiling is \(50\). Told the case, you can condition on it and pick the better arm in each:

    \[ \begin {align*} R^* &= 0.5 \cdot \max _{a}\mathbb {E}[R(a) \mid x = 1] + 0.5 \cdot \max _{a}\mathbb {E}[R(a) \mid x = 2] \\ &= 0.5 \cdot 20 + 0.5 \cdot 90 \\ &= 55 \end {align*} \]

    The \(5\) points of difference are the value of the observation — which is what turns a bandit into an associative (contextual) problem.

    Exercise 3.3. Where to draw the agent-environment boundary

    • November 24, 2024
    • Kellen Kanarios

    Where should the line between agent and environment be drawn — at the steering wheel, at the muscles, at the intent to drive somewhere? Is any level fundamentally preferable?

    Solution.

    Draw it where you can already execute the behavior that carries you from one state to another. Fixing the boundary above the level of reliable control means the agent must relearn what it already has; fixing it below means solving a control problem you did not need to solve. This is precisely the premise of hierarchical reinforcement learning, which raises the boundary over time by learning subpolicies and then treating them as primitive.

    Exercise 3.5. Adapting the continuing formulation to episodic tasks

    • November 24, 2024
    • Kellen Kanarios

    Restate the equations of the continuing case so they apply to episodic tasks.

    Solution.

    Add a terminal state — some \(t\) adjoined to \(\mathcal {S}\) — and split the normalization condition on whether we have reached it:

    \[ \begin {cases} p(t, 0 \mid s, a) = 1, &\text { if } s = t\\ \sum _{s^{\prime }\in \mathcal {S}}\sum _{r\in \mathcal {R}}p(s^{\prime },r|s,a)=1,\mathrm {~for~all~}s\in \mathcal {S},a\in \mathcal {A}(s), &\text { if } s \neq t \end {cases} \]

    The content of this is just that once you hit a terminal state you can reach nothing else, and accrue nothing further.

    Exercise 3.7. The maze-runner that never learns to hurry

    • November 24, 2024
    • Kellen Kanarios

    A maze-running agent gets \(+1\) for escaping and \(0\) otherwise, and after many episodes shows no improvement. What is going wrong?

    Solution.

    The task has not actually been communicated. Every escaping trajectory earns the same return regardless of how long it took, so the agent has no reason to prefer a fast escape to a slow one. Fix it by paying \(-1\) per timestep, or by discounting so that a reward collected later is worth less.

    Exercise 3.8. Computing returns backwards

    • November 24, 2024
    • Kellen Kanarios

    With \(\gamma = 0.5\) and the reward sequence \(R_1 = -1\), \(R_2 = 2\), \(R_3 = 6\), \(R_4 = 3\), \(R_5 = 2\), what are \(G_0\) through \(G_5\)?

    Solution.

    The recursion \(G_t = R_{t+1} + \gamma G_{t+1}\) is solved from the back:

    \[ \begin {align*} G_5 &= 0 \\ G_4 &= R_{5} + \gamma G_5 = 2 \\ G_3 &= R_{4} + \gamma G_4 = 4 \\ G_2 &= R_{3} + \gamma G_3 = 8 \\ G_1 &= R_{2} + \gamma G_2 = 6 \\ G_0 &= R_{1} + \gamma G_1 = 2 \end {align*} \]

    Exercise 3.9. Return of an infinite constant reward stream

    • November 24, 2024
    • Kellen Kanarios

    With \(\gamma = 0.9\), a reward of \(2\) followed by an infinite sequence of \(7\)s, what are \(G_1\) and \(G_0\)?

    Solution.

    Peel off the leading term and sum the geometric tail:

    \[ \begin {align*} G_0 &= R_{1} + \gamma R_{2} + \gamma ^2 R_{3} + \cdots \\ &= 2 + \sum _{i = 1}^{\infty } \gamma ^{i} R_{i} \\ &= 2 + \gamma \sum _{i = 0}^{\infty } \gamma ^{i} R_{i + 2} \\ &= 2 + \frac {7 \gamma }{1 - \gamma } \\ &= 65 \end {align*} \]

    and

    \[ \begin {align*} G_1 &= R_{2} + \gamma R_{2} + \gamma ^2 R_{3} + \cdots \\ &= 7 + \sum _{i = 1}^{\infty } \gamma ^{i} R_{i} \\ &= 7 + \gamma \sum _{i = 0}^{\infty } \gamma ^{i} R_{i + 3} \\ &= 7 + \frac {7 \gamma }{1 - \gamma } \\ &= 70 \end {align*} \]

    Exercise 3.11. Expected reward in terms of the policy and dynamics

    Exercise 3.15. Adding a constant to every reward

    • November 24, 2024
    • Kellen Kanarios

    In gridworld the rewards are positive, so what matters is their differences. Show that adding a constant \(c\) to every reward adds a constant \(v_c\) to the value of every state, and give \(v_c\) in terms of \(c\) and \(\gamma \).

    Solution.

    Starting from

    \[ \begin {align*} v_{\pi }(s) = \mathbb {E}_{\pi } \left [\sum _{k = 0}^{\infty } \gamma ^{k} R_{t + k + 1} \mid S_t = s\right ] \end {align*} \]

    and shifting every reward by \(c\), the shift factors out of the expectation as its own geometric series:

    \[ \begin {align*} v_{\pi }'(s) &= \mathbb {E}_{\pi } \left [\sum _{k = 0}^{\infty } \gamma ^{k} (R_{t + k + 1} + c) \mid S_t = s\right ] \\ &= \mathbb {E}_{\pi } \left [\sum _{k = 0}^{\infty } \gamma ^{k} R_{t + k + 1}\mid S_t = s\right ] + \sum _{k = 0}^{\infty } \gamma ^{k} c \\ &= v_{\pi }(s) + \frac {c}{1 - \gamma } \end {align*} \]

    so \(v_c = \frac {c}{1 - \gamma }\), the same for every state — and therefore no change to the ordering of policies.

    Exercise 8.1. Can multi-step bootstrapping match Dyna with a perfect model?

    • November 24, 2024
    • Kellen Kanarios

    The nonplanning method in the maze example is a special case of the \(n\)-step method. Could a multi-step bootstrapping method do as well as a Dyna agent given a perfect model?

    Solution.

    Take \(n\) large enough and the first pass is just as good, in the sense that every \((s,a)\) pair on the encountered trajectory gets updated.     Exercise 8.5. Dyna-Q+ in stochastic and changing environments

    • November 24, 2024
    • Kellen Kanarios

    How might the tabular Dyna-Q algorithm be modified for stochastic environments? How might it handle environments that change over time?

    Solution.

    Replace the deterministic transition entry with an empirical distribution over successor states and rewards. For a changing environment, weight recent observations more heavily when updating that empirical model, e.g.

    \[\hat {R}_{t + 1}(S,A) = \lambda \hat {R}_{t}(S, A) + (1 - \lambda )R_{t + 1}(S, A)\]

    which is exponential recency-weighting — the same instrument used for nonstationary bandits in Chapter 2.

    It strengthens it. Samples concentrate where the probability mass is, so a handful of them recovers most of what the expected update computes — and the expected update pays for the whole tail to get there.

    • November 24, 2024

    Show that tabular methods are a special case of linear function approximation. What are the feature vectors?

    Solution.

    Linear function approximation carries two objects, \(\boldsymbol {w}\) and \(\boldsymbol {x}(s)\), updated as

    \[w_{t + 1} = w_{t} + \alpha (r_t + \gamma w_{t}^{\top } x_{t+1} - w_t^{\top } x_t) x_t\]

    The tabular setting is the one where we can afford a coordinate per state, \(x(s) \in \mathbb {R}^{|S|}\). Take the features to be one-hot, \(x : s_i \mapsto \boldsymbol {e}_i\), and identify

    \[r_i = \mathbb {E}_{a \sim \pi , s \sim p}[r(s_i)], \quad w_i = v_{\pi }(s_i)\]

    Substituting,

    \[w_{t + 1} = w_{t} + \alpha (\mathbb {E}_{a \sim \pi , s \sim p}[r(s_i)] + v(s_{t + 1}) - v(s_{t})) \cdot \boldsymbol {e}_i\]

    Since \(\boldsymbol {w}\) is the table of values and \(\boldsymbol {e}_i\) zeroes out everything else, updating the \(i\)th entry is exactly one tabular update to \(v_{\pi }(s_i)\). Generalization across states is precisely what the one-hot encoding refuses to do.

    • May 12, 2026

    Solution.

    Both grow linearly in the quantum: round robin's responsiveness is precisely what a long quantum spends.

    Exercise 1.1. No infinite fair independent sequence on a discrete space

    • November 17, 2024
    • Kellen Kanarios

    Show that a discrete probability space cannot carry an infinite sequence of independent events \(A_1, A_2, \ldots \), each of probability \(1/2\).

    Solution.

    Denote the sample space \(\mathcal {X}\). Independence of \(A_1\) and \(A_2\) splits it into four cells of probability \(1/4\) apiece:

    \[P(A_1 \cap A_2) + P(A_1 \cap A_2^c) + P(A_1^c \cap A_2) + P(A_1^c \cap A_2^c) = 1\]

    Every \(x \in \mathcal {X}\) lies in exactly one of the four, so \(\mathbb {P}(\{x\}) \leq 1/4\). Running the same construction on \(A_1, \ldots , A_n\) gives \(n\) disjoint cells and the bound \(\mathbb {P}(\{x\}) \leq 1/n\) for every \(x\); the sequence is infinite, so \(n\) is unbounded and \(\mathbb {P}(\{x\}) = 0\).

    But the space is discrete, so all of its mass sits on its atoms:

    \[\sum _{x \in \mathcal {X}} \mathbb {P}(\{x\}) = 1\]

    A countable sum of zeros cannot be one, and we have our contradiction.

    Exercise 3.2. Measurability as agreement of inner and outer measure

    • November 17, 2024
    • Kellen Kanarios

    Let \(P\) be a probability measure on a field \(\mathscr {F}_{0}\), define \(P^{\star }(A)\) for every subset \(A\) of \(\Omega \) by (3.1), and denote also by \(P\) the extension of \(P\) to \(\mathscr {F}=\sigma (\mathscr {F}_{0})\). Show that \(A\) is \(P^*\)-measurable if and only if \(P^*(A) = P_*(A)\).

    Solution.

    Suppose \(P^*(A) = P_*(A)\) and fix \(E \subset \Omega \). We must show

    \[P^*(E \cap A) + P^*(E \cap A^c) = P^*(E)\]

    The preceding part of the exercise supplies \(\overline {A}, \underline {A} \in \mathscr {F}\) with \(\underline {A} \subset A \subset \overline {A}\), and the hypothesis collapses their measures onto each other:

    \[P(\overline {A}) = P^*(A) = P_*(A) = P(\underline {A})\]

    Approximate \(E\) the same way — there is \(B \in \mathscr {F}\) with \(E \subset B\) and \(P^*(E) = P(B)\). Then

    \[P^*(E \cap A) \leq P^*(B \cap \overline {A}) = P(B \cap \overline {A})\]

    and

    \[P^*(B \cap A) \leq P^*(B \cap \underline {A}^c) = P(B \cap \underline {A}^c)\]

    so that

    \[P^*(E \cap A) + P^*(E \cap A^c) \leq P(B \cap \underline {A}^c) + P(B \cap \overline {A}) = P^*(E)\]

    as desired.

    Remark. The difficulty is bookkeeping, not measure theory: three objects live on three different domains, and conflating them is what makes the problem look impenetrable.
    1. \(P\) is defined on the initial field \(\mathscr {F}_0\), the closure over finite unions and complements of \(\Omega \).
    2. \(P^*\) is defined on the whole powerset \(\mathcal {P}(\Omega )\), but is not a measure there. In particular \(E\) need not lie in \(\mathscr {F}\), which is exactly why the argument has to route through \(B\).
    3. \(P\) (abusing notation) is \(P^*\) restricted to the \(P^*\)-measurable subsets of \(\Omega \).
    The tempting shortcut — apply finite additivity and conclude everything is \(P^*\)-measurable — fails because \(P^*\) is countably subadditive only on the \(P^*\)-measurable sets, not on \(\mathcal {P}(\Omega )\).

    Online Softmax [PI7N]

    • May 20, 2026
    • Kellen Kanarios

    This covers the math behind the online softmax algorithm required by Flash Attention (v1).

    Safe softmax

    • May 20, 2026
    • Kellen Kanarios

    The first thing we must consider is numerical precision. Namely, the original softmax operation is given by

    \[\mathrm {softmax}(\mathbf {x}) = \frac {\exp (\mathbf {x})}{\sum _{i=1}^n \exp (\mathbf {x}_i)}\]

    However, when operating with low precision data types (i.e. float16) the maximum value is \(65536\). Therefore, with \(\exp \) we can easily get numerically overflow.

    To get around this, the online softmax algorithm adheres to the safe softmax. For safe softmax, we simply multiply the numerator and denominator by \(\exp (-m)\), where \(m = \max \{x_{1}, \ldots , x_n\}\). This gives

    \[\mathrm {softmax}(\mathbf {x}) = \frac {\exp (\mathbf {x} - m)}{\sum _{i=1}^n \exp (\mathbf {x}_i - m)}\]

    Since \(x_i - m \leq 0\), this ensures that each \(\exp (x_i - m)\) is bounded in a safe range.

    Problem. Note that computing the \(\max \) over \(\mathbf {x}\) means that we must have all of the logits in a row of \(QK^T\) materialized in SMEM, or first loop over all of them to compute the max before computing the normalization constant.

    Fusing the max and normalization

    • May 20, 2026
    • Kellen Kanarios

    The online softmax algorithm fuses the max reduction into the normalization pass, so a single sweep over the row suffices to compute the normalization with the max. The key difficulty is that the denominator depends on \(n\) for each \(i\) i.e.

    \[d = \sum _{i=1}^{n} \exp (x_i - m_n)\]

    Therefore, we must find a recursive relationship such that \(d_{i+1} = f(d_i, m_i, x_{i+1})\) for some function \(f\). This would then allow us to locally compute \(d_{i+1}\) with only the local information of current \(x_{i+1}\) and the two running statistics \(d_i\) and \(m_i\). This is exactly the kind of algorithm that is conducive to memory tiling.

    Question. What is \(f(d_i, m_i, x_{i+1})\)?
    Answer.Consider \(d_{i+1} = d_i \cdot \exp (m_{i} - m_{i + 1}) + \exp (x_{i + 1} - m_{i + 1})\).
    Proof. This can be seen by directly rewriting \(d_{i + 1}\). \[ \begin {align*} d_{i + 1} &= \sum _{j = 1}^{i+1} \exp (x_j - m_{i + 1}) \\ &= \left (\sum _{j = 1}^{i} \exp (x_j - m_{i+1})\right ) + \exp (x_{i+1} - m_{i+1}) \\ &= \left (\sum _{j = 1}^{i} \exp (x_j - m_{i})\right )\exp (m_{i} - m_{i + 1}) + \exp (x_{i+1} - m_{i+1}) \\ &= d_{i} \exp (m_{i} - m_{i + 1}) + \exp (x_{i+1} - m_{i+1}) \end {align*} \]

    The running denominator \(d\) is rescaled by \(e^{m - m_{\text {new}}}\) each time a new maximum is found, keeping it consistent with the safe-softmax shift.

    online_softmax.py
    m = float("-inf")                    # running max of the logits
d = 0.0                              # running softmax denominator
for i in range(n):                   # one fused sweep for the stats
    m_new = max(m, x[i])
    d = d * exp(m - m_new) + exp(x[i] - m_new)
    m = m_new
p = [exp(x[i] - m) / d for i in range(n)]   # second pass: normalized probs
    Remark. Unfortunately, we cannot get around the second pass to compute the normalized output for \(\mathbf {p}\). However, this is not the case in Flash Attention (v1).

    Flash Attention (Fwd) [OGCS0]

    • May 27, 2026
    • Kellen Kanarios

    Unlike in the online softmax, we are not interested in the outputted probability vector \(\mathbf {p}\). Instead we are interested in the entire output matrix \(O\) given by

    \[O = \mathrm {softmax}(QK^T) V\]

    For more details see self-attention.

    Notation. In correspondence with the notation in the online softmax, we define the following: \[x_{i,j} = \mathbf {q}_i \cdot \mathbf {k}_j,\] where \(\mathbf {q}_i\) is the \(i\)th row of \(Q\) and \(\mathbf {k}_j\) is the \(j\)th row of \(K\). Similarly, \(\mathbf {o}_i\) is the \(i\)th row of the output matrix \(O\) given by \[\mathbf {o}_i = \sum _{j = 1}^{n} \frac {\exp (x_{i,j} - m_n)}{d_n} \cdot \mathbf {v}_j \]

    Now following the template provided by the online softmax, we must find a recurrence for \(\mathbf {o}_i\). Namely, we will consider the sequence \(\mathbf {o}_{i,k}'\) given by \[\mathbf {o}_{i,k}' = \sum _{j = 1}^{k} \frac {\exp (x_{i,j} - m_k)}{d_k} \cdot \mathbf {v}_j, \] such that \(\mathbf {o}_{i,n}' = \mathbf {o}_n\)

    Claim. We have the following recurrence for \(\mathbf {o}_{i,k}'\): \[ \mathbf {o}_{i,k}' = \mathbf {o}_{i, k-1} \cdot \frac {d_{k - 1} \cdot \exp (m_{k-1} - m_{k})}{d_k} + \frac {\exp (x_{i,j} - m_k)}{d_k} \cdot \mathbf {v}_k \]
    Proof. We will proceed by directly rewriting the recurrence for \(\mathbf {o}_{i,k}'\) as \[ \begin {align*} \mathbf {o}_{i,k}' &= \sum _{j = 1}^{k} \frac {\exp (x_{i,j} - m_k)}{d_k} \cdot \mathbf {v}_j \\ &= \left (\sum _{j = 1}^{k - 1} \frac {\exp (x_{i,j} - m_{k-1})}{d_{k-1}} \cdot \mathbf {v}_j\right ) \frac {d_{k - 1} \cdot \exp (m_{k-1} - m_{k})}{d_k} + \frac {\exp (x_{i,k} - m_k)}{d_k} \cdot \mathbf {v}_k \\ &= \mathbf {o}_{i, k-1} \cdot \frac {d_{k - 1} \cdot \exp (m_{k-1} - m_{k})}{d_k} + \frac {\exp (x_{i,k} - m_k)}{d_k} \cdot \mathbf {v}_k .\end {align*} \]

    Thus, we are left with the following algorithm

    flash_attention.py
    for i in range(N):                      # one query row at a time
    m = float("-inf")                    # running max of the logits
    d = 0.0                              # running softmax denominator
    o = zeros(head_dim)                  # running output accumulator
    for j in range(M):                   # stream over keys/values
        x = q[i] @ k[j]                  # logit x_{i,j}
        m_new = max(m, x)
        d_new = d * exp(m - m_new) + exp(x - m_new)
        o = o * (d * exp(m - m_new) / d_new) + (exp(x - m_new) / d_new) * v[j]
        m, d = m_new, d_new
    out[i] = o
    Remark. A key benefit of this algorithm is that it is entirely parallelizable across rows. This means that we can loop across entire tiles like in the GEMM case.

    Flash Attention (Bwd) [OGCRZ]

    • May 27, 2026
    • Kellen Kanarios

    The forward pass of flash attention avoids materializing the \(N \times N\) attention matrix by streaming an online softmax. The backward pass has to pull the same trick twice over, because the naive gradient computation wants two \(N \times N\) matrices — \(\mathbf {P}\) and \(d\mathbf {P}\). Getting there means first writing down every gradient we need, then finding a way to recompute rather than store each one.

    Notation. Following the notation in the original paper, \[\mathbf {S} = \mathbf {Q} \mathbf {K}^T, \quad \mathbf {P} = \mathrm {softmax}(\mathbf {S}), \quad \mathbf {O} = \mathbf {P} \mathbf {V},\] where \(\mathbf {Q}, \mathbf {K}, \mathbf {V}, \mathbf {O}\) are \(N \times d\) and \(\mathbf {S}, \mathbf {P}\) are \(N \times N\). For a scalar loss \(\phi \) we abbreviate the gradient with respect to any matrix \(\mathbf {X}\) as \[d\mathbf {X} = \frac {\partial \phi }{\partial \mathbf {X}},\] and write \(\mathbf {L}_i\) for the softmax denominator of row \(i\) saved by the forward pass, so that \(\mathbf {P}_{ij} = \exp (\mathbf {Q}_i \cdot \mathbf {K}_j) / \mathbf {L}_i\).

    The gradients we need for FlashAttention [4QZE]

    • August 3, 2026
    • Kellen Kanarios

    Everything downstream is chain rule; the only step with any content is differentiating through the softmax. We take the gradients in dependency order, starting from \(d\mathbf {O}\) which arrives from the layer above.

    \(d\mathbf {P}\) and \(d\mathbf {V}\) from \(\mathbf {O} = \mathbf {P}\mathbf {V}\)

    • August 3, 2026
    • Kellen Kanarios

    Both fall straight out of the product rule for matrices:

    \[ d\mathbf {P} = \frac {\partial \phi }{\partial \mathbf {O}} \frac {\partial \mathbf {O}}{\partial \mathbf {P}} = d\mathbf {O} \mathbf {V}^T, \qquad d\mathbf {V} = \frac {\partial \phi }{\partial \mathbf {O}} \frac {\partial \mathbf {O}}{\partial \mathbf {V}} = \mathbf {P}^T d\mathbf {O}. \]

    The shapes are a useful sanity check. \(d\mathbf {O}\) has one entry per output, so it is \(N \times d\); \(\mathbf {V}^T\) is \(d \times N\); their product is \(N \times N\), matching \(\mathbf {P}\). Likewise \(\mathbf {P}^T d\mathbf {O}\) is \(N \times d\), matching \(\mathbf {V}\).

    Componentwise, from \(\mathbf {O}_{ik} = \sum _j \mathbf {P}_{ij} \mathbf {V}_{jk}\),

    \[ \begin {align*} d\mathbf {P}_{ij} &= \sum _{k} \frac {\partial \phi }{\partial \mathbf {O}_{ik}} \cdot \frac {\partial \mathbf {O}_{ik}}{\partial \mathbf {P}_{ij}} = \sum _{k} d\mathbf {O}_{ik} \mathbf {V}_{jk}, \\ d\mathbf {V}_{jk} &= \sum _{i} \frac {\partial \phi }{\partial \mathbf {O}_{ik}} \cdot \frac {\partial \mathbf {O}_{ik}}{\partial \mathbf {V}_{jk}} = \sum _{i} d\mathbf {O}_{ik} \mathbf {P}_{ij} = \sum _{i} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} d\mathbf {O}_{ik} .\end {align*} \]

    That last line is worth noting already: \(d\mathbf {V}\) never needs \(\mathbf {P}\) stored, only the ability to re-evaluate \(\mathbf {P}_{ij}\) from \(\mathbf {Q}\), \(\mathbf {K}\), and \(\mathbf {L}\).

    \(d\mathbf {S}\) through the softmax

    • August 3, 2026
    • Kellen Kanarios

    Softmax acts row by row, so drop into the scalar case with \(\mathbf {s}\) and \(\mathbf {p}\) single rows. The softmax Jacobian is \(\partial \mathbf {p}_i / \partial \mathbf {s}_j = \mathbf {p}_i(\delta _{ij} - \mathbf {p}_j)\), giving

    \[ \begin {align*} d\mathbf {s}_j &= \sum _{i} d\mathbf {p}_i \cdot \frac {\partial \mathbf {p}_i}{\partial \mathbf {s}_j} \\ &= \sum _{i} d\mathbf {p}_i \cdot \mathbf {p}_i (\delta _{ij} - \mathbf {p}_{j}) \\ &= d\mathbf {p}_{j} \mathbf {p}_{j} - \mathbf {p}_{j}\sum _{i} d\mathbf {p}_{i} \mathbf {p}_{i} .\end {align*} \]

    As a row vector this is \(d\mathbf {s} = \mathbf {p} \odot (d\mathbf {p} - \mathbf {p} \cdot d\mathbf {p})\), where the subtracted term is the scalar \(\mathbf {p} \cdot d\mathbf {p}\) broadcast across the row. Collecting those scalars into a column \(\mathbf {D}\) with \(\mathbf {D}_i = \mathbf {P}_i \cdot d\mathbf {P}_i\) recovers the matrix form

    \[d\mathbf {S} = \mathbf {P} \odot (d\mathbf {P} - \mathbf {D}).\]

    \(\mathbf {D}\) is the piece that will cause trouble later: it is a dot product over an entire row of \(\mathbf {P}\), which is exactly the thing we refuse to materialize.

    \(d\mathbf {Q}\) and \(d\mathbf {K}\) from \(\mathbf {S} = \mathbf {Q}\mathbf {K}^T\)

    • August 3, 2026
    • Kellen Kanarios

    One more chain rule, and the sums run over opposite indices:

    \[ \begin {align*} d\mathbf {Q}_{i} &= \sum _{j} d\mathbf {S}_{ij} \mathbf {K}_{j} = \sum _{j} \mathbf {P}_{ij} \left (d\mathbf {P}_{ij} - \mathbf {D}_i\right ) \mathbf {K}_{j}, \\ d\mathbf {K}_{j} &= \sum _{i} d\mathbf {S}_{ij} \mathbf {Q}_{i} = \sum _{i} \mathbf {P}_{ij} \left (d\mathbf {P}_{ij} - \mathbf {D}_i\right ) \mathbf {Q}_{i} .\end {align*} \]

    Recomputing instead of storing

    • August 3, 2026
    • Kellen Kanarios

    Every gradient above is expressed through \(\mathbf {P}_{ij}\) and \(d\mathbf {P}_{ij}\), both \(N \times N\). Materializing either one is exactly the quadratic memory cost the forward pass went to such lengths to avoid, so the backward pass has to be able to produce those entries on demand.

    💡 Insight. Both are recoverable from the \(N \times d\) tensors already resident in memory. The forward pass saved \(\mathbf {L}\), so \[\mathbf {P}_{ij} = \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}},\] and \(d\mathbf {P}\) is just an inner product of two rows, \[d\mathbf {P}_{ij} = \sum _{k} d\mathbf {O}_{ik} \mathbf {V}_{jk} = d\mathbf {O}_{i} \cdot \mathbf {V}_j.\] Neither ever requires an \(N \times N\) intermediate.

    Substituting both into the previous section leaves \(d\mathbf {Q}\) and \(d\mathbf {K}\) in terms of \(\mathbf {Q}\), \(\mathbf {K}\), \(\mathbf {V}\), \(d\mathbf {O}\), \(\mathbf {L}\), and \(\mathbf {D}\) alone:

    \[ \begin {align*} d\mathbf {Q}_{i} &= \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \left (d\mathbf {O}_{i} \cdot \mathbf {V}_j - \mathbf {D}_i\right ) \mathbf {K}_{j}, \\ d\mathbf {K}_{j} &= \sum _{i} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \left (d\mathbf {O}_{i} \cdot \mathbf {V}_j - \mathbf {D}_i\right ) \mathbf {Q}_{i}. .\end {align*} \]

    Getting \(\mathbf {D}\) for free

    • August 3, 2026
    • Kellen Kanarios

    One problem survives. \(\mathbf {D}_i = \mathbf {P}_i \cdot d\mathbf {P}_i\) is a dot product over a full row, so computing it inside the streaming loop would mean a reduction over all \(j\) before any tile of \(d\mathbf {Q}_i\) could be finished. This is the same global dependency the online softmax was designed to break.

    The way out is that the row sum has already been computed once, in the forward pass. Expanding and pulling \(d\mathbf {O}_i\) out of the sum:

    \[ \begin {align*} \mathbf {D}_i &= \mathbf {P}_{i} \cdot d\mathbf {P}_{i} \\ &= \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} d\mathbf {P}_{ij} \\ &= \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \left (d\mathbf {O}_{i} \cdot \mathbf {V}_{j}\right ) \\ &= d\mathbf {O}_{i} \cdot \sum _{j} \frac {\exp \left (\mathbf {Q}_{i} \cdot \mathbf {K}_{j}\right )}{\mathbf {L}_{i}} \mathbf {V}_{j} \\ &= d\mathbf {O}_{i} \cdot \mathbf {O}_{i} .\end {align*} \]

    The inner sum is precisely the definition of \(\mathbf {O}_i\). So \(\mathbf {D}\) is a single elementwise product of \(d\mathbf {O}\) and \(\mathbf {O}\) summed along the head dimension — one \(O(Nd)\) pass over tensors we already have, done once before the backward loop begins.

    Summary

    • May 27, 2026
    • Kellen Kanarios

    Forward pass. Store \(\mathbf {O}\) and the softmax denominators \(\mathbf {L}\), both \(O(Nd)\).

    Between the passes. Receive \(d\mathbf {O}\) from the layer above (automatic in JAX), then precompute \(\mathbf {D}_i = d\mathbf {O}_i \cdot \mathbf {O}_i\) in \(O(N)\) memory.

    Backward pass. Stream over tiles, recomputing \(\mathbf {P}_{ij}\) from \(\mathbf {Q}, \mathbf {K}, \mathbf {L}\) and \(d\mathbf {P}_{ij}\) from \(d\mathbf {O}, \mathbf {V}\) as needed:

    1. \(d\mathbf {V}_j = \sum _i \mathbf {P}_{ij} d\mathbf {O}_i\), accumulated over query tiles.
    2. \(d\mathbf {Q}_i = \sum _j \mathbf {P}_{ij}(d\mathbf {O}_i \cdot \mathbf {V}_j - \mathbf {D}_i)\mathbf {K}_j\), accumulated over key tiles.
    3. \(d\mathbf {K}_j = \sum _i \mathbf {P}_{ij}(d\mathbf {O}_i \cdot \mathbf {V}_j - \mathbf {D}_i)\mathbf {Q}_i\), accumulated over query tiles.

    Each accumulator is \(O(d)\) per row or column, so the whole backward pass stays linear in \(N\).

    The cache controller

    • August 3, 2026
    • Kellen Kanarios

    Silent upgrades. If a cache in \(E\) may upgrade to \(M\) silently, the directory never learns the line went dirty, and the value it hands to the next GetS or GetM is stale. There are two consistent ways out: forbid the silent upgrade, in which case no forwarding is needed; or allow it and treat \(E\) exactly like \(M\), forwarding everything. Neither requires a writeback on PutE. I take the first, matching the table.

    Signaling exclusivity. The directory needs a way to tell a requester "you are the first reader, take the line exclusive." That is a new ExclusiveData message: receiving it in \(IS^D\) lands the cache in \(E\) rather than \(S\). It turns out to also be the key to the second race below.

    Remark. Once PutE or PutM has been sent, \(EI^A\) and \(MI^A\) are functionally identical. Both appear above for completeness, but transitioning from \(E\) straight into \(MI^A\) verifies the same.

    The directory controller

    • August 3, 2026

    Symmetrically, the directory gains an \(E^D\) state, which for completeness is kept distinct from \(M^D\) but could be folded into it.

    Forwards arriving before exclusive data

    • August 3, 2026
    • Kellen Kanarios

    The first processor issues GetS and waits in \(IS^D\), while the home directory has already moved to \(E\) and sent it ExclusiveData. A second processor then issues GetM, and home's Fwd-GetM overtakes the data in flight.

    Fix. Stall Fwd-GetM and Fwd-GetS in \(IS^D\) until the data lands. This is safe here because the data is on the response channel, which no stall can block.

    Losing exclusive data to an invalidation

    • August 3, 2026
    • Kellen Kanarios

    The nastier version of the same race: the invalidation arrives before the forward. By the \(II^A\) rule inherited from MSI, a PutAck in that state drops the line to \(I\). This discards data a forwarded request is about to ask for.

    Example.
    1. Proc_1 load-misses → \(IS^D\)
    2. Home takes the first GetS from Proc_1 → \(E\), sends ExclusiveData
    3. Proc_2 issues GetM → \(IM^{AD}\)
    4. Home sends Inv to Proc_1
    5. Home forwards Fwd-GetM to Proc_1
    6. Proc_1 receives Inv → \(II^D\)
    7. Proc_1 receives ExclusiveData → \(I\), and the data is lost

    Fix. ExclusiveData pays for itself a second time. Because the message is distinguishable from ordinary Data, a cache receiving it in \(II^D\) knows it was the first reader and transitions to \(E\) instead of \(I\). There, the pending Fwd-GetM or Fwd-GetS is handled correctly.

    Losing data to a PutM/Fwd-GetM race

    • August 3, 2026
    • Kellen Kanarios

    Consider the PutM rule that downgrades a cache from modified to invalid. The evicting cache must not drop the data when it sends PutM, because it may still have to service a forwarded request; it transitions to \(MI^A\) and keeps the value. But nothing stops the PutAck from arriving first, taking it to \(I\) before the Fwd-GetM shows up. The data is gone and the forwarded request has nobody to answer it.

    Fix. Add the \(M^D\) state to the directory controller. While in \(M^D\), a PutM from a node that is not the current owner stalls until the data arrives. I have not found a cleaner way to close this race without the extra state.

    Deadlocking two stores against a load

    • August 3, 2026

    Why three virtual channels

    • March 24, 2026
    • Kellen Kanarios

    The valid-invalid protocol shipped with the Murphi docs uses two Virtual Channels. A directory protocol needs three: one each for requests, forwarded requests, and responses. The reason is that deadlock is a cycle in the dependency graph, so it suffices to exhibit one.

    • A node issues GetS to the directory, giving an edge \(N_1 \to D\).
    • The directory forwards Fwd-GetS to the owner, extending the chain to \(N_1 \to D \to N_2\).
    • The owner sends data back to the requester, closing the cycle \(N_1 \to D \to N_2 \to N_1\).

    The data closing that cycle would travel on the same channel as the requests waiting behind it, so a full request buffer wedges the response that would drain it. Partitioning by message class breaks the cycle:

    • Request: GetS, GetM, PutS, PutM
    • Forwarded: Fwd-GetS, Fwd-GetM, Inv, PutAck
    • Response: Data, InvAck

    These are enumerated directly in the model's MessageType.

    msi.m
    MessageType: enum {
  GetS,           -- request for shared copy
  GetM,           -- request for modified (exclusive) copy
  PutS,           -- evict shared copy
  PutM,           -- evict modified copy (w/ data)

  FwdGetS,        -- forwarded GetS to owner
  FwdGetM,        -- forwarded GetM to owner
  Inv,            -- invalidation request

  Data,           -- data response
  InvAck,         -- invalidation acknowledgment
  PutAck          -- put acknowledgment
};

      PT_IS_DI,    -- sent GetS, got Inv, waiting for Data then go to I
      PT_IM_AD,    -- sent GetM (from I), waiting for Data and InvAcks
      PT_SM_AD,    -- sent GetM (from S), waiting for Data and InvAcks
      PT_IM_A,     -- got Data for GetM, waiting for remaining InvAcks
      PT_MI_A,     -- sent PutM, waiting for PutAck
      PT_SI_A,     -- sent PutS, waiting for PutAck
      PT_II_A      -- waiting for PutAck, already invalidated
    };
    val: Value;
    ack: AckCount;  -- tracks InvAck count
  End;
    Remark. load, store, and replacement only move the protocol between stable states. To simulate the system it is therefore enough to implement the rules that initiate those transitions evict from modified, load from invalid, and let the model checker drive the transient states from there.

    The directory controller

    • August 3, 2026
    • Kellen Kanarios

    The directory side starts from the analogous table.

    This table is where the first real gap shows up. It gives the directory a single transient state, and the races below force a second one, \(M^D\).

    Losing data to a PutM/Fwd-GetM race

    • August 3, 2026
    • Kellen Kanarios

    Consider the PutM rule that downgrades a cache from modified to invalid. The evicting cache must not drop the data when it sends PutM, because it may still have to service a forwarded request; it transitions to \(MI^A\) and keeps the value. But nothing stops the PutAck from arriving first, taking it to \(I\) before the Fwd-GetM shows up. The data is gone and the forwarded request has nobody to answer it.

    Fix. Add the \(M^D\) state to the directory controller. While in \(M^D\), a PutM from a node that is not the current owner stalls until the data arrives. Leaving \(M^D\) for \(M\) requires the new owner to send data back to the directory even on a three-hop transaction, so the directory learns that the forward actually completed. I have not found a cleaner way to close this race without the extra state.

    Deadlocking two stores against a load

    • August 3, 2026
    • Kellen Kanarios

    The \(M^D\) fix introduces a deadlock of its own. Take two processors that store-miss and a third that load-misses. The second store wins at the directory: the first store gets data and moves \(IM^{AD} \to IM^{A}\), then the second triggers a Fwd-GetM that takes ownership away from it.

    Meanwhile the load miss sits in \(IS^D\). When its Inv arrives, the table says to stall — and because Inv and Fwd-GetM share the forwarded channel, that stall blocks the Fwd-GetM behind it. The winning processor never receives the data, and nothing ever drains the channel.

    Fix. Another transient state absent from the table: \(II^A\), meaning "was in \(IS^A\), got invalidated, now waiting on PutAck before settling in \(I\)". The invalidation is processed rather than stalled, so the forwarded channel keeps moving.

    Not clearing the owner too eagerly

    • August 3, 2026
    • Kellen Kanarios

    One more correction to the table: when the home directory is in \(M\) and receives a GetS, it must not clear the owner field as the figure directs. Once in \(S^D\), the directory can no longer tell whether an incoming PutM came from the owner (and should stall) or from a stale node. The owner is only cleared once the data has actually arrived.

    MESI in Murphi [QTSW]

    • August 3, 2026
    • Kellen Kanarios

    With those states in place the rest of MSI is mechanical, and MESI is a short step from it (modulo two design choices and two more races).

    The cache controller

    • August 3, 2026
    • Kellen Kanarios

    Silent upgrades. If a cache in \(E\) may upgrade to \(M\) silently, the directory never learns the line went dirty, and the value it hands to the next GetS or GetM is stale. There are two consistent ways out: forbid the silent upgrade, in which case no forwarding is needed; or allow it and treat \(E\) exactly like \(M\), forwarding everything. Neither requires a writeback on PutE. I take the first, matching the table.

    Signaling exclusivity. The directory needs a way to tell a requester "you are the first reader, take the line exclusive." That is a new ExclusiveData message: receiving it in \(IS^D\) lands the cache in \(E\) rather than \(S\). It turns out to also be the key to the second race below.

    Remark. Once PutE or PutM has been sent, \(EI^A\) and \(MI^A\) are functionally identical. Both appear above for completeness, but transitioning from \(E\) straight into \(MI^A\) verifies the same.

    The directory controller

    • August 3, 2026
    • Kellen Kanarios

    Symmetrically, the directory gains an \(E^D\) state, which for completeness is kept distinct from \(M^D\) but could be folded into it.

    Forwards arriving before exclusive data

    • August 3, 2026
    • Kellen Kanarios

    The first processor issues GetS and waits in \(IS^D\), while the home directory has already moved to \(E\) and sent it ExclusiveData. A second processor then issues GetM, and home's Fwd-GetM overtakes the data in flight.

    Fix. Stall Fwd-GetM and Fwd-GetS in \(IS^D\) until the data lands. This is safe here because the data is on the response channel, which no stall can block.

    Losing exclusive data to an invalidation

    • August 3, 2026
    • Kellen Kanarios

    The nastier version of the same race: the invalidation arrives before the forward. By the \(II^A\) rule inherited from MSI, a PutAck in that state drops the line to \(I\). This discards data a forwarded request is about to ask for.

    Example.
    1. Proc_1 load-misses → \(IS^D\)
    2. Home takes the first GetS from Proc_1 → \(E\), sends ExclusiveData
    3. Proc_2 issues GetM → \(IM^{AD}\)
    4. Home sends Inv to Proc_1
    5. Home forwards Fwd-GetM to Proc_1
    6. Proc_1 receives Inv → \(II^D\)
    7. Proc_1 receives ExclusiveData → \(I\), and the data is lost

    Fix. ExclusiveData pays for itself a second time. Because the message is distinguishable from ordinary Data, a cache receiving it in \(II^D\) knows it was the first reader and transitions to \(E\) instead of \(I\). There, the pending Fwd-GetM or Fwd-GetS is handled correctly.

    The process abstraction, what the OS has to support to maintain it, and the data structure that holds it together.

    Process [FCHM]

    • May 12, 2026
    • Kellen Kanarios

    A running program, plus all the state the OS needs to pause it and resume it later. A process consists of:

    1. Memory: an Address space holding the program's code, stack, and heap.
    2. Registers: general-purpose registers carrying current computation, plus special-purpose registers:
      • Program counter (PC): the next instruction to run.
      • Stack pointer and frame pointer: where the process sits on its stack.

    A process moves between three states:

    • running: currently on a CPU.
    • ready: runnable, waiting for the Scheduling to give it a CPU.
    • blocked: waiting on I/O or another event, not runnable.
    Remark. Threads (see Concurrency Intro) share an address space within a process but each have their own PC, register set, and stack.

    Process API [JJ45]

    • May 12, 2026
    • Kellen Kanarios

    The minimum operations any OS must expose for working with Processes:

    1. Create: load a program from disk, set up its address space (stack, heap, code), and jump to main. The OS also initializes argc/argv.
    2. Destroy: kill a misbehaving or unwanted process.
    3. Wait: block until another process completes — useful for ordering dependent work.
    4. Miscellaneous control: e.g. suspend / resume.
    5. Status: report on running processes.
    Remark. The stack is allocated up front. The heap starts small and grows via malloc, which calls into the OS (brk/sbrk) when it runs out of headroom.

    On Unix, the concrete realization of this API uses fork(), wait(), and exec() — covered separately.

    Process control block [JE53]

    • May 12, 2026
    • Kellen Kanarios

    The kernel-side data structure holding all per-process state. There is one PCB per Process, threaded together into the process list. The PCB is what the OS reads and writes during a Context switch: the saved register set lives here, as does the process state, the open files, the parent pointer, and so on.

    An example from xv6:

    // the registers xv6 will save and restore
// to stop and subsequently restart a process
struct context {
  int eip;
  int esp;
  int ebx;
  int ecx;
  int edx;
  int esi;
  int edi;
  int ebp;
};
// the different states a process can be in
enum proc_state { UNUSED, EMBRYO, SLEEPING, RUNNABLE, RUNNING, ZOMBIE };
// the information xv6 tracks about each process
// including its register context and state
struct proc {
  char *mem;                 // Start of process memory
  uint sz;                   // Size of process memory
  char *kstack;              // Bottom of kernel stack for this process
  enum proc_state state;     // Process state
  int pid;                   // Process ID
  struct proc *parent;       // Parent process
  void *chan;                // If non-zero, sleeping on chan
  int killed;                // If non-zero, have been killed
  struct file *ofile[NOFILE]; // Open files
  struct inode *cwd;         // Current directory
  struct context context;    // Switch here to run process
  struct trapframe *tf;      // Trap frame for the current interrupt
};
    Remark. Threads need an analogous thread control block; see Concurrency Intro.

      Exercise 1. fork() copies the address space, not the variable

      • May 12, 2026
      • Kellen Kanarios

      Write a program that calls fork(). Before forking, set a variable — say x — to 100. What is its value in the child? What happens when parent and child both change it?

      Solution.

      The child gets a copy of the parent's address space, \(x\) included. Each subsequent write lands in that process's own copy, so neither sees the other's change.

      Solution.

      Both have access to the same descriptor. Concurrent writes can in principle interleave, but in my runs whichever process was scheduled first always finished writing before the other started — plausibly a scheduling artifact rather than a guarantee.

      Exercise 1. When SJF matches FIFO

      • May 12, 2026
      • Kellen Kanarios

      For what types of workloads does SJF scheduling deliver the same turnaround times as FIFO scheduling?

      Solution.

      Workloads that arrive in increasing order of total job time — FIFO is then already running them shortest-first.

      Exercise 2. When SJF matches round robin

      • May 12, 2026
      • Kellen Kanarios

      For what workloads and quantum lengths does SJF deliver the same response times as Round-robin scheduling?

      Solution.

      Short jobs and long quanta. A quantum long enough to hold a whole job turns round robin into run-to-completion, and short jobs make the ordering hardly matter.

      Exercise 3. Response time under SJF as jobs grow

      • May 12, 2026
      • Kellen Kanarios

      What happens to response time under SJF as job lengths increase?

      Solution.

      It degrades: the longest job waits out every shorter one ahead of it, so as those grow the response time grows with them.

      Exercise 4. Worst-case response time under round robin

      • May 12, 2026
      • Kellen Kanarios

      What happens to response time under round robin as the quantum grows? Can you write the worst-case response time for \(N\) jobs?

      Solution.

      Job \(i\) waits out the \(i - 1\) slices ahead of it, so with quantum \(S\) the worst case is the last job's:

      \[\mathrm {RT}_{\max } = S(N - 1)\]

      and averaging over the \(N\) jobs halves it,

      \[\overline {\mathrm {RT}} = \frac {1}{N} \sum _{i = 1}^{N} (i - 1)S = \frac {S}{N} \cdot \frac {N(N-1)}{2} = \frac {S(N - 1)}{2}\]

      Both grow linearly in the quantum: round robin's responsiveness is precisely what a long quantum spends.
